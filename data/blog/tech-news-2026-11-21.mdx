이번 주 후반은 서버 쪽 소식이 몰렸습니다. 1년을 기다린 PostgreSQL 19가 나왔고, 그 앞에 서 있는 NGINX와 뒤에서 도는 Ruby 런타임에는 동시에 치명적인 취약점이 공개됐습니다. 마지막으로 개발자 노트북에도 해당되는 Windows 잠금 화면 우회 기법을 정리합니다.

## 1. PostgreSQL 19 정식 출시: REPACK, 읽기 일관성 있는 스탠바이, get-or-create

**무엇인가요?**

PostgreSQL Global Development Group이 11월 19일 PostgreSQL 19를 정식 출시했습니다. 10월에 RC 1이 나오며 예고했던 날짜 그대로입니다. 운영 편의(블로트 정리, 자동 VACUUM), 복제, 개발자용 SQL 기능이 고르게 손봐졌습니다.

**핵심 내용**

- **`REPACK` 명령**: 테이블 블로트를 회수하고 인덱스 순서대로 재정렬하는 새 명령입니다. `REPACK (CONCURRENTLY)`로 실행하면 읽기와 쓰기를 막지 않고 처리합니다. 기존 `VACUUM FULL`과 `CLUSTER`를 대신하는 명령이며, 두 명령은 호환성 때문에 남아 있습니다. 그동안 pg_repack 확장을 따로 설치해 쓰던 작업이 코어로 들어온 셈입니다.
- **스탠바이에서 read-your-writes**: 새 `WAIT FOR LSN` 명령으로 스탠바이 세션이 특정 WAL 위치까지 반영될 때를 기다린 뒤 조회할 수 있습니다. 주 서버에 쓰고 곧바로 읽기 복제본에서 조회했더니 방금 쓴 데이터가 없다는, 흔한 문제를 DB 차원에서 풀 수 있게 됐습니다.
- **`INSERT ... ON CONFLICT DO SELECT`**: 충돌한 기존 행을 `RETURNING`으로 돌려받을 수 있습니다. 필요하면 `FOR UPDATE`/`FOR SHARE`로 잠글 수도 있습니다. 있으면 가져오고 없으면 만드는 "get or create"를 왕복 한 번으로 끝낼 수 있습니다.
- **논리 복제 편의**: 첫 논리 복제 슬롯을 만들면 실효 WAL 레벨이 자동으로 `logical`로 올라가서, 서버 재시작 없이 논리 복제를 켤 수 있습니다(`effective_wal_level`로 확인). `FOR ALL SEQUENCES`로 시퀀스 값 복제, `FOR ALL TABLES`의 `EXCEPT` 절도 추가됐습니다.
- **그 밖의 개발자 기능**: `COPY`의 JSON 출력, SQL/JSON path 문자열 메서드(`lower()`, `upper()`, `replace()` 등), 윈도 함수 `lag()`/`lead()` 등의 `IGNORE NULLS`, 날짜와 타임스탬프 범위를 받는 `random()`이 들어왔습니다. 공지에 따르면 외래 키 검사도 빨라져 대량 삽입이 테스트에서 2배 가까이 빨라졌습니다.
- **플랜 고정 도구**: 새 확장 `pg_plan_advice`와 `pg_stash_advice`로 플래너의 결정을 기술하고 재현하고, 쿼리 식별자별로 저장해 적용할 수 있습니다.

**주의할 점**

릴리스 노트의 "Migration to Version 19" 항목이 꽤 깁니다. 눈여겨볼 것만 추리면 다음과 같습니다.

- **JIT가 기본으로 꺼집니다.** JIT를 켤지 판단하는 비용 추정이 믿을 만하지 않았다는 이유입니다. 큰 분석 쿼리를 많이 돌린다면 직접 다시 켜야 합니다.
- **인증**: RADIUS 인증이 제거됐고, md5 비밀번호 로그인에 성공하면 경고가 남습니다(`md5_password_warnings`로 끌 수 있음). md5는 이후 버전에서 제거될 예정이니 SCRAM으로 옮겨 두는 편이 좋습니다.
- **설정 변경**: `io_workers`가 사라지고 `io_min_workers`/`io_max_workers`로 바뀌었습니다. `max_locks_per_transaction` 기본값은 64에서 128이 됐고, `standard_conforming_strings`는 항상 `on`입니다.
- **동작 변경**: 행이 없을 때 `json_array()`가 NULL 대신 빈 JSON 배열을 돌려줍니다. 결과가 NULL인지로 분기하던 코드는 확인이 필요합니다.
- **pg_upgrade 거부 조건**: btree_gist로 만든 `inet`/`cidr` 인덱스가 있거나, 데이터베이스·역할 이름에 줄바꿈 문자가 있으면 업그레이드가 거부됩니다. 전문 검색과 pg_trgm 인덱스는 업그레이드 후 재색인이 권장됩니다.

**개발자에게 왜 중요한가요?**

Node.js 백엔드에서 Prisma나 Drizzle로 upsert를 짤 때 "충돌하면 기존 행 반환"을 위해 쿼리를 두 번 날리거나 `DO UPDATE SET id = id` 같은 꼼수를 쓰던 경우가 많았습니다. 이것이 정식 문법으로 들어왔고, 읽기 복제본 지연 문제도 애플리케이션 쪽 우회 없이 다룰 수 있게 됐습니다. 다만 ORM이 새 문법을 지원하기까지는 시간이 걸리고, 관리형 DB(RDS, Cloud SQL, Supabase 등)에서 19를 고를 수 있게 되는 시점도 서비스마다 다릅니다.

## 2. NGINX HTTP/2, 10년 묵은 원격 코드 실행: CVSS 9.2 다섯 건

**무엇인가요?**

11월 18일 NGINX 보안 릴리스로 CVSS 4.0 기준 9.2점 취약점 다섯 건이 고쳐졌습니다. 가장 주목받는 CVE-2026-123007("nginx2root")은 HTTP/2의 송신 윈도 계산에서 생기는 정수 언더플로로, 2015년에 나온 1.9.5부터 1.31.8까지 모든 오픈소스 릴리스에 들어 있었습니다. Wiz, Rapid7, Xint 등 여러 팀이 각자 찾아 보고했습니다.

**핵심 내용**

- **CVE-2026-123007**: HTTP/2만 켜져 있으면 해당됩니다. Wiz는 64비트 시스템에서 백엔드나 서드파티 모듈 없이 정적 파일만 서빙하는 평범한 HTTPS 구성으로 시연했고, ASLR로도 막히지 않는다고 설명했습니다.
- **CVE-2026-123633**: HTTP/2 연결의 use-after-free입니다. 리버스 프록시로 요청을 넘기는 중 워커의 연결 슬롯이 부족해질 때 발생합니다.
- **나머지 세 건**: 변수로 조합한 프록시 서버 이름과 SSI/mirror 서브요청 조합(CVE-2026-123634), HTTP/3(CVE-2026-121810), 메일 프록시(CVE-2026-113425) 구성에 해당합니다.
- **수정 버전**: 오픈소스 1.31.9(mainline)와 1.30.7(stable)이 다섯 건을 모두 고칩니다. NGINX Plus는 37.3.0.1, 37.0.8.1 등의 빌드로 나뉘어 있고, 영향 범위를 두고 보도마다 차이가 있으니 F5 권고문(K000163926)을 직접 확인하는 편이 안전합니다.
- **실제 악용**: 11월 18일 기준으로 보고된 공격은 없습니다. 다만 공개 PoC가 GitHub에 올라왔습니다.

**당장 할 수 있는 일**

업그레이드가 우선입니다. 이때 `nginx -s reload`만 하면 예전 실행 파일이 계속 돌기 때문에, 완전히 재시작하거나 바이너리 라이브 업그레이드를 해야 한다는 점이 함정입니다. 바로 올릴 수 없다면 임시로 HTTP/2를 끌 수 있습니다.

```nginx
server {
    # 1.25.1 이상: http2 지시어로 끄고, listen의 http2 파라미터도 제거
    listen 443 ssl;
    http2 off;
}
```

HTTP/2를 끄면 앞의 두 건(123007, 123633)만 막히고 나머지 세 건은 그대로입니다. 1.25.0 이하라면 `listen` 지시어에서 `http2`를 빼는 방식입니다.

**개발자에게 왜 중요한가요?**

Node.js나 Next.js 앱 앞에 NGINX를 리버스 프록시로 두는 구성은 아주 흔하고, 공식 `nginx` Docker 이미지를 베이스로 정적 파일을 서빙하는 프런트엔드 배포도 많습니다. 직접 설치하지 않았더라도 Dockerfile의 `FROM nginx:...` 태그가 고정돼 있다면 이미지를 다시 받아 빌드해야 합니다. CDN이나 WAF가 앞에서 HTTP/2를 종단하면 일부 완화되지만, 원본 서버가 직접 노출돼 있다면 기대면 안 됩니다.

## 3. Ruby2Shell: 문자열 대소문자 변환 한 번에 1바이트 힙 오버플로

**무엇인가요?**

Ruby 팀이 11월 18일 3.3.14, 3.4.13, 4.0.10을 내놓으며 인터프리터 자체의 취약점 일곱 건을 고쳤습니다. 그중 CVE-2026-132825("Ruby2Shell")는 ISO-8859-1, Windows-1252 같은 단일 바이트 인코딩 문자열의 대소문자를 바꿀 때 생깁니다. 독일어 ß(0xDF)는 대문자로 바꾸면 "SS" 두 글자가 되는데, 출력 공간을 한 바이트만 확인하는 바람에 힙 버퍼 끝을 1바이트 넘어 쓰게 됩니다. 이 코드는 Ruby 2.4.0부터 있었습니다.

**핵심 내용**

- **영향 버전**: 4.0.0~4.0.9, 3.4.0~3.4.12, 3.3.0~3.3.13. 지원이 끝난 3.2 이하는 수정판이 없습니다.
- **함께 고쳐진 여섯 건**: 정규식 컴파일의 double free와 힙 오버플로, `Regexp#to_s` 오버플로, 대소문자 무시 매칭의 범위 밖 읽기 등입니다. 보안 업체 정리에 따르면 Ruby 팀은 일곱 건 중 다섯 건에서 원격 코드 실행 PoC를 확인했습니다.
- **Rails와 Sinatra**: 보안 업체들은 기본 설정의 Rails와 classic 스타일 Sinatra 앱이 인증 없이 도달 가능한 경로를 가진다고 전했습니다. GitLab, Mastodon, Discourse처럼 Ruby를 번들한 자체 호스팅 제품도 해당됩니다.
- **실제 악용**: 11월 19일 기준 보고된 공격은 없지만, 연구진이 공개 후 약 일주일 뒤 PoC를 공개할 예정이라고 합니다.

**당장 할 수 있는 일**

```bash
ruby -v   # 3.3.14 / 3.4.13 / 4.0.10 이상인지 확인
```

이 문제는 gem이 아니라 인터프리터에 있으므로 `bundle update`로는 고쳐지지 않습니다. `.ruby-version`, Dockerfile의 베이스 이미지 태그, CI의 Ruby 버전을 올리고 이미지를 다시 빌드한 뒤 앱 서버를 재시작해야 합니다. 배포판 패키지는 버전 번호를 그대로 둔 채 수정을 넣는 경우도 있으니 배포판 보안 공지도 함께 보세요. 별도 우회 설정은 공개되지 않았습니다.

**개발자에게 왜 중요한가요?**

JS 중심 팀이라도 사내 GitLab, 문서용 Discourse, 오래된 Rails 관리자 도구가 어딘가에서 돌고 있는 경우가 많습니다. 직접 Ruby 코드를 짜지 않아도 Ruby를 품은 도구를 운영하고 있다면 해당된다는 점이 이번 건의 핵심입니다. 공급사 패치가 나올 때까지는 VPN이나 IP 허용 목록 뒤로 숨기는 것이 현실적인 대응입니다.

## 4. FastUnlock: 패치 없는 Windows 잠금 화면 우회

**무엇인가요?**

11월 19일 한 연구자가 GitHub에 Windows 잠금 화면에서 프로그램을 실행하는 기법 FastUnlock을 공개했습니다. 잠금 화면의 내레이터(Narrator)와 Microsoft 계정 복구 옵션을 이용하는 방식이며, ThreatLocker가 직접 시험해 동작을 확인했습니다. 11월 20일 기준 Microsoft의 수정은 없고 CVE도 배정되지 않았습니다.

**핵심 내용**

- **전제 조건**: 기기를 물리적으로 손에 쥐고 있어야 하고, 잠금 화면 복구 옵션에서 Microsoft 계정에 접근할 수 있어야 합니다. 모든 기기에서 통하지는 않는다고 합니다.
- **얻는 권한**: ThreatLocker 시험에서는 관리자가 아닌 제한된 계정(WSIAccount)으로 프로그램이 실행됐습니다.
- **BitLocker**: 암호화를 깨거나 키를 빼내는 기법은 아닙니다. 다만 TPM 자동 잠금 해제만 쓰는 BitLocker는 이미 부팅된 상태라 이 시나리오를 막아 주지 못합니다.
- **실제 악용**: 보고된 사례는 없습니다.

**당장 할 수 있는 일**

BitLocker에 부팅 PIN을 추가하고, 노트북을 두고 자리를 뜰 때는 잠금 상태로 두기보다 종료하거나 최대 절전 모드로 전환하는 것이 권장됩니다. 잠금 화면 하나에만 기대지 말라는 것이 요지입니다.

**개발자에게 왜 중요한가요?**

개발자 노트북에는 클라우드 자격 증명, SSH 키, `.env` 파일, 브라우저에 로그인된 관리자 콘솔이 몰려 있습니다. 관리자 권한이 아니더라도 사용자 영역 파일에 접근할 수 있느냐는 별개 문제이므로, 출장이나 카페 작업이 잦다면 이번 기회에 부팅 PIN을 설정해 두는 편이 좋습니다.

## 마무리

PostgreSQL 19가 pg_repack, upsert 꼼수, 복제본 지연 우회처럼 앱과 운영 쪽에서 해 오던 일을 DB 안으로 끌어들인 같은 주에, NGINX와 Ruby는 10년 가까이 묵은 코드가 한꺼번에 드러났습니다. 새 기능은 천천히 도입해도 되지만, 내 스택 아래에 깔린 런타임과 프록시의 버전은 이번 주 안에 확인해야 합니다.
