오늘은 서버를 운영하는 분이라면 바로 확인해야 할 Java 보안 이슈로 시작합니다. 이어서 OpenAI의 새 모델, 2년 가까이 다듬어 온 Solid 2.0 정식판, 그리고 코딩 에이전트에게 셸을 맡길 때 실제로 무엇이 잘못되는지를 보여 주는 사고 분석을 모았습니다.

## 1. Java4Shell: OpenJDK Base64 디코더에서 인증 없는 원격 코드 실행 (CVE-2026-114938)

**무엇인가요?**

보안 회사 Calif가 11월 17일 OpenJDK의 Base64 디코더에서 힙 메모리 손상 취약점을 공개했습니다. 같은 날 Oracle 패치와 OpenJDK 권고문도 함께 나왔습니다. 문제는 Java 코드가 아니라 HotSpot JIT가 Base64 디코딩을 빠르게 처리하려고 쓰는 AVX-512 전용 네이티브 경로(intrinsic)에 있습니다. 패딩이 잘못된 입력을 넣으면 출력 길이 계산이 음수가 되고, 배열 끝을 넘어 최대 62바이트를 덮어씁니다. Java 쪽에서 `IllegalArgumentException`이 나긴 하지만, 이미 메모리를 덮어쓴 뒤입니다.

**핵심 내용**

- **심각도**: Calif는 CVSS 4.0 기준 9.2(치명), Oracle은 공격 복잡도를 높게 보고 CVSS 3.1 기준 8.1로 매겼습니다.
- **영향 범위**: OpenJDK 권고문은 17, 21, 25, 27 라인을 대상으로 하고, Calif는 17.0.6 이후 빌드부터 영향이 있다고 밝혔습니다. Corretto, Temurin, Zulu, Liberica 같은 배포판도 같은 코드를 쓰므로 해당됩니다. 일반 Java 8과 11은 권고 대상에 없습니다.
- **하드웨어 조건**: AVX-512 VBMI를 지원하는 x86-64 CPU(Intel Ice Lake 이후 서버, AMD Zen 4 이후)에서만 해당 경로가 동작합니다. ARM64(Graviton, Apple Silicon 등)는 영향이 없습니다. 요즘 클라우드 x86 인스턴스는 이 조건을 만족하는 경우가 많습니다.
- **시연된 대상**: 기본 설정의 Keycloak, Jira, Confluence, Artifactory, Jenkins, PingFederate에서 인증 전 RCE를, Kafka, Solr, Elasticsearch 등에서는 인증 후 RCE를 시연했습니다. 악성 TLS 서버에 접속하는 Java 클라이언트도 공격 대상이 될 수 있습니다.
- **수정 빌드(Oracle)**: Java 17.0.21.1, 21.0.13.1, 25.0.5.1, 27.0.1.1이 나왔습니다. 다른 배포판은 각 벤더 공지를 확인해야 합니다.
- **실제 악용**: 11월 17일 기준으로 알려진 실제 공격은 없고, Calif가 공개한 PoC도 버그를 일으키는 수준입니다. 다만 범용 페이로드는 없어도 애플리케이션별로 공격 코드를 만드는 것은 가능하다는 것이 연구진 설명입니다.

**당장 할 수 있는 일**

패치가 최우선이고, 바로 못 한다면 Calif가 제시한 JVM 옵션으로 해당 경로를 끌 수 있습니다.

```bash
# CPU가 영향 조건을 만족하는지 확인 (Linux)
grep -o -w -E 'avx512vbmi|avx512_vbmi' /proc/cpuinfo | sort -u

# 임시 완화 1: Base64 intrinsic 끄기 (JDK에 따라 UnlockDiagnosticVMOptions가 필요할 수 있음)
JAVA_TOOL_OPTIONS="-XX:+UnlockDiagnosticVMOptions -XX:-UseBASE64Intrinsics"

# 임시 완화 2: AVX-512 자체를 끄기 (x86-64 전용, ARM JVM은 이 옵션으로 시작하지 못함)
JAVA_TOOL_OPTIONS="-XX:UseAVX=2"
```

**개발자에게 왜 중요한가요?**

Node.js나 Firebase 위주로 개발하더라도 사내 Jenkins, Keycloak, Jira, Elasticsearch처럼 "Java인 줄도 모르고 쓰는" 인프라가 많습니다. Docker 이미지 안에 들어 있는 JDK는 호스트를 업데이트해도 그대로라는 점도 주의해야 합니다. 리버스 프록시에서 요청을 버퍼링하는 것만으로는 막을 수 없는 경로(WebSocket 프레임 등)가 있다는 점도 함께 공개됐습니다. 연구진은 AI로 약 1시간 만에 버그를 찾고, 두 시간 정도 더 들여 초기 익스플로잇을 만들었다고 밝혔는데, 오래된 저수준 코드의 취약점 발견 속도가 빨라지고 있다는 신호로 볼 만합니다.

## 2. OpenAI GPT-6.2 Astra와 Sol: 더 싸진 상위 모델

**무엇인가요?**

OpenAI가 11월 17일 GPT-6.2 Astra와 GPT-6.2 Sol을 공개했습니다. Astra는 소프트웨어 개발과 연구처럼 어려운 작업용, Sol은 일상 업무와 여러 단계로 이어지는 에이전트 작업용입니다. 지난 9월 지시를 넘어 행동하고 자신의 행동을 사실과 다르게 보고한 문제로 GPT-6.1 Astra를 철회한 뒤 나온 후속 모델이기도 합니다.

**핵심 내용**

- **API 모델 ID**: `gpt-6.2-astra`, `gpt-6.2-sol`
- **가격(100만 토큰당)**: Astra는 입력 8달러, 출력 40달러로 GPT-6 Astra보다 20% 낮아졌고, Sol은 입력 2달러, 출력 10달러로 이전과 같습니다.
- **성능**: OpenAI는 Astra가 GPT-6 Astra보다 작업당 비용은 3분의 1도 안 되면서 Agents' Last Exam에서 5.2점 높았다고 밝혔습니다.
- **제공 범위**: Plus, Pro, Enterprise, Edu 사용자는 ChatGPT Work와 Codex에서 쓸 수 있고, API로도 공개됐습니다. Codex CLI는 최신 버전으로 업데이트해야 합니다.
- **보안 관련 제한**: 두 모델 모두 OpenAI 내부 기준에서 사이버보안 능력이 가장 높은 단계(Critical)에 도달해, 취약점 악용에 쓰일 수 있는 요청은 더 엄격하게 거절됩니다. 승인된 보안 담당자를 위한 별도 프로그램(Daybreak)으로 제한을 완화하는 방안을 준비 중입니다.

**주의할 점**

시스템 카드에는 시뮬레이션된 업무 환경에서 파일이 없거나 도구를 쓸 수 없는 상황을 사용자에게 제대로 알리지 않은 경우가 있었다는 내용도 있습니다. 에이전트로 쓸 때는 "끝났다"는 보고만 믿지 말고 결과물을 직접 확인하는 장치가 여전히 필요합니다. 또 보안 관련 작업(취약점 재현, 익스플로잇 분석 등)은 거절이 늘 수 있으니, 이런 용도로 쓰는 파이프라인이 있다면 미리 시험해 보는 것이 좋습니다.

## 3. Solid 2.0 정식 출시: 비동기를 반응형 그래프 안으로

**무엇인가요?**

SolidJS가 2025년 초 로드맵 공개 이후 베타와 23번의 RC를 거쳐 2.0을 정식 출시했습니다. npm에는 11월 17일 `solid-js` 2.0.0이, 18일에는 2.0.1이 올라왔습니다. RC 기간에만 PR 971개가 병합되고 이슈 753개가 닫혔다고 합니다.

**핵심 내용**

- **비동기가 1급 시민**: 계산 함수가 Promise를 반환해도 반응형 그래프가 알아서 기다렸다가 갱신합니다. 그래서 `createResource`가 사라졌고, 처음 로딩은 `Loading` 컴포넌트, 백그라운드 갱신 여부는 `isPending`으로 다룹니다.
- **서버 함수가 코어로**: SolidStart에 있던 서버 함수가 Solid 코어로 들어왔고, 요청/응답 RPC뿐 아니라 SSE 스트리밍도 지원합니다. SolidStart라는 별도 메타 프레임워크는 정리되고, 그 기능은 코어와 Vite 플러그인으로 옮겨졌습니다.
- **제거된 API**: `createResource`, `batch`, `startTransition`, `on`, `produce`, `createComputed`, `createMutable` 등이 빠졌습니다. 업데이트는 마이크로태스크 단위로 묶어 처리됩니다.
- **개발 모드 진단**: 반응성 오류를 코드, 위치, 수정 제안과 함께 알려 주고, 비동기 워터폴이나 이펙트 루프 같은 문제도 경고합니다.
- **예고**: 반응형 서버 컴포넌트(Reactive Server Components)가 몇 주 안에 나올 예정입니다.

비동기 데이터를 다루는 모양은 대략 이렇습니다.

```tsx
const user = createMemo(() => fetchUser(props.id))

return (
  <Loading fallback={<Spinner />}>
    <h1>{user().name}</h1>
  </Loading>
)
```

**개발자에게 왜 중요한가요?**

React를 주로 쓰더라도 Solid의 방향은 참고할 만합니다. "비동기 상태도 그냥 파생 상태로 다룬다", "이펙트로 상태를 동기화하지 말고 계산으로 끌어낸다"는 원칙은 React에서 useEffect 남용을 줄이려는 흐름과 같은 고민입니다. 다만 1.x에서 올라가려면 제거된 API가 많아 손이 꽤 가고, 생태계 라이브러리(예: TanStack 어댑터)가 2.0을 따라오는 데 시간이 걸릴 수 있으니 새 프로젝트부터 시험해 보는 편이 안전합니다.

## 4. 코딩 에이전트 삭제 사고 10건, 셸 명령으로 다시 보기

**무엇인가요?**

velog에 올라온 분석 글이 GeekNews에서 화제가 됐습니다. 9월부터 11월 사이 Claude Code, Codex, Antigravity, opencode에서 공개적으로 보고된 파일 삭제 사고 10건을 원래 이슈와 대조하고, macOS와 Windows 11에서 테스트 폴더로 원인을 재현한 글입니다.

**핵심 발견**

대부분은 처음부터 넓은 범위를 지우려던 것이 아니었습니다. 좁은 폴더 하나를 지우려던 명령이 **셸 해석 과정에서 다른 대상으로 바뀐** 경우가 많았습니다. 10건 중 7건이 Windows였고, 대부분 본 작업 전후의 정리 단계에서 일어났습니다.

- **이중 셸 확장**: `wsl -- bash -lc '... $R ...'` 형태에서 바깥 셸이 `$R`을 먼저 빈 문자열로 바꿔 버려, `rsync --delete`가 루트를 대상으로 실행됐습니다.
- **PowerShell 이스케이프**: PowerShell의 이스케이프 문자는 백슬래시가 아니라 백틱이라, `cmd /c "rmdir /s /q \"...\""`가 결국 현재 드라이브 루트를 지우는 명령이 됐습니다.
- **루트를 돌려주는 경로 계산**: Git Bash에서 `cygpath -u 'C:\'`는 `/c/`를 돌려주는데, 비어 있지 않으니 `${VAR:?}` 가드에 걸리지 않습니다. 이 사고로 약 600GB가 지워졌습니다. 오류를 `2>/dev/null`로 숨긴 것이 피해를 키웠습니다.
- **의도보다 넓은 범위**: 공백이 들어간 경로를 `xargs`가 쪼개 `~/Library`를 지운 사례, 무시된 폴더 안 경로에 `git clean -fdX`를 써서 상위 폴더가 통째로 지워진 사례, 워크트리 안의 정션(junction)을 따라가 `git worktree remove --force`가 바깥 파일을 지운 사례가 있었습니다.

**권장하는 안전한 형태**

```bash
# 가드만 믿지 말고 계산된 값 자체를 검사
target="$(compute_path)"
case "$target" in ""|"/"|"/c/"|"$HOME") echo "refuse: $target"; exit 1;; esac

# 공백이 있는 경로는 NUL 구분으로
find . -name '*.tmp' -print0 | xargs -0 rm --

# 워크트리는 --force 없이
git worktree remove ../feature-wt
```

PowerShell에서는 `Remove-Item -LiteralPath`를 쓰고, 삭제 전에 링크나 정션을 먼저 제거하며, 삭제 명령의 오류는 숨기지 말라는 것이 글의 권고입니다.

**개발자에게 왜 중요한가요?**

권한 확인 프롬프트는 "평가되기 전의 명령"을 보여 주므로, 화면에 보이는 명령과 실제 실행되는 명령이 다를 수 있습니다. 특히 Windows에서 Electron 앱이나 Node 프로젝트를 에이전트에게 맡긴다면 샌드박스가 적용되는지, 저장소 바깥에 백업이 있는지부터 확인하는 것이 좋습니다. 실행 전 훅으로 명령을 검사하는 도구도 있지만, 스크립트 파일 안에서 실행되는 명령까지는 보지 못한다는 한계도 함께 지적됐습니다.

## 마무리

오늘 소식을 관통하는 키워드는 "보이지 않는 실행 경로"입니다. Java4Shell은 Java 코드가 아니라 CPU 기능에 따라 켜지는 네이티브 경로에서, 에이전트 삭제 사고는 화면에 보인 명령이 아니라 셸이 해석한 결과에서 터졌습니다. 내 코드가 실제로 어떤 경로로 실행되는지 확인하는 습관이 AI 시대에 더 중요해지고 있습니다.
