오늘은 보안 소식이 중심입니다. 다만 결이 조금씩 다릅니다. 첫 번째는 npm과 Electron 앱 배포 파이프라인 자체가 공격 경로가 된 사건이고, 나머지는 운영 중인 서비스의 설정을 다시 확인하게 만드는 변화입니다. 서비스에서 회원가입·비밀번호 재설정 메일을 직접 보내고 있다면 3번을 꼭 읽어 보세요.

## 1. bee-js 13.3.0과 Swarm Desktop 0.56.2: 공식 파이프라인이 악성 코드를 배포했습니다

**무슨 일이 있었나요?**

분산 스토리지 프로젝트 Swarm을 만드는 Ethersphere의 npm 패키지 `@ethersphere/bee-js` 13.3.0과 데스크톱 앱 Swarm Desktop 0.56.2에 악성 로더가 들어간 채 배포됐습니다. 11월 9일(UTC) 자정 직후 벌어진 일이며, Socket과 SafeDep이 분석을 공개했습니다. 패키지 자체의 사용자 수는 많지 않지만, 많은 팀이 믿고 있는 방어 장치들이 이번에는 전혀 도움이 되지 않았다는 점에서 모든 패키지 관리자와 Electron 앱 개발자가 참고할 만한 사례입니다.

**핵심 내용**

- **훔친 것은 npm 토큰이 아니라 GitHub 계정입니다**: 공격자는 메인테이너 계정과 릴리스 자동화용 봇 계정을 손에 넣은 뒤, GitHub 릴리스를 하나 만들었습니다. 그러자 프로젝트의 정식 publish 워크플로가 승인 절차 없이 그대로 npm에 배포했습니다.
- **npm provenance는 진짜였습니다**: 정상 워크플로에서 빌드됐기 때문에 13.3.0에는 위조되지 않은 provenance 증명이 붙어 있었습니다. Socket은 provenance가 어디서 빌드됐는지를 보여 줄 뿐, 소스가 검토됐다는 뜻은 아니라고 강조합니다.
- **설치 스크립트로 실행됩니다**: 악성 커밋은 기존 `prepare` 훅을 `postinstall`로 바꿔, 설치하는 순간 외부 서버에서 코드를 받아 실행합니다. 이 패키지 역사상 처음 생긴 설치 훅이었습니다.
- **Electron 앱은 서명·공증까지 받았습니다**: Swarm Desktop은 수동 실행 가능한 서명 워크플로가 임의 브랜치를 받아들이고 서명 인증서에 접근할 수 있었습니다. 그 결과 macOS 공증과 Windows 서명을 정상적으로 통과했고, 자동 업데이트를 통해 Windows x64와 Apple Silicon Mac 사용자에게 전달됐습니다. 로더는 메인 프로세스에 들어 있어 앱을 켤 때마다 실행됩니다.
- **노린 것**: 노드 지갑 키 파일과 평문 비밀번호가 담긴 설정 파일을 훔쳐 가고, Linux·macOS에는 원격 셸을, Windows에는 정상 서명된 원격 지원 도구를 서비스로 심었습니다. 원격 셸의 서버 주소는 이더리움 스마트 컨트랙트에서 읽어 옵니다.

**어떻게 확인하나요?**

```bash
# lockfile과 사내 레지스트리 캐시에서 문제 버전 찾기
grep -rn "bee-js" package-lock.json pnpm-lock.yaml yarn.lock 2>/dev/null | grep "13.3.0"

# 안전한 버전으로 고정
npm install @ethersphere/bee-js@13.2.0 --save-exact
```

- bee-js는 13.2.0으로 고정하고, 설치 스크립트가 켜진 상태에서 13.3.0을 설치한 PC나 CI 러너는 침해된 것으로 보고 접근 가능했던 자격 증명을 모두 교체하세요.
- Swarm Desktop은 0.56.2를 실행한 적이 있다면 깨끗한 0.56.3으로 바꾸고, 재설치만으로는 지워지지 않는 지속성 장치(`~/.solidity/` 폴더, LaunchAgent, systemd 유닛, 원격 지원 서비스)를 직접 제거해야 합니다.

**개발자에게 왜 중요한가요?**

이번 사건의 교훈은 사용자보다 배포하는 쪽에 있습니다. 제가 관리하는 저장소에도 그대로 적용해 볼 수 있습니다.

- publish 워크플로 안에서 릴리스 커밋이 보호된 브랜치에 있는지 확인하고, 배포 환경(environment)에 필수 리뷰어를 둡니다.
- 코드 서명 인증서는 `workflow_dispatch`로 아무 브랜치에서나 돌릴 수 있는 워크플로에 연결하지 않습니다. Electron 앱의 서명·공증 단계는 특히 main 브랜치와 승인으로 묶어 두는 것이 좋습니다.
- 사용하는 쪽에서는 설치 스크립트를 기본으로 막는 설정(pnpm의 허용 목록 방식 등)을 쓰면 이번 같은 `postinstall` 공격을 한 단계 줄일 수 있습니다. 다만 지난번 PolinRider 사례처럼 진입 파일에 코드를 숨기는 방식은 막지 못하니, 새 버전을 바로 받지 않는 지연 정책도 함께 고려하세요.

## 2. Microsoft 11월 Patch Tuesday: 1,000건 넘는 수정과 Outlook 제로데이

**무엇이 나왔나요?**

Microsoft가 11월 10일(미국 시간) 월간 보안 업데이트를 배포했습니다. 집계 기관마다 숫자가 달라서 Tenable은 1,093건, BleepingComputer는 다른 공급사 수정까지 포함해 1,235건으로 셉니다. 어느 쪽이든 지난달에 이어 1,000건을 넘는 큰 규모입니다.

**핵심 내용**

- **제로데이 1건**: Outlook의 스푸핑 취약점 CVE-2026-124194가 실제 공격에 쓰였습니다. 조작된 메시지 파일을 열면 Outlook이 경고 없이 공격자 서버에 접속하고, 이 과정에서 사용자의 NTLMv2 해시가 노출될 수 있습니다. 미리 보기 창으로는 발동하지 않으며, Windows 누적 업데이트가 아니라 Office 보안 업데이트로 고쳐집니다.
- **AI가 찾은 취약점**: 이 제로데이는 Claude를 사용한 연구자들이 발견한 것으로 크레딧에 올라 있습니다. 최근 몇 달 사이 AI 도구가 취약점 발견에 쓰였다는 소식이 이어지고 있습니다.
- **VS Code 취약점**: Tenable 정리에 따르면 Visual Studio Code에서 보안 기능 우회(CVE-2026-121663, CVSS 8.8)와 원격 코드 실행(CVE-2026-121662, CVSS 8.6) 두 건이 고쳐졌고, 둘 다 악용 가능성이 높은 것으로 분류됐습니다.
- **그 밖의 Critical**: Active Directory, Exchange Server, Schannel, Windows NAT의 원격 코드 실행 등이 포함됩니다.

**개발자에게 왜 중요한가요?**

VS Code는 자동 업데이트가 기본이라 대부분은 이미 적용돼 있겠지만, 회사 정책으로 업데이트를 묶어 둔 환경이나 Cursor처럼 VS Code 기반의 다른 에디터를 쓰는 경우에는 상위 수정이 언제 반영되는지 따로 확인해야 합니다. Windows 빌드 서버나 사내 Exchange를 운영하는 팀이라면 이번 달 패치 일정을 미루지 않는 편이 좋습니다.

**주의할 점**

- 공개된 정보는 대부분 요약 수준입니다. 각 CVE의 정확한 영향 버전은 Microsoft 보안 업데이트 가이드에서 직접 확인하세요.
- Outlook 제로데이는 Office 업데이트 채널을 따로 관리하는 조직이라면 Windows 업데이트만으로 끝났다고 착각하기 쉽습니다.

## 3. Outlook.com, DMARC 레코드가 없는 도메인의 메일을 거부하기 시작했습니다

**무슨 일이 있었나요?**

11월 5일 무렵부터 outlook.com, hotmail.com, live.com, msn.com 주소로 보낸 메일 중 일부가 DMARC 레코드가 없다는 이유로 반송되고 있습니다. 이메일 인증 업체 dmarcian과 MailRoute 등이 관련 사례를 정리했습니다.

**핵심 내용**

- **반송 메시지**: `550 5.7.1` 오류와 함께 SPF/DKIM/DMARC 인증 레코드가 없다는 문구가 오며, 끝에 `AS9031519` 코드가 붙기도 합니다. 예전 대량 발송자용 오류(`5.7.515`)와 달리 어떤 검사가 실패했는지는 알려 주지 않습니다.
- **소규모 발송자도 걸립니다**: Microsoft가 2025년에 발표한 규칙은 하루 5,000통 이상 보내는 발송자 대상이었는데, 이번에는 그보다 훨씬 적게 보내는 도메인도 반송을 겪고 있습니다. SPF와 DKIM이 정상인데도 DMARC가 없어서 거부된 사례도 있습니다.
- **일관되지 않습니다**: 같은 발송자의 메일 중 일부만 실패하고, 다시 보내면 통과하기도 합니다. Microsoft 365 업무용 주소는 같은 메일을 받아들였다고 합니다.
- **공식 발표는 없습니다**: 11월 9일 기준 Microsoft는 이 문제를 조사 중인 서비스 저하로만 인정했고, 정책 변경이라고 밝히지는 않았습니다. 의도된 변화인지 버그인지는 아직 확실하지 않습니다.

**개발자에게 왜 중요한가요?**

회원가입 인증, 비밀번호 재설정, 결제 영수증처럼 서비스가 자기 도메인으로 보내는 트랜잭션 메일이 Outlook 계열 사용자에게 조용히 사라질 수 있습니다. Firebase Authentication에서 커스텀 도메인으로 이메일 템플릿을 보내도록 설정했거나, SendGrid·SES 같은 서비스를 쓰는 경우 모두 해당될 수 있습니다. 원인이 버그로 밝혀지더라도 DMARC는 Gmail과 Yahoo도 이미 요구하고 있는 설정이라, 이번 기회에 추가해 두어 손해 볼 일은 없습니다.

```txt
; 처음에는 모니터링만 하는 p=none으로 시작
_dmarc.example.com.  TXT  "v=DMARC1; p=none; rua=mailto:dmarc-reports@example.com"
```

**주의할 점**

- DMARC는 SPF나 DKIM 중 하나가 통과하고, 그 도메인이 보낸 사람(From) 도메인과 일치해야 통과합니다. 레코드만 추가하고 정렬(alignment)을 확인하지 않으면 효과가 없습니다.
- `p=none`은 시작점일 뿐입니다. 보고서로 정상 발송 경로를 모두 확인한 뒤 `quarantine`, `reject`로 단계적으로 올리는 것이 권장됩니다.

## 4. GitHub: 1년간 활동 없는 저장소는 Dependabot 알림이 멈춥니다

**무엇이 바뀌나요?**

GitHub가 11월 10일 변경 로그에서 12월 8일부터 비활성 저장소의 Dependabot 알림을 일시 중지한다고 밝혔습니다.

**핵심 내용**

- **비활성의 기준**: 지난 1년 동안 어떤 브랜치나 태그에도 푸시가 없고, 저장소 생성이나 Dependabot 알림 활성화도 없었던 저장소입니다.
- **무엇이 일어나나요?**: 기존 알림은 지워지지 않고 보관(archive)됩니다. 새 알림도 더 이상 생기지 않습니다.
- **다시 켜는 방법**: 저장소에 아무 푸시나 하면 자동으로 다시 켜지고, 저장소 설정에서 직접 켤 수도 있습니다. 보관된 알림은 복원되고 1년 기준도 다시 시작됩니다.
- **적용 범위**: github.com의 모든 요금제와 데이터 레지던시를 쓰는 GitHub Enterprise Cloud에 적용되고, GitHub Enterprise Server에는 적용되지 않습니다. 조직의 보안 구성으로 Dependabot 알림을 강제하고 있다면 예외입니다.

**함께 나온 소식: Actions 워크플로 로그 비밀 값 스캔**

하루 전인 11월 9일에는 GitHub Actions 워크플로 로그에 찍힌 비밀 값을 secret scanning이 찾아 주는 기능이 퍼블릭 프리뷰로 나왔습니다. 다만 GitHub Secret Protection이나 Advanced Security를 쓰는 Enterprise Cloud 대상이고, 기본으로 꺼져 있으며, 활성화 이후 실행된 로그만 검사합니다. Actions가 이미 마스킹한 값이나 커스텀 패턴은 잡지 않습니다.

**개발자에게 왜 중요한가요?**

개인 계정에는 오래전에 만들어 두고 여전히 배포 중인 저장소가 꽤 있습니다. GitHub Pages로 띄워 둔 포트폴리오, 가끔 쓰는 CLI 도구, 회사 고객사에 납품하고 손대지 않는 프로젝트 같은 것들입니다. 코드는 그대로여도 의존성의 취약점은 계속 새로 발견되는데, 12월 8일 이후에는 그런 알림을 받지 못하게 됩니다. 여전히 운영 중인 저장소라면 설정에서 알림을 다시 켜 두거나, 조직 단위 보안 구성으로 강제해 두는 것이 안전합니다.

## 마무리

오늘 소식을 관통하는 말은 믿던 신호가 더 이상 충분하지 않다는 것입니다. 정상 워크플로가 만든 provenance도, 공식 서명도, 오랫동안 문제없던 메일 설정도, 조용한 알림함도 그 자체로 안전을 보장하지 않습니다. 신호가 무엇을 증명하고 무엇을 증명하지 않는지 한 번씩 짚어 보는 하루가 되면 좋겠습니다.
