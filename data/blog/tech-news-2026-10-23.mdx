오늘은 "HTTPS니까 안전하다"는 전제를 흔드는 인증기관 사고 하나와, 데이터 작업이나 AI API를 다루는 개발자에게 바로 쓸모가 있을 도구 소식 두 개를 골랐습니다. 첫 번째 소식은 브라우저보다 Node.js, Electron, Docker 이미지처럼 인증서 번들을 따로 들고 다니는 환경에서 더 중요합니다.

## 1. eMudhra 중간 CA 개인 키 유출: 브라우저 밖이 더 위험합니다

### 무엇인가

인도의 인증기관 eMudhra가 2025년 4월에 만든 중간 CA(intermediate CA) 인증서 8개의 개인 키가 사실상 공개된 것과 다름없는 상태였다는 사실이 10월 17일 한 보안 연구자에 의해 드러났습니다. 키 값 자체가 아주 작은 숫자여서, 공개된 인증서만 보고 최대 256번 정도만 시도하면 개인 키를 알아낼 수 있었습니다. 한 연구자는 실제로 키 하나를 계산해 GitHub에 올려 증명했고, 그 값은 4였습니다.

eMudhra는 키 생성 스크립트의 오류로 약한 키 묶음이 하나 더 만들어졌고, 이름이 비슷해서 그쪽이 서명에 쓰였다고 설명했습니다. 문제의 인증서 8개는 모두 폐기됐고, 이 건은 CVE-2026-111943 등으로 추적되고 있습니다.

### 핵심 내용

- **영향 범위**: 이 중간 CA들은 emSign ECC Root CA - G3 루트와 Sectigo(Comodo AAA Services) 루트 아래에 연결돼 있었습니다. 6개는 TLS 인증서, 2개는 코드 서명 인증서를 발급할 수 있는 CA입니다.
- **브라우저 대응**: Mozilla와 Chrome은 10월 17일 차단 목록으로 막았고, Apple은 10월 19일 보호 조치를 넣었습니다. Firefox는 차단 목록을 받지 못하는 환경을 위해 10월 20일 158.0.1을 냈습니다.
- **실제 악용 여부**: 10월 19일부터 google.com 같은 도메인의 위조 인증서가 Certificate Transparency 로그에 나타났지만, 10월 21일 기준으로 실제 사용자 공격이 확인된 사례는 없습니다. 다만 2025년 4월부터 누군가 키를 계산해 썼을 가능성은 이론적으로 열려 있습니다.
- **패치된 곳**: Go(1.27.3, 1.26.10), Python certifi(2026.10.19), pip, uv, Rust webpki-roots와 rustls-webpki, Composer ca-bundle, Homebrew, curl CA 번들, Ubuntu·Alpine·Arch·Gentoo의 ca-certificates, 그리고 Electron(44.9.1, 43.8.1, 42.11.16)이 업데이트를 냈습니다.
- **Node.js**: 내장 루트 인증서를 NSS 3.131.1로 올리고 emSign 루트 3개를 빼는 변경이 10월 20일 main 브랜치에 병합됐습니다. 이 변경이 들어간 릴리스가 나오면 올리고 프로세스를 재시작해야 합니다. Bun, Debian, FreeBSD는 기사 작성 시점에 아직 대기 중이었습니다.

### 개발자에게 왜 중요한가

브라우저는 벤더가 차단 목록을 밀어 넣어 주니 사용자가 할 일이 거의 없습니다. 문제는 인증서 번들 파일을 스스로 읽고 폐기 여부를 확인하지 않는 클라이언트입니다. Node.js 서버의 `fetch`와 `https`, Electron 앱, Go 바이너리, CI 러너, 오래된 베이스 이미지로 만든 컨테이너가 모두 여기에 해당합니다. 중간자 위치에 있는 공격자가 위조 인증서를 내밀면 이런 클라이언트는 정상 사이트로 믿고 토큰이나 API 키를 보내 버릴 수 있습니다.

Electron 앱을 배포하고 있다면 Electron 버전을 올린 새 빌드를 내야 사용자 쪽에 반영됩니다. Go처럼 빌드 시점의 인증서 처리가 바이너리에 박히는 언어는 다시 빌드해야 합니다.

### 주의할 점

- Docker 이미지는 `ca-certificates`를 갱신한 뒤 캐시 없이 다시 빌드해야 합니다. 이미지 태그만 그대로 두면 예전 번들이 남습니다.
- macOS에 기본으로 들어 있는 `/usr/bin/curl`은 폐기 정보를 확인하지 않아 계속 믿을 수 있다는 지적이 있습니다. 로컬 스크립트는 Homebrew curl을 쓰는 편이 안전합니다.
- Java는 OS 인증서 저장소를 갱신해도 JDK 자체의 `cacerts`는 바뀌지 않습니다.
- 내 서비스의 서버 인증서가 emSign ECC Root CA - G3에 연결돼 있다면 교체해야 합니다. Chrome은 10월 27일 이 루트를 제거할 예정이라는 안내가 나와 있습니다.

```bash
# RHEL/Fedora 계열
sudo dnf upgrade ca-certificates
# Debian/Ubuntu 계열
sudo apt-get update && sudo apt-get install --only-upgrade ca-certificates
# 이미지는 캐시 없이 다시 빌드
docker build --pull --no-cache -t my-app .
```

## 2. DuckDB 2.0 LTS: 서버 모드, 트리거, 그리고 에이전트 모드

### 무엇인가

임베디드 분석용 SQL 데이터베이스 DuckDB가 10월 21일 2.0.0 LTS(코드명 Cinnamon Teal)를 공개했습니다. 1.0이 안정성에 초점을 맞췄다면, 2.0은 1.5 이후 2만 개 가까운 커밋이 들어간 기능 중심 릴리스입니다. 최소 2027년 10월까지 지원되며, CLI와 Python 패키지는 바로 쓸 수 있고 나머지 클라이언트 라이브러리는 며칠 안에 따라온다고 합니다.

### 핵심 내용

- **서버 모드(Quack 프로토콜)**: CLI에 `-serve`와 `-connect` 인자가 생겼고, 새 `CONNECT` 문으로 원격 DuckDB는 물론 PostgreSQL과 MySQL에도 붙어 쿼리 일부를 원격 서버로 내려보낼 수 있습니다. "서버 없이 쓰는 DB"였던 DuckDB가 서버 역할도 하게 된 셈입니다.
- **비동기 I/O**: Parquet, CSV, 네이티브 파일을 읽을 때 여러 요청을 동시에 띄워 S3 같은 오브젝트 스토리지에서 특히 빨라졌습니다.
- **VARIANT 타입**: 반구조화 데이터를 저장할 때 공통 구조를 찾아 쪼개 저장해서 압축률과 속도를 높입니다. JSON 수정 함수(`json_set`, `json_insert`, `json_replace`, `json_remove`)도 추가됐습니다.
- **트리거**: `CREATE TRIGGER`로 BEFORE/AFTER, 행 단위/문장 단위 트리거를 만들 수 있습니다. 일부 조합은 아직 지원되지 않습니다.
- **에이전트 모드**: CLI가 코딩 에이전트에서 실행된 것을 감지하면 결과를 간결한 Markdown 표로 내고, 잘린 결과를 표시하고, 오류를 JSON으로 알려 줍니다. TPC-H 기준으로 모델이 읽어야 할 출력이 59% 줄었다고 합니다. `-agent`, `-no-agent`로 직접 켜고 끌 수 있습니다.
- **새 SQL 파서**: PostgreSQL에서 가져온 파서를 PEG 기반 자체 파서로 바꿨습니다. 오류 위치를 더 정확히 짚어 주고, 확장 기능이 SQL 문법을 추가할 수 있게 됐습니다.

### 개발자에게 왜 중요한가

로그 분석, 내부 대시보드, 데이터 정리 스크립트처럼 "Postgres를 띄우기는 과하고 스프레드시트로는 부족한" 작업에 DuckDB를 쓰는 사람이 많습니다. 이번에 서버 모드와 원격 DB 연결이 들어오면서 여러 프로세스가 같은 DuckDB를 공유하거나, 운영 PostgreSQL 데이터를 가져와 분석하는 흐름이 훨씬 단순해집니다. Claude Code 같은 코딩 에이전트에게 데이터 탐색을 맡기는 경우라면 에이전트 모드 덕분에 토큰 낭비도 줄어듭니다.

### 주의할 점

- **저장 형식**: 2.0으로 만든 DB 파일은 이전 버전에서 열 수 없습니다. 반대로 2.0은 기존 파일을 읽고 쓸 수 있고, 그 파일은 예전 버전에서도 계속 열립니다. 여러 버전이 같은 파일을 쓰는 환경이라면 새 파일을 만드는 쪽부터 조심해야 합니다.
- **람다 문법**: 화살표 한 개짜리 람다 문법이 기본으로 꺼졌습니다. 아래처럼 Python 스타일로 바꿔야 하며, 두 형식 모두 2.1에서 제거될 예정입니다.
- 운영 핵심 워크로드라면 11월에 예정된 첫 패치 릴리스를 기다리라는 것이 공식 권고입니다. 1.4는 11월 17일에 지원이 끝나고, 1.5는 2027년 3월까지 연장됐습니다.
- Intel Mac(osx_amd64)은 단계적으로 빠지고 있어 2.1부터 지원되지 않습니다.

```sql
-- 2.0 권장 람다 문법
SELECT list_transform([1, 2, 3], lambda x: x + 1);
```

## 3. OpenAI, Go로 만든 공식 CLI 공개

### 무엇인가

OpenAI가 REST API를 터미널에서 직접 호출할 수 있는 공식 CLI를 GitHub(openai/openai-cli)에 공개했고, 이번 주 Hacker News에서 주목을 받았습니다. Go로 작성됐고 Apache 2.0 라이선스입니다. 명령 구조는 `openai` 뒤에 리소스 이름과 동작을 붙이는 방식입니다.

### 핵심 내용

- **설치**: Homebrew(`brew install openai/tools/openai`) 또는 Go 1.25 이상에서 `go install`로 설치합니다.
- **인증**: 일반 API는 `OPENAI_API_KEY`, 사용량 조회 같은 관리용 API는 `OPENAI_ADMIN_KEY`를 씁니다. 조직·프로젝트 ID와 상호 TLS(베타)도 환경 변수나 플래그로 지정할 수 있습니다.
- **파일 입력**: 인자에 `@파일경로`를 쓰면 파일 내용을 그대로 넘깁니다. 텍스트나 base64로 강제하는 접두어도 있습니다.
- **출력 형식**: `--format`으로 json, jsonl, yaml, pretty 등을 고르고, `--transform`에 GJSON 문법을 써서 필요한 필드만 뽑을 수 있습니다.
- **기타**: `--base-url`로 호환 API 서버를 가리킬 수 있고, `--debug`는 HTTP 요청과 응답 본문을 그대로 찍습니다.

### 개발자에게 왜 중요한가

지금까지는 API를 빠르게 시험하려면 curl에 JSON을 손으로 짜 넣거나 짧은 Node.js 스크립트를 만들어야 했습니다. 공식 CLI가 생기면 쉘 스크립트와 CI에서 모델 호출, 파일 업로드, 사용량 집계를 한 줄로 처리할 수 있습니다. 결과를 jsonl로 받아 다른 도구로 넘기기도 쉽고, 코딩 에이전트에게 쥐여 주기에도 SDK 코드보다 단순합니다.

### 주의할 점

- `--debug`는 요청 본문까지 출력하므로 CI 로그에 프롬프트나 민감한 데이터가 남을 수 있습니다.
- 관리용 키(`OPENAI_ADMIN_KEY`)는 권한이 넓으니 일반 키와 분리해서 다루는 것이 좋습니다.
- 저장소에 아직 정식 릴리스 태그가 보이지 않아 명령 구조가 바뀔 수 있습니다. 스크립트에 박아 넣기 전에 버전을 고정해 두는 편이 안전합니다.

```bash
export OPENAI_API_KEY="sk-..."
openai responses create --input "Say this is a test" --model gpt-5.5
```

## 마무리

eMudhra 사고는 우리가 매일 쓰는 신뢰의 근거가 결국 어딘가의 스크립트 한 줄에 달려 있다는 걸 보여 줍니다. 브라우저는 알아서 막아 주지만 서버, CI, 데스크톱 앱 속 인증서 번들은 우리가 직접 챙겨야 합니다. 오늘 할 일 하나를 고르라면 배포 중인 이미지와 Electron 버전부터 확인해 보시길 권합니다.
