수요일 소식은 개발자가 매일 쓰면서도 거의 의심하지 않는 도구들에 관한 이야기입니다. 패키지를 받아 오는 저장소, 하루 종일 열어 두는 터미널, 웹 페이지를 띄우는 브라우저 엔진, 그리고 패치가 나오기 전 서버를 지키는 런타임까지 차례로 살펴봅니다.

## 1. Hex.pm, 13분간의 원격 코드 실행과 전체 자격 증명 교체

**무엇인가요?**

Elixir·Erlang·Gleam 생태계의 패키지 저장소 Hex.pm이 11월 23일(UTC) 보안 사고를 공개했습니다. 공격자는 약 13분 동안 69번의 공격 요청을 보내 웹 서버 6대에서 운영체제 명령을 실행했고, 운영팀은 방화벽 차단 후 20분 안에 수정 빌드를 배포했습니다.

**핵심 내용**

- **원인**: Hex 클라이언트가 쓰는 Erlang 바이너리 형식 요청 본문을 라우팅과 인증보다 먼저 디코딩하고 있었습니다. 안전 모드 디코더가 맵 내부를 검사하지 않아 가짜 Elixir 구조체가 통과했고, 로그 포매터가 이 값을 `inspect` 하는 과정에서 여러 라이브러리의 구현이 연쇄적으로 호출되며 명령 실행까지 이어졌습니다. 이 검사는 2016년에 빠졌다고 합니다.
- **CVE**: Hex.pm 취약점은 CVE-2026-129514입니다. 같은 유형의 문제가 Ash 프레임워크의 키셋 페이지네이션 커서에서도 발견돼 CVE-2026-124283으로 등록됐고, ash 3.38.0에서 고쳐졌습니다.
- **배제할 수 없는 것**: 데이터베이스 읽기는 로그가 남지 않아 이메일, 비밀번호 해시, API 키 해시, 2FA 시크릿, 세션, 비공개 패키지·문서가 읽혔을 가능성을 배제하지 못했습니다.
- **확인된 것**: 사고 중 게시된 릴리스 23개와 이후 기록된 패키지·레지스트리 파일이 모두 기록과 일치해 패키지 변조 흔적은 없었습니다. 서버가 읽을 수 있던 자격 증명은 레지스트리 서명 키 등 일부를 제외하고 모두 교체됐고, 이 과정에서 모든 사용자가 로그아웃됐습니다.
- **API 키는 교체 요청 대상이 아님**: 128비트 난수를 HMAC으로 저장하고 있어 해시만으로 역산하기 어렵다고 판단했습니다.

**지금 해야 할 일**

1. hex.pm에서 비밀번호를 변경합니다.
2. 대시보드의 보안 메뉴에서 인증 앱을 새로 등록해 2FA를 재설정하고, 새 복구 코드를 보관합니다.
3. 새 레지스트리 서명 체계를 담은 Hex 클라이언트가 며칠 안에 나오면 업데이트합니다. 그때까지는 서드파티 미러 대신 공식 저장소에서만 패키지를 받으라고 권고했습니다.

```bash
# 새 클라이언트가 나오면
mix local.hex --force
```

4. Hex를 사칭하는 피싱 메일을 조심합니다.

**개발자에게 왜 중요한가요?**

Elixir를 쓰지 않더라도 교훈은 그대로 적용됩니다. 인증 전에 요청 본문을 풍부한 타입으로 역직렬화하는 코드, 그리고 로그를 남기려고 값을 문자열로 바꾸는 평범한 코드가 연결되면 공격 경로가 됩니다. Node.js 서버에서도 인증 미들웨어 앞에 둔 바디 파서나 커스텀 디코더가 무엇을 받아들이는지 점검해 볼 만합니다. 분 단위 타임라인과 규제 기관 신고 시각까지 공개한 사고 보고서 자체도 좋은 참고 자료입니다.

## 2. 파일을 cat 하기만 해도 명령이 실행되는 iTerm2 취약점

**무엇인가요?**

보안 연구자가 macOS 터미널 iTerm2에서 Kitty 이미지 프로토콜의 응답을 악용해 임의 명령을 실행하는 방법을 공개했습니다. 피해자가 조작된 파일을 `cat`으로 출력하기만 하면 되고, 기본 설정에서 bash·zsh·fish 모두 동작한다고 합니다.

**핵심 내용**

- **영향 범위**: 공개된 표 기준으로 3.6.1부터 3.7.8까지 영향을 받고, 3.7.9에서 수정됐습니다. 개발자가 문제를 확인하고 두 개의 커밋으로 고쳤다고 합니다.
- **원리**: 세 가지가 맞물립니다. APC 이스케이프 시퀀스 처리에는 OSC와 달리 신뢰된 터미널인지 확인하는 단계가 없었고, 파일 전송 오류 메시지에 파일 경로의 줄바꿈이 그대로 들어갔으며, 그 오류 응답이 셸의 입력으로 되돌아갔습니다. 메모리 손상이 아닌 논리 버그입니다.
- **전달 경로**: README, 로그, 텍스트 파일 등 형식을 가리지 않습니다. 저장소, 공유 폴더, 압축 파일, 이메일 첨부로 들어올 수 있습니다.
- **설정으로는 막을 수 없음**: 잠재적으로 위험한 이스케이프 시퀀스를 끄는 옵션도 APC 시퀀스는 다루지 않아 이번 문제에는 효과가 없습니다. 기본값으로 꺼져 있기도 합니다.
- **주의**: 이 문제는 SSH 통합 기능에서 나왔던 iTerm2 취약점(CVE-2026-41253)과는 다른 경로입니다. 이번 건의 CVE 번호는 공개 글에 없습니다.

**개발자에게 왜 중요한가요?**

클론한 저장소의 README를 터미널에서 열어 보거나, 서버 로그를 `cat`·`tail` 하는 일은 하루에도 수십 번 합니다. 터미널 에뮬레이터는 출력된 바이트를 해석하는 프로그램이고, 그 해석기에 버그가 있으면 읽기만 해도 실행이 됩니다. iTerm2를 쓴다면 메뉴에서 업데이트를 확인해 3.7.9 이상인지 확인하고, 그 전까지는 출처가 불분명한 파일을 `less`처럼 제어 문자를 그대로 내보내지 않는 도구로 여는 습관이 안전합니다.

## 3. 자체 엔진 브라우저 Ladybird, 첫 알파 공개

**무엇인가요?**

Chromium·WebKit·Gecko 어느 것도 포크하지 않고 엔진을 처음부터 만든 브라우저 Ladybird가 11월 23일 첫 알파를 공개했습니다. 지금까지는 소스에서 직접 빌드해야 했지만, 이제 macOS와 Linux용 빌드를 내려받을 수 있습니다.

**핵심 내용**

- **엔진 구성**: HTML, CSS, DOM, 레이아웃, JavaScript(LibJS, 인터프리터와 JIT), WebAssembly를 직접 구현했습니다. 사이트마다 샌드박스된 렌더러 프로세스를 따로 두고, 이미지 디코딩과 네트워크도 별도 프로세스에서 처리합니다. 코드베이스는 점차 Rust를 도입하고 있습니다.
- **개발 도구 지원**: 자동화 테스트용 WebDriver와 Firefox DevTools 프로토콜을 지원합니다.
- **알파의 의미**: 일부 사이트는 동작하지 않고 가끔 충돌하며, 보안은 아직 보장하지 않는다고 명시했습니다. 롤링 채널로 자동 업데이트가 이어집니다.
- **피드백 경로**: 브라우저 안에서 깨진 사이트를 바로 신고할 수 있고, 충돌 보고서는 내용을 확인한 뒤 보낼지 선택할 수 있습니다.
- **운영 방식**: 비영리 단체가 후원과 기부로 개발하며, 허용적 라이선스로 GitHub에서 공개 개발합니다. 베타나 정식 출시 일정은 밝히지 않았습니다.

**개발자에게 왜 중요한가요?**

웹 엔진이 사실상 셋으로 수렴한 상황에서, 표준 문서만 보고 새로 만든 엔진은 내 코드가 특정 엔진의 관대한 동작에 기대고 있는지 드러내 줍니다. 프로젝트도 웹사이트를 만든다면 직접 띄워 보고 깨지는 부분을 알려 달라고 요청했습니다. WebDriver를 지원하니 Playwright·Selenium 계열 E2E 테스트에 실험적으로 붙여 보는 것도 가능하지만, 보안을 보장하지 않는 알파이므로 실제 계정에 로그인하는 용도로는 쓰지 않는 것이 좋습니다.

## 4. OpenAI와 Cisco의 Shirudo, 패치 전까지 eBPF로 공격을 막는 방패

**무엇인가요?**

OpenAI와 Cisco가 오픈소스 Linux 런타임 Shirudo를 공개했습니다. 이름은 일본어로 방패라는 뜻이며, AI 에이전트가 취약점에 맞춘 작은 방어 코드(shield)를 만들어 서비스를 멈추지 않고 적용하게 하는 것이 목표입니다.

**핵심 내용**

- **기반 기술**: Isovalent가 공개한 eBPF 기반 보안 도구 Tetragon 위에 만들어졌습니다. eBPF로 커널 수준에서 완화 코드를 주입합니다.
- **방패를 만드는 흐름**: 에이전트가 취약점을 찾거나 전달받으면, 운영자 쪽 Shirudo가 먼저 익스플로잇을 재현·검증한 뒤 eBPF 또는 애플리케이션 바이트코드로 된 방패를 만듭니다. 방패가 공격을 막는지, 서비스가 여전히 정상 동작하는지도 함께 확인합니다.
- **사람의 승인과 단계적 적용**: 운영자가 승인해야 배포됩니다. 적용 전에 애플리케이션에 어떤 영향을 주는지 관찰하는 단계를 거치고, 근거가 충분할 때 실제 차단으로 전환하며, 정식 패치가 적용되면 방패는 은퇴합니다.
- **배포와 신뢰**: 방패는 서명된 패키지로 OCI 호환 레지스트리를 통해 배포되고, 대상 시스템에서 TPM을 이용해 서명을 검증한 뒤 로드됩니다.
- **시연**: OpenAI는 Codex가 만든 방패로 실행 중인 Elasticsearch에 대한 Java4Shell 공격을 재시작 없이 막았다고 밝혔습니다.
- **확인하지 못한 부분**: 지원 커널 버전 같은 요구 사항은 이번에 확인한 자료에 나와 있지 않습니다. 도입 전에는 공식 문서를 직접 확인해야 합니다.

**개발자에게 왜 중요한가요?**

Hex.pm 사례처럼 공격이 시작된 뒤 대응까지 주어진 시간은 분 단위로 짧아지고 있습니다. 패치를 빌드하고 배포하는 데 걸리는 시간을 런타임 방어로 메우겠다는 접근은, 당장 재시작하기 어려운 레거시 서비스나 사내 서버를 운영하는 팀에게 현실적인 선택지가 될 수 있습니다. 다만 AI가 만든 커널 수준 코드를 운영 환경에 넣는 일이므로, 승인 단계를 누가 어떤 기준으로 맡을지가 도구 자체보다 더 중요합니다.

## 마무리

오늘 소식의 공통점은 읽기만 하는 동작도 안전하지 않다는 것입니다. 요청 본문을 디코딩하고, 로그를 문자열로 바꾸고, 파일을 화면에 출력하는 평범한 일이 실행으로 이어질 수 있으니, 입력을 해석하는 모든 지점을 신뢰 경계로 다시 바라볼 필요가 있습니다.
