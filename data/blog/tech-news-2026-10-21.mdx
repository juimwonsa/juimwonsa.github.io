오늘은 공급망 방어 도구 하나, 프레임워크와 브라우저 릴리스 둘, 그리고 AI 에이전트가 공격자 손에 들어갔을 때 어떤 일이 벌어지는지 보여 주는 보안 보고서 하나를 골랐습니다. 마침 최근 이 블로그에서 계속 다뤄 온 "악성 패키지"와 "에이전트 보안" 이야기가 오늘도 이어집니다.

## 1. GitHub, 패키지 방화벽 공개 프리뷰

### 무엇인가

GitHub가 10월 20일 **package firewall**을 공개 프리뷰로 내놓았습니다. 개발 환경과 원래 패키지 레지스트리 사이에 끼어서, 메타데이터 요청과 패키지 다운로드를 검사한 뒤 수상한 패키지를 막아 주는 프록시입니다.

노리는 대상은 분명합니다. 최근 몇 주 동안 이 블로그에서 다룬 악성 npm 패키지들처럼, **설치하는 순간 실행돼 CI 서버나 개발자 PC의 자격 증명을 훔치는 악성 코드**입니다.

### 핵심 내용

- **보호 대상**: GitHub Actions 러너, 코딩 에이전트, 그 밖의 CI/CD 호스트
- **지원 생태계**: 지금은 **npm만** 지원합니다.
- **정책으로 고를 수 있는 것**
  - 새로 올라온 버전을 바로 받지 않고 일정 기간 기다리게 하는 **쿨다운 기간**
  - GitHub Advisory Database의 악성 코드·취약점 경고와 대조
  - 증명(attestation) 수준이 이전 버전보다 낮아지는 것 같은 공급망 이상 징후 검사
- **동작 방식**: 엔터프라이즈 관리자가 정책을 정하고, 러너와 에이전트가 레지스트리에 직접 가지 않고 방화벽을 거치도록 설정합니다. 잘못 막힌 패키지는 예외 요청 흐름으로 풀 수 있습니다.
- **대상과 가격**: GitHub Enterprise Cloud(데이터 상주형 포함) 고객 대상이며, 프리뷰 기간에는 무료입니다. 정식 출시 후에는 Actions처럼 사용량 기반으로 과금할 예정인데 요금은 아직 공개되지 않았습니다.

### 개발자에게 왜 중요한가

그동안 악성 패키지 대응은 주로 "설치한 뒤에 알림을 받는" 방식이었습니다. 하지만 postinstall 스크립트로 토큰을 훔치는 공격은 알림이 오기 전에 이미 끝나 있습니다. 방화벽은 **설치 자체를 막는 앞단 방어선**이라는 점에서 성격이 다릅니다. 특히 쿨다운은 "올라온 지 몇 시간 된 버전"을 노리는 계정 탈취형 공격에 잘 맞는 대책입니다.

### 주의할 점

- 개인 계정이나 Team 플랜에서는 아직 쓸 수 없습니다. 이 경우에는 락파일 고정, `npm ci`, 설치 스크립트 비활성화 같은 기본 수칙이 여전히 1차 방어선입니다.
- 엔드포인트가 방화벽을 **거치도록 설정해야만** 효과가 있습니다. 설정이 빠진 러너나 로컬 에이전트는 그대로 레지스트리에 직접 접근합니다.

## 2. React Native 0.88: 웹과 같은 이벤트 모델, 깨지는 변경은 없음

### 무엇이 바뀌었나

10월 19일 React Native 0.88이 나왔습니다. React 19.3.0, Metro 0.87을 함께 올렸고, 0.83, 0.86에 이어 이번에도 **사용자 코드에 영향을 주는 깨지는 변경이 없다**고 밝혔습니다. 0.87을 쓰고 있다면 앱 코드를 고치지 않고 올릴 수 있다는 뜻입니다.

### 핵심 내용

- **웹 방식 이벤트 전파가 기본값**: 이벤트가 W3C `EventTarget` 방식으로 처리됩니다. 위에서 대상까지 내려가는 캡처 단계와 다시 올라오는 버블링 단계가 웹과 같아졌고, `stopPropagation()`, `preventDefault()`도 웹과 같은 규칙을 따릅니다. 이벤트 prop 이름이나 핸들러 순서는 그대로입니다. Canary 빌드에서는 네이티브 ref에 `addEventListener`를 붙이는 명령형 API도 써 볼 수 있습니다.
- **가변 폰트**: `Text`와 `TextInput`에서 `fontVariationSettings`를 Android, iOS 모두 지원합니다.
- **iOS SceneDelegate 지원**: Apple이 iOS 27 SDK부터 UIScene 생명주기를 요구하면서, Xcode 27로 빌드한 UIKit 앱은 이를 갖추지 않으면 실행되지 않습니다. 0.88은 `SceneDelegate`에서 React Native를 시작하는 진입점을 추가했고, 기존 `AppDelegate` 방식도 계속 동작합니다. 다만 현재는 단일 씬만 지원합니다.
- **기타**: Java TurboModule이 `ArrayBuffer`를 직접 주고받을 수 있게 됐고, Swift Package Manager 지원이 실험 단계에서 한층 다듬어졌습니다. 팀은 0.89에서 SwiftPM을 기본값으로 바꿀 계획입니다.

```tsx
// 가변 폰트: 객체 형태
<Text style={{ fontVariationSettings: { wght: 700, slnt: -10 } }}>굵고 기울어진 글자</Text>
```

### 개발자에게 왜 중요한가

웹 개발에 익숙한 React 개발자라면 이벤트 동작이 웹과 같아진 것이 가장 반갑습니다. 머릿속 모델을 하나로 통일할 수 있기 때문입니다. 그리고 iOS 쪽은 **선택이 아니라 일정이 정해진 숙제**입니다. Xcode 27로 넘어가기 전에 SceneDelegate 이전을 미리 해 두는 편이 안전합니다. 커뮤니티 템플릿의 `SceneDelegate.swift`와 `Info.plist`가 좋은 참고 예시입니다.

### 주의할 점

- React Native 내부 이벤트 구조에 직접 손을 댄 라이브러리나 코드는 꼭 테스트해야 합니다. 예전 경로는 내부 플래그 뒤에 남아 있지만 곧 제거될 예정입니다.
- `InitializeCore` 임포트는 `react-native/setup-env`로 바꾸라는 안내가 나왔고, iOS의 `InputAccessoryView`도 지원 중단 대상입니다.
- 0.85.x는 이제 지원이 끝났습니다. Expo 사용자는 Expo SDK 58에서 0.88을 만나게 됩니다.

## 3. Chrome 156 정식 출시: 실패한 import 재시도, CSS random()

### 무엇이 나왔나

Chrome이 2주 릴리스 주기로 바뀐 뒤, 10월 20일 **Chrome 156**이 Windows, Mac, Linux 안정 채널에 올라왔습니다. 프런트엔드 개발자가 체감할 만한 변경을 추리면 다음과 같습니다.

### 핵심 내용

- **실패한 모듈 로드를 캐시하지 않음**: 지금까지는 동적 `import()`가 네트워크 문제로 한 번 실패하면 그 실패가 그대로 기억돼, 같은 주소로 다시 불러도 계속 실패했습니다. 이제는 다시 호출하면 실제로 재시도합니다. 코드 분할을 많이 쓰는 SPA나 Electron 렌더러에서 "청크 로드 실패" 화면을 줄일 수 있습니다.
- **CSS `random()` 함수**: 지정한 범위 안에서 무작위 숫자 값을 만드는 함수가 들어왔습니다. 장식용 애니메이션 정도는 JavaScript 없이 처리할 수 있게 됩니다.
- **한 축만 스크롤하는 컨테이너**: `overflow: scroll clip`처럼 한쪽 축은 스크롤, 다른 쪽은 잘라내기로 지정할 수 있어서, `position: sticky`를 축별로 제어하기 쉬워졌습니다.
- **내비게이션을 시작한 요소를 고르는 의사 클래스**: 페이지 이동을 일으킨 링크나 버튼에 이동이 끝날 때까지 스타일을 줄 수 있습니다.
- **IndexedDB 저장소 교체**: 내부 구현이 LevelDB에서 SQLite로 바뀌기 시작했습니다. Web API는 그대로이고, 우선 새로 만드는 저장소부터 적용되며 기존 데이터는 이번 단계에서 건드리지 않습니다.
- **WebTransport 헤더**: 연결할 때 사용자 정의 HTTP 헤더를 보내고 서버 응답 헤더를 읽을 수 있습니다.

```js
// Chrome 156부터는 실패 후 다시 import()하면 실제로 재요청합니다
async function loadWithRetry(path, retries = 2) {
  try {
    return await import(path)
  } catch (err) {
    if (retries === 0) throw err
    await new Promise((r) => setTimeout(r, 1000))
    return loadWithRetry(path, retries - 1)
  }
}
```

### 주의할 점

- 재시도 동작은 Chrome 156 이후에만 기대할 수 있습니다. 다른 브라우저나 구버전에서는 여전히 실패가 캐시될 수 있으니, 그 경우에는 새로고침 같은 대체 경로를 남겨 두세요.
- Electron은 각 메이저 버전이 특정 Chromium 버전에 묶여 있으므로, 이 변경이 내 앱에 언제 들어오는지는 Electron 릴리스 노트에서 Chromium 버전을 확인해야 합니다.
- Fenced Frame 요소와 `window.fence` API는 156에서 아무 동작도 하지 않는 형태로 바뀌었고, 이후 버전에서 완전히 제거될 예정입니다.

## 4. Cairn: AI 에이전트 무리로 100곳 넘는 사이트를 뚫은 캠페인

### 무슨 일이 있었나

노르웨이 보안 업체 NorForge가 10월 19일 보고서를 내고, Reuters가 이를 단독 보도했습니다. 한 중국어권 공격자가 오픈소스 에이전트 협업 플랫폼 **Cairn**을 이용해, 사람 손을 거의 거치지 않고 **1,200곳이 넘는 웹사이트를 공격해 100곳 이상을 뚫었다**는 내용입니다. 피해 기업으로는 Deere, SharkNinja, Cummins가 거론됐고, 각 회사는 피해 범위가 제한적이라거나 조사 중이라고 밝혔습니다.

### 어떻게 동작했나

- Cairn은 원래 해킹 전용이 아니라 범용 문제 해결 도구입니다. 목표와 대상을 주면 여러 에이전트가 단계별로 약점을 찾고, 발견한 내용을 **공유 보드**에 올려 서로 이어 씁니다.
- 공격 파이프라인은 Playwright로 실제 주문이 되는 쇼핑몰인지 먼저 확인한 뒤 Cairn에 넘겼습니다.
- 에이전트에게 준 지시는 로그인 없이 코드를 실행하는 것, 곧 SQL 인젝션, 안전하지 않은 파일 업로드, 로그인 우회, 위험한 객체 역직렬화 같은 고전적인 취약점이었습니다. 성공하면 파일 업로드용 웹셸을 심어 발판을 만들었습니다.
- 한 사례에서는 본 서비스가 단단하자, 에이전트가 옆에 노출된 관리 패널을 찾아 몇 시간 동안 시도한 끝에 서버 명령 실행에 성공했다고 합니다.
- NorForge 추정으로는 성공률이 약 10%, 성공까지 평균 23시간 가까이 걸렸고, 토큰 비용은 전체 약 5,000달러, 성공 한 건당 약 50달러 수준이었습니다. 어디까지나 추정치입니다.

아이러니하게도 이 캠페인이 드러난 계기는 공격자들이 **Cairn 관리 패널을 인터넷에 그대로 열어 둔 것**이었습니다. 연구자는 스캐닝으로 이 패널들을 찾았고, 그 안에서 수백 개의 자격 증명과 API 키도 발견했습니다.

### 개발자에게 왜 중요한가

에이전트가 새로운 공격 기법을 만들어 낸 것은 아닙니다. 노린 것은 대부분 오래된 취약점입니다. 달라진 것은 **비용과 끈기**입니다. 사람이라면 포기했을 사이트에도 에이전트는 하루 가까이 매달리고, 그 비용이 몇십 달러에 불과합니다. "작은 사이트라 누가 노리겠어"라는 생각이 더는 통하지 않는다는 뜻입니다.

당장 점검해 볼 만한 것들입니다.

- 관리자 페이지, 스테이징 서버, 테스트용 대시보드가 인터넷에 열려 있지 않은지 확인합니다.
- 파일 업로드 경로에서 확장자와 실행 권한을 제한하고, 웹 루트에 예상하지 못한 파일이 생기는지 감시합니다.
- 내가 띄운 **에이전트 도구의 대시보드**도 똑같이 공격 표면입니다. 인증 없이 외부에 노출하지 마세요. 이번 공격자들이 바로 그 실수로 정체가 드러났습니다.

## 마무리

오늘 소식을 관통하는 한 줄은 "막는 쪽도, 뚫는 쪽도 자동화된다"입니다. GitHub는 설치 단계에서 패키지를 걸러 내는 문지기를 세웠고, 공격자는 에이전트 무리를 저렴하게 굴리기 시작했습니다. 한편 React Native와 Chrome은 웹 표준에 한 걸음 더 다가갔습니다. 참고로 지난주에 예고된 Node.js 보안 릴리스도 10월 21일 전후로 나올 예정이니, 서버 쪽 업데이트 일정도 함께 챙겨 두세요.
