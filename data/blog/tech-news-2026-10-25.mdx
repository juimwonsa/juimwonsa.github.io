이번 주는 Node.js 보안 릴리스 이야기가 계속 이어졌는데, 오늘은 그 여파가 데스크톱 앱 쪽에 어떻게 닿는지 살펴봅니다. Electron은 Node.js를 앱 안에 통째로 넣어 배포하기 때문에, Node.js가 고쳐졌다고 내 앱이 바로 안전해지지는 않습니다. 이어서 AI 에이전트 표준 두 개가 중립 재단으로 옮겨 간 소식, 에이전트에게 로그인을 맡기는 새 방식, 그리고 반대로 에이전트가 공격 도구로 쓰인 대형 사고를 골랐습니다.

## 1. Electron 정식 버전, 아직 Node.js 10월 보안 수정 전

### 무엇인가

Node.js는 10월 21일 22.23.4, 24.22.1, 26.12.1을 내고 높은 등급 4건을 포함한 취약점 10건을 고쳤습니다. 그런데 Electron 릴리스 페이지를 보면, 10월 20일에 나온 최신 정식 버전 45.0.0, 44.9.3, 43.8.3은 모두 Node.js 24.22.0을 담고 있습니다. 수정판 바로 이전 버전입니다.

Electron 쪽 작업은 진행 중입니다. Node.js를 24.22.1로 올리는 자동 PR이 10월 21일 43·44·45 브랜치에 각각 올라왔고, 10월 22일 모두 병합됐습니다. 하지만 이를 담은 정식 패치 버전은 아직 나오지 않았고, 현재 24.22.1이 들어간 것은 10월 23일 나온 46.0.0-alpha.1과 나이틀리뿐입니다. 병합된 PR에는 언제 배포되느냐는 질문이 달려 있습니다.

### 핵심 내용

- **Electron 앱과 관련 있는 수정**: 내장 Brotli 디코더의 메모리 범위 밖 쓰기(CVE-2026-111497)가 가장 큽니다. 메인 프로세스에서 `fetch()`로 외부 서버 응답을 받거나 `zlib`으로 외부 데이터를 푸는 코드가 노출 경로입니다. 숫자 모양 호스트에서 TLS 인증서 호스트명 검증이 틀어지는 문제(CVE-2026-105483, CVE-2026-106069), `dns.resolve` 계열이 NUL 문자에서 호스트명을 자르는 문제(CVE-2026-105482)도 사용자가 서버 주소를 직접 입력하는 앱이라면 따져 볼 만합니다.
- **Node.js만 따로 올릴 수 없음**: Electron 앱의 메인 프로세스와 유틸리티 프로세스는 Electron이 품은 Node.js로 돕니다. 개발 PC의 Node.js나 `.nvmrc`를 올려도 배포되는 앱에는 영향이 없습니다.
- **42.x는 기다려도 안 옴**: Electron 45 출시와 함께 42.x는 지원이 끝났고, 42.x 최신 버전은 Node.js 24.19.0에 머물러 있습니다. 42 이하를 쓰고 있다면 지금이 메이저 업그레이드 시점입니다.
- **Electron 45 자체의 변화**: Chromium 156, V8 15.6 기반입니다. 샌드박스 프리로드에서 `Buffer`, `setImmediate` 전역과 `events`, `timers`, `url` 심이 빠졌고, 화면 캡처 권한 요청이 `media`가 아니라 `display-capture`로 들어오는 등 깨지는 변경이 꽤 있습니다. `safeStorage`의 동기 메서드는 지원 중단(deprecated)되어 Electron 46에서 제거될 예정입니다.

### 개발자에게 왜 중요한가

웹 서버는 이미지를 다시 빌드하면 끝나지만, 데스크톱 앱은 Electron 패치가 나와야 빌드를 시작할 수 있고, 그 뒤에도 사용자 PC에 자동 업데이트가 퍼져야 끝납니다. 즉 실제 노출 기간이 서버보다 훨씬 깁니다. 지금 할 일은 패치 버전이 나오는 즉시 배포할 수 있게 준비해 두는 것, 그리고 그 사이 내 앱이 어떤 경로로 외부 데이터를 압축 해제하는지 점검하는 것입니다.

### 주의할 점

- 45로 올리는 김에 보안 패치까지 한 번에 받으려 한다면, 45.0.0에는 아직 수정이 없다는 점을 기억해야 합니다. 45.0.1 이후 버전을 기다리거나, 기존 라인의 다음 패치를 받으면 됩니다.
- 패치 전까지는 메인 프로세스가 사용자가 입력한 URL이나 신뢰할 수 없는 서버에 요청을 보내는 코드가 있는지 먼저 찾아 두는 것이 좋습니다. Node.js 쪽 공식 입장은 우회 설정 없이 업데이트하라는 것입니다.
- 패키징된 앱이 실제로 어떤 Node.js를 품고 있는지는 아래처럼 확인할 수 있습니다.

```bash
# 개발 의존성으로 설치된 Electron의 내장 Node.js 버전 확인
ELECTRON_RUN_AS_NODE=1 npx electron -p process.versions.node
# 24.22.1 이상이어야 10월 21일 수정이 반영된 것
```

## 2. Agent Skills와 Open Responses, Agentic AI Foundation으로 이관

### 무엇인가

Linux Foundation 산하 Agentic AI Foundation(AAIF)이 10월 22일 AGNTCon + MCPCon North America에서 새 프로젝트 4개를 받아들였다고 발표했습니다. Anthropic의 Agent Skills, OpenAI의 Open Responses, Hugging Face의 강화학습 환경 프레임워크 OpenEnv, Alibaba의 에이전트 샌드박스 OpenSandbox입니다. 이로써 MCP, AGENTS.md, A2A 등을 포함해 재단이 맡은 프로젝트는 10개가 됐습니다.

### 핵심 내용

- **Agent Skills**: SKILL.md 파일 하나와 필요한 스크립트, 참고 자료를 폴더로 묶어 에이전트가 필요할 때 불러 쓰게 하는 형식입니다. Anthropic은 명세뿐 아니라 이름과 로고, GitHub 조직, agentskills.io 도메인까지 넘겼습니다. Anthropic 발표에 따르면 70개가 넘는 에이전트 플랫폼이 이 형식을 지원하고, 공개된 스킬은 100만 개, 설치 수는 2억 8천만 회에 가깝습니다. 앞으로 버전 단위 릴리스, 정식 변경 제안 절차, 스킬 작성자와 설치자를 위한 보안 가이드를 만들 계획이라고 합니다.
- **Open Responses**: OpenAI Responses API를 바탕으로, 여러 모델 제공사에 같은 요청 형식과 스트리밍 이벤트를 쓰자는 명세입니다. 1월에 처음 공개됐고, 이번에 재단으로 옮겨 기술 운영위원회가 관리하게 됐습니다. The New Stack에 따르면 Vercel AI Gateway와 Databricks가 이미 구현했고, Ollama, LM Studio, vLLM, OpenRouter, AWS Bedrock 등이 지지 명단에 올랐습니다. 다만 Anthropic과 Google은 각자의 API를 유지하고 있어 지지 명단에 없습니다.

### 개발자에게 왜 중요한가

사내에서 쓰는 스킬 폴더나 SKILL.md는 이제 특정 회사 제품의 부가 기능이 아니라 중립 재단이 관리하는 표준 형식이 됐습니다. Claude Code용으로 만든 스킬을 다른 도구에서도 쓸 수 있을 가능성이 커졌다는 뜻입니다. Open Responses는 로컬 모델(Ollama, vLLM)과 게이트웨이를 오가며 개발하는 경우, 요청 코드를 한 형식으로 맞출 근거가 생겼다는 점에서 의미가 있습니다.

### 주의할 점

- 재단 이관은 관리 주체가 바뀐 것이지 명세 자체가 바뀐 것은 아닙니다. 당장 기존 스킬이나 코드를 고칠 필요는 없습니다.
- 스킬은 스크립트를 함께 실행할 수 있는 구조라, 남이 만든 스킬을 설치하는 일은 사실상 코드 실행을 허락하는 일입니다. 보안 가이드가 나오기 전까지는 출처를 직접 확인한 스킬만 쓰는 편이 안전합니다.
- Open Responses를 지원한다는 것과 모든 기능이 똑같이 동작한다는 것은 다릅니다. 제공사를 바꿀 때 도구 호출, 추론 옵션 같은 세부 동작은 따로 테스트해야 합니다.

## 3. 1Password for Agents: 에이전트는 비밀번호를 보지 않고 로그인

### 무엇인가

1Password가 10월 22일 개인용 AI 에이전트가 사용자를 대신해 웹사이트에 로그인할 수 있게 하는 1Password for Agents를 발표했습니다. 핵심은 에이전트가 비밀번호나 일회용 코드를 직접 받지 않는다는 점입니다.

### 핵심 내용

- **동작 방식**: 에이전트가 로그인 화면에 도달하면 1Password에 자격 증명을 요청합니다. 에이전트는 고유한 디지털 키로 자기 신원을 증명하고, 사용자는 자기 기기에서 어떤 계정이 왜 필요한지 보고 승인하거나 거절합니다. 승인하면 1Password가 로그인 양식에 직접 채워 넣고, 에이전트는 그 뒤 작업을 이어 갑니다.
- **파트너**: Meta의 Muse와 SpaceXSI의 Grok Bot은 며칠 안에 순차 적용되고, Anthropic의 Claude Duet, OpenAI의 ChatGPT Work와 dots 등은 곧 지원될 예정입니다. Browserbase, Browser Use, Perplexity, Ramp 등도 통합을 준비 중입니다.
- **가격과 지역**: 1Password Individual, Family 요금제에서 추가 비용 없이 쓸 수 있습니다. 다만 1Password.eu, 1Password.ca 계정은 아직 지원하지 않습니다.
- **제한**: 브라우저에 저장된 비밀번호나 메모에 적어 둔 비밀번호는 에이전트가 쓸 수 없고, 안전장치와 기능은 통합마다 다르다고 밝혔습니다.

### 개발자에게 왜 중요한가

브라우저 자동화 에이전트를 만들 때 가장 곤란한 부분이 로그인입니다. 비밀번호를 프롬프트나 환경 변수로 넘기면 모델 컨텍스트, 로그, 트레이스 어디에든 남을 수 있습니다. 비밀은 모델 밖에서 채우고 모델은 결과만 받는 구조가 사실상의 기본값이 되어 가고 있다는 신호로 볼 수 있습니다. 직접 만드는 에이전트에도 같은 원칙을 적용해 볼 만합니다.

### 주의할 점

- 지금은 정해진 파트너 에이전트만 쓸 수 있고, 공개 SDK나 API 세부 사항은 발표에 없습니다. 직접 만든 에이전트를 붙이려면 1Password 파트너십 팀에 문의해야 합니다.
- 비밀번호를 보지 않더라도, 로그인된 세션 안에서 에이전트가 하는 행동은 여전히 내 계정으로 이뤄집니다. 승인 단계를 습관적으로 누르지 않는 것이 중요합니다.

## 4. ConnectWise 공급망 공격: AI 에이전트로 2천여 조직을 노리다

### 무엇인가

Microsoft 보안 연구팀이 10월 21일, 중국 정부와 연계된 해킹 그룹이 IT 관리 업체 ConnectWise의 클라우드 백업 서비스를 뚫고 그 고객사 Microsoft 365 환경에 접근했다고 공개했습니다. TechCrunch 보도에 따르면 피해 대상은 약 2,250개 조직이고, 공격자는 분당 3,000건 가까운 로그인을 시도했습니다. Microsoft는 이 속도의 배경으로 ARTEX라는 오픈소스 AI 프레임워크를 지목했습니다.

### 핵심 내용

- **공격 경로**: 공격자는 ConnectWise Cloud Backup(옛 SkyKick)이 고객 테넌트와 연결할 때 쓰는 애플리케이션 자격 증명을 훔쳤습니다. 이 앱은 여러 테넌트에 설치되는 신뢰된 OAuth 앱이라, 고객이 이미 허락한 권한으로 메일과 파일에 정상 사용자처럼 접근할 수 있었습니다.
- **추가 행동**: Microsoft는 Microsoft Graph API를 이용한 정찰, 그리고 해당 서비스 주체에 자격 증명을 더 붙여 백도어를 만들려는 시도를 관찰했다고 합니다.
- **대응**: ConnectWise는 Cloud Backup과 이에 연결된 SaaS Security, Cloud Management 서비스를 멈추고 조사 중입니다. ConnectWise는 로그 보존, 앱 자격 증명과 페더레이션 신뢰 관계 점검, 메일 자동 전달과 받은편지함 규칙 확인을 권고했습니다.

### 개발자에게 왜 중요한가

이 사고는 사용자 비밀번호가 아니라 SaaS 연동 앱의 자격 증명 하나에서 시작됐습니다. Microsoft Graph나 Google Workspace에 붙는 멀티 테넌트 앱을 만들고 있다면, 내 서버에 있는 클라이언트 시크릿이 수천 개 고객 테넌트로 들어가는 열쇠가 될 수 있다는 뜻입니다. 여기에 공격을 자동화하는 에이전트가 더해지면, 사람이 알아채기 전에 대량 접근이 끝나 버립니다. Microsoft도 이 속도가 방어자에게 대응할 시간을 거의 주지 않는다고 지적했습니다.

### 주의할 점

- 연동 앱을 만드는 쪽이라면 오래 쓰는 클라이언트 시크릿보다 인증서나 워크로드 ID 연동처럼 유출에 강한 방식으로 옮기고, 요청 권한을 꼭 필요한 범위로 줄이는 것을 검토할 만합니다.
- 연동 앱을 쓰는 쪽이라면 테넌트에 동의해 둔 서드파티 앱 목록과 각 앱의 권한, 최근 서비스 주체 로그인 기록을 한 번 살펴보는 것이 좋습니다.
- 공격 초기 경위나 정확한 기간은 아직 공개된 정보가 엇갈립니다. 세부 사항은 Microsoft와 ConnectWise의 원문 공지를 기준으로 확인해야 합니다.

## 마무리

오늘 소식은 모두 신뢰를 누구에게 어디까지 맡기느냐의 문제로 묶입니다. Electron 앱은 런타임 보안을 Electron 릴리스 주기에 맡기고 있고, 에이전트에게 로그인을 맡길 때는 비밀을 모델 밖에 두는 구조가 표준이 되어 가며, 연동 앱 하나에 맡긴 권한은 공격자에게 그대로 넘어갈 수 있습니다. 내가 위임한 것들의 목록을 한 번 정리해 보기 좋은 주말입니다.
