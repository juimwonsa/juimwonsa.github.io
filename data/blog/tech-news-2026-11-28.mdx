토요일 소식은 프런트엔드 개발자에게 특히 가까운 이야기로 골랐습니다. 결제 페이지에 붙은 서드파티 태그가 어떻게 새로운 유출 경로가 되는지, 포매터 하나로 CI 시간을 얼마나 줄일 수 있는지, iPhone에서 내 웹앱이 돌아가는 엔진이 앞으로 바뀔 수 있을지, 그리고 같은 모델 이름이라도 실제 사용 토큰이 달라질 수 있다는 점을 차례로 봅니다.

> 오늘 글의 1·2·4번 소식은 1차 출처 페이지를 직접 열어 확인하지 못해, GeekNews에 정리된 요약을 기준으로 작성했습니다. 세부 수치는 원문 링크에서 한 번 더 확인하시길 권합니다.

## 1. WebRTC 데이터 채널을 쓴 블랙프라이데이 카드 스키머

**무엇인가요?**

보안 업체 InfoHawk가 블랙프라이데이 직전 Lascana, Samsonite, American Tourister, Revolve, FWRD의 온라인 스토어에서 카드 정보 탈취 스크립트를 발견했다고 밝혔습니다. 신고 후 11월 24~25일에 모두 제거됐습니다. 눈에 띄는 점은 페이로드를 받고 데이터를 내보내는 통로로 일반 HTTP 요청이 아니라 WebRTC 데이터 채널을 썼다는 것입니다.

**핵심 내용**

- **침투 경로가 전부 서드파티**: Samsonite·American Tourister는 쿠키 동의 배너(Seers) 설정, Lascana는 마케팅 픽셀(Quorum), Revolve·FWRD는 자사 CDN의 변조된 파일을 통해 로더가 들어왔습니다. 동의 배너 설정의 개인정보 처리방침 필드에 이미지 onerror 핸들러를 넣는 방식도 쓰였다고 합니다.
- **모바일 결제 화면만 노림**: 작은 화면이나 터치 기기에서만 동작했고, Samsonite 변종은 checkout 경로에서만 실행됐습니다. 데스크톱 점검이나 홈페이지 스캔으로는 놓치기 쉬운 구조입니다.
- **동작 순서**: S3 버킷에서 로더 스크립트를 받은 뒤, 브랜드처럼 보이는 도메인에 HTTP로 릴레이 정보를 요청하고 WebRTC 연결을 맺습니다. 이후 TURN 릴레이(확인된 교환에서는 모두 turn.cloudflare.com)를 거쳐 데이터 채널로 페이로드를 조각조각 받고, SHA-256으로 검증한 다음 eval로 실행합니다. 수집한 정보도 같은 채널로 내보냅니다.
- **확인 범위**: 실제 외부 전송이 관찰된 곳은 Lascana 한 곳이고, 실제 고객 피해 규모는 확인되지 않았습니다. 결제 검증 이전에 전송되므로 거절되거나 취소된 주문의 카드 정보도 빠져나갈 수 있습니다.

**개발자에게 왜 중요한가요?**

이번 사례는 CSP를 꼼꼼히 걸어도 빈틈이 있다는 점을 보여 줍니다. `connect-src` 허용 목록은 WebRTC 연결 전에 나가는 두 번의 HTTP 요청은 막을 수 있지만, 연결이 맺어진 뒤의 데이터 채널 트래픽까지 막아 주지는 못합니다. 지난 16일 Optimizely 사건과 마찬가지로, 내 코드 저장소에는 아무 변경이 없는데 사용자 화면에서 악성 코드가 도는 구조입니다.

점검할 만한 것들은 다음과 같습니다.

- 결제·로그인 페이지에서 서드파티 태그, 픽셀, 동의 배너를 최대한 걷어냅니다.
- 카드 입력은 PG사가 제공하는 격리된 결제 iframe 안에서만 받도록 합니다.
- 실제 휴대폰 크기의 터치 환경에서 결제 흐름을 직접 테스트합니다.
- Chrome에서는 DevTools 대신 `chrome://webrtc-internals`로 예상치 못한 WebRTC 연결이 있는지 볼 수 있습니다.
- 번들과 태그 설정에서 `KghRtc`, `rtc-signal-v1`, `quickfetch` 같은 문자열을 검색해 봅니다.

```js
// 결제 페이지에서 WebRTC를 쓸 일이 없다면, 서드파티보다 먼저 로드되는 스크립트에서 생성자를 막는 것도 방법입니다.
// 단, 공격 스크립트가 다른 iframe의 생성자를 가져오는 식으로 우회할 수 있어 완전한 방어는 아닙니다.
if (location.pathname.startsWith('/checkout')) {
  Object.defineProperty(window, 'RTCPeerConnection', { value: undefined, configurable: false })
}
```

**주의할 점**

위 코드는 보조 수단일 뿐입니다. 근본적인 해결은 민감한 페이지에서 서드파티 스크립트를 줄이고, 브라우저에서 실제로 무엇이 실행되는지 주기적으로 감시하는 것입니다.

## 2. tidy: Prettier 스타일을 따르는 Rust 단일 실행 파일 포매터

**무엇인가요?**

lukeed가 공개한 tidy는 Prettier와 같은 결과를 내는 것을 목표로 한 Rust 기반 포매터입니다. Node.js 없이 단일 실행 파일로 돌아가며 MIT 라이선스입니다. macOS, Linux, Windows용 실행 파일과 함께 Rust 라이브러리, `tidyrs`라는 Node.js 바인딩, 브라우저 플레이그라운드도 제공됩니다.

**핵심 내용**

- **지원 언어**: JavaScript, TypeScript, JSX, HTML, Vue, CSS, SCSS, Less, Markdown, JSON, YAML, GraphQL에 더해 플러그인 없이 TOML, XML, Dockerfile, INI도 다룹니다.
- **내장 언어 처리**: Vue·HTML의 style·script 블록, Markdown의 코드 블록과 front matter, JS 템플릿 문자열 안의 CSS·GraphQL·HTML·Markdown까지 정리합니다.
- **속도**: 자체 벤치마크(M1 Max)에서 파일 12,071개를 280ms에 처리해, 18.5초가 걸린 Prettier보다 약 66배 빨랐다고 합니다.
- **호환성**: Prettier 출력과 바이트 단위로 비교하고 있으며, 다른 부분은 저장소의 deviations 문서에 따로 정리돼 있습니다.
- **명령어**: 기본 흐름은 아래와 같습니다.

```bash
tidy init           # 기존 Prettier 또는 oxfmt 설정을 옮겨 옴 (.editorconfig 반영)
tidy check          # 포맷이 맞는지 검사 (CI용)
tidy up             # 실제로 파일을 정리
tidy check --changed  # 현재 브랜치에서 바뀐 파일만
```

**개발자에게 왜 중요한가요?**

React·Electron 모노레포에서 Prettier는 pre-commit 훅과 CI 양쪽에서 은근히 시간을 잡아먹습니다. Biome, oxfmt에 이어 tidy까지, "Prettier 결과는 유지하되 네이티브로 빠르게"라는 선택지가 늘고 있습니다. 특히 Vue·Markdown·템플릿 문자열 안의 내장 언어까지 한 번에 처리한다는 점이 다른 도구와의 차별점입니다.

**주의할 점**

바로 바꾸기보다는 한 브랜치에서 `tidy up`을 돌린 뒤 diff가 얼마나 생기는지부터 확인하는 것이 안전합니다. deviations 문서를 먼저 읽고, Prettier 플러그인(예: Tailwind 클래스 정렬)에 의존하고 있다면 그 기능이 대체되는지도 확인해야 합니다. 새 프로젝트인 만큼 버전 고정도 잊지 마세요.

## 3. EU 집행위원회, iOS 브라우저 경쟁을 DMA 우선순위로

**무엇인가요?**

Open Web Advocacy(OWA)를 비롯한 단체들이 보낸 공개 서한에 대해 EU 집행위원회가 브라우저 경쟁을 디지털시장법(DMA)의 우선순위 중 하나로 꼽았습니다. 집행위는 iPhone과 iPad에서 경쟁 브라우저가 Safari와 실질적으로 경쟁할 수 있도록 Apple과 논의 중이라고 밝혔습니다.

**핵심 내용**

- OWA는 Apple의 DMA 의무가 시작된 지 2년 반이 넘었지만, 아직 어떤 브라우저 회사도 기존 EU 사용자를 자체 엔진으로 옮기지 못했다고 지적합니다.
- OWA는 대화만이 아니라 공식 집행 절차를 시작해, 브라우저와 웹앱 경쟁을 막는 남은 장벽을 Apple이 없애도록 강제해야 한다고 요구합니다.
- 서한에는 Mozilla, Vivaldi, Brave, Tor Project 같은 브라우저 회사와 Ecosia, Kagi, Shopify, Vercel, Y Combinator 등 다양한 단체가 이름을 올렸습니다.

**개발자에게 왜 중요한가요?**

iOS에서는 지금도 사실상 모든 브라우저가 WebKit 위에서 돌아가므로, 웹앱 개발자는 iOS Safari의 버그와 늦은 기능 지원을 그대로 떠안고 있습니다. 웹 푸시, PWA 설치 경험, 최신 CSS·Web API 지원처럼 Electron 대신 웹앱으로 가려는 팀이 늘 걸리는 지점이 여기에 있습니다. 실제 집행이 시작되면 최소한 EU에서는 Blink나 Gecko 기반 브라우저가 iOS에 들어올 가능성이 커집니다.

**주의할 점**

아직은 집행위가 "논의 중"이라고 답한 단계이고, 공식 절차나 일정이 나온 것은 아닙니다. 당장 iOS 대응 전략을 바꿀 소식은 아니지만, 2027년 웹앱 로드맵을 짤 때 지켜볼 변수로는 충분합니다.

## 4. GPT-6.2 Astra·Sol, 추론 토큰이 눈에 띄게 줄었다는 측정

**무엇인가요?**

모델끼리 같은 과제를 맞대결시키는 OpenCode 기반 벤치마크 Agent Duel의 데이터를 분석한 글이 화제가 됐습니다. 글쓴이는 GPT-6.2 Astra와 Sol이 이전 버전보다 과제당 출력 토큰과 추론 토큰을 유의미하게 적게 쓴다며, OpenAI가 비용 절감 방향으로 모델을 조정한 것 같다고 추정했습니다.

**핵심 내용**

- 상대 모델 대비 지출 비율을 Elo 점수와 함께 비교했을 때, 이전 버전인 Astra 6와 Sol 6.1은 다른 모델들과 비슷한 수준이었지만 6.2 두 모델은 아래쪽으로 크게 벗어났습니다.
- 추론 토큰 감소의 p값은 Sol 0.00013, Astra 0.0064로 통계적으로 의미 있는 차이로 제시됐습니다.
- 글쓴이 스스로도 토큰 수와 API 지출만으로는 OpenAI의 실제 운영 비용이나 조정 이유를 알 수 없다고 밝혔습니다.
- 댓글에서는 같은 `high` 추론 설정이라도 버전마다 의미가 다를 수 있다는 지적, 일부 비용 차이가 과금 버그 때문이었다는 주장 등이 나왔지만 확인된 내용은 아닙니다.

**개발자에게 왜 중요한가요?**

에이전트나 Firebase Functions 뒤에서 LLM을 호출하는 서비스라면, 모델 버전만 올렸는데 비용·지연시간·품질이 함께 바뀌는 일이 생길 수 있습니다. 토큰이 줄면 비용은 반가운 일이지만, 어려운 과제에서 덜 생각하고 답하는 쪽으로 바뀌었을 가능성도 있습니다. 모델을 바꿀 때는 내 서비스의 대표 과제로 만든 평가 세트를 돌려 보고, 응답의 usage 필드에서 추론 토큰을 따로 기록해 두는 습관이 도움이 됩니다.

**주의할 점**

한 벤치마크 플랫폼의 데이터를 바탕으로 한 개인 분석이므로 "OpenAI가 품질을 낮췄다"는 결론으로 받아들이기는 이릅니다. 추론 강도 파라미터를 한 단계 올렸을 때의 비용과 품질을 직접 비교해 보는 것이 가장 정확합니다.
