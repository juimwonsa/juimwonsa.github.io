어제까지 보안 사고 소식이 이어졌다면, 오늘은 조금 숨을 돌리고 "에이전트와 함께 일하는 방식"에 관한 소식을 모았습니다. 에이전트가 쓴 코드를 어떻게 믿을지, 에이전트에게 어디까지 권한을 줄지, 그리고 코드를 빨리 만들어 내는 것과 소프트웨어를 오래 유지하는 것은 왜 다른 문제인지까지, 서로 이어지는 이야기입니다.

## 1. Claude Code 팀이 에이전트가 쓴 코드를 검증하는 방법

**무엇인가요?**

claude.dev 블로그에 11월 16일 Addy Osmani가 쓴 글이 올라왔습니다. Claude Code 팀은 코드의 약 90%를 Claude가 작성하고 리뷰하는데, 이 글은 그 상태에서 품질을 어떻게 지키는지를 꽤 구체적으로 설명합니다. 핵심 주장은 간단합니다. 검증 루프가 없으면 사람 한 명이 에이전트 한두 개만 지켜볼 수 있지만, 검증이 자동화돼 있으면 수십 개를 동시에 돌릴 수 있다는 것입니다.

**피해야 할 테스트**

- **불안정한(flaky) 테스트**는 에이전트에게 "코드를 고치지 말고 다시 돌려 보라"는 잘못된 습관을 가르칩니다.
- **느린 테스트**는 한 번에 돌릴 수 있는 양을 줄이고 실패 원인을 좁히기 어렵게 만듭니다.
- 팀 규칙상 Claude는 불안정한 테스트를 건너뛰거나, sleep을 넣거나, 통과할 때까지 재시도할 수 없습니다. 원인을 못 찾으면 테스트를 지우고 이유를 기록합니다.

**권장하는 세 가지 테스트**

- **E2E 테스트(최우선)**: 장바구니 담기부터 주문 확인까지 실제 사용자 흐름을 따라갑니다. 기능이 되거나 안 되거나 둘 중 하나라 속이기 어렵고, 실패하면 단계별 기록과 스크린샷까지 남겨 에이전트가 원인을 찾기 쉽습니다.
- **속성 기반 테스트**: "절대 깨지면 안 되는 성질"을 적어 두고 라이브러리가 수천 개의 입력으로 반례를 찾게 합니다. 인코딩 후 디코딩하면 원래 값이 나와야 한다(왕복), 잔액은 음수가 될 수 없다(불변식), 마이그레이션을 두 번 돌려도 결과가 같아야 한다(멱등성), 최적화한 코드는 느리지만 단순한 구현과 결과가 같아야 한다(동등성) 같은 것들입니다. JS/TS라면 fast-check를 추천합니다.
- **차등 테스트**: 대규모 마이그레이션에서 기존 시스템과 새 시스템에 같은 입력을 넣고 출력을 비교합니다. 공백 같은 의미 없는 차이는 정규화하고, 의도한 변경은 승인 목록으로 관리합니다.

TypeScript 프로젝트에서 왕복 성질을 확인하는 속성 기반 테스트는 대략 이런 모양입니다.

```ts
import fc from 'fast-check'

test('serialize/parse 왕복', () => {
  fc.assert(
    fc.property(fc.record({ id: fc.integer(), name: fc.string() }), (user) => {
      expect(parse(serialize(user))).toEqual(user)
    })
  )
})
```

**팀이 실제로 돌리는 장치들**

- **직접 실행해 보기**: 테스트보다 앱을 실제로 띄워 보는 것을 더 중요하게 봅니다. 웹은 Chrome 확장, 모바일은 시뮬레이터용 MCP, 데스크톱은 컴퓨터 사용 도구를 씁니다. 앱을 띄우는 절차는 `.claude/skills/` 아래 `verify` 스킬로 정리해 두고 커밋 전에 실행합니다.
- **세 번 실패하면 사람에게**: Claude가 실패를 고치려고 세 번 시도해도 안 되면 멈추고 사람에게 넘깁니다.
- **diff로 걸리는 신뢰성 체크리스트**: 과거 사고에서 나온 39개 항목이 있고, 각 항목에는 diff에서 알아볼 수 있는 조건이 붙어 있습니다. 변경마다 보통 3~10개만 해당돼 검사합니다.
- **변경이 자기 검사 규칙을 고칠 수 없게**: 리뷰 기준 파일(REVIEW.md)은 PR 브랜치가 아니라 기본 브랜치에서 읽습니다.
- **커밋 검증 도장**: 커밋마다 어떻게 검증했는지(검증 안 함 포함)를 기록하고, 검증 없이 커밋하면 막는 게이트를 둡니다. 처음에는 막지 않고 기록만 하는 관찰 모드로 오탐을 먼저 걸러 냅니다.

**개발자에게 왜 중요한가요?**

개인 프로젝트에서도 바로 가져올 만한 것이 많습니다. 특히 "에이전트가 테스트를 통과시켰다"는 말을 믿으려면 그 테스트가 불안정하지 않고, 에이전트가 손댈 수 없는 곳에 있어야 한다는 점이 가장 실용적입니다. React나 Electron 앱이라면 Playwright 같은 도구로 핵심 사용자 흐름 몇 개만 E2E로 묶어 두어도, 에이전트에게 맡길 수 있는 범위가 눈에 띄게 넓어집니다.

## 2. OpenCode Browse: 로그인된 내 브라우저를 에이전트에게 빌려주기

**무엇인가요?**

OpenCode를 만드는 Anomaly 팀이 Browse를 공개했습니다. MCP 서버와 Chromium 확장으로 이뤄져 있고, 코딩 에이전트가 새 헤드리스 브라우저가 아니라 **내가 평소 쓰는 브라우저**를 열린 탭, 저장된 로그인, 설치된 확장 그대로 조작하게 해 줍니다.

**핵심 기능**

- 에이전트는 페이지 읽기, 클릭, 입력, 스크린샷, 탭 녹화, 네트워크 트래픽 기록을 할 수 있습니다.
- 에이전트용 탭은 백그라운드에서 열리고 접힌 탭 그룹에 묶여 작업을 방해하지 않습니다.
- 로그인, 2단계 인증, 결제처럼 사람이 필요한 단계에서는 탭을 사용자에게 넘기고, 사용자가 처리한 뒤 Continue를 누르면 에이전트가 이어서 진행합니다.
- 툴바 버튼으로 이미 열어 둔 탭 하나만 에이전트에게 "빌려줄" 수 있고, 허용 사이트 목록으로 에이전트 탭이 갈 수 있는 곳을 제한할 수 있습니다.
- Chrome, Edge, Brave, Arc, Vivaldi, Opera 등 Chromium 계열을 지원하고, OpenCode뿐 아니라 Claude Code, Cursor, Codex, Zed 같은 MCP 클라이언트에서 쓸 수 있습니다.

설치는 Chrome 웹 스토어의 확장부터 시작하는 것이 권장 경로이고, CLI 설치는 보조 수단으로 안내됩니다.

```bash
npm install -g @opencode/browse && browse install
```

**개발자에게 왜 중요한가요?**

관리자 페이지 확인, 내부 대시보드 조회, 로그인이 필요한 화면의 버그 재현처럼 지금까지 에이전트에게 맡기기 어려웠던 일을 위임할 수 있게 됩니다. 위 1번 글이 말한 "에이전트에게 실행 중인 시스템을 볼 눈과 손을 주라"는 조언과도 맞닿아 있습니다.

**주의할 점**

에이전트가 **이미 인증된 세션** 안에서 움직인다는 것은 그만큼 위험도 크다는 뜻입니다. 공개 페이지에 숨겨진 지시문(프롬프트 인젝션)이 로그인된 메일이나 클라우드 콘솔로 이어질 수 있습니다. 허용 사이트를 좁게 잡고, 가능하면 업무용과 분리된 브라우저 프로필에서 쓰는 편이 안전합니다. 라이선스와 녹화된 네트워크 데이터의 보관 방식은 공식 페이지에 명시돼 있지 않으니 도입 전에 확인이 필요합니다.

## 3. Redict 지원 종료: Valkey로 옮기세요

**무엇인가요?**

Redis가 라이선스를 바꾼 뒤 등장했던 카피레프트 포크 Redict가 11월 17일 프로젝트 종료를 발표했습니다. 7.3.6이 마지막 릴리스입니다.

**왜 접나요?**

Redict는 향후 라이선스 변경을 막을 수 있는 카피레프트 포크로 Redis 커뮤니티를 모으려 했지만, 지속 가능한 커뮤니티를 만들지 못했다고 스스로 밝혔습니다. 그 사이 Valkey 포크가 자리를 잡았고, Redis도 다시 오픈소스 라이선스로 돌아왔기 때문입니다.

**어디로 가야 하나요?**

- 공식 권장은 **Valkey**입니다. 패키지 매니저로 설치했다면 Valkey를 설치하고 설정 파일 이름만 바꾸면 된다고 안내합니다.

```bash
mv /etc/redict.conf /etc/valkey.conf
```

- 컨테이너라면 Valkey 이미지를 받아 기존 설정 파일로 띄우면 됩니다. Lua 스크립트, 모듈, hiredict 클라이언트에 대한 마이그레이션 문서도 따로 마련돼 있습니다.
- 다시 Redis로 돌아가는 것은 권하지 않는다고 적었습니다. Redis가 기여자 라이선스 동의(CLA)를 요구하므로 언젠가 또 라이선스를 바꿀 여지가 있다는 이유입니다.

**개발자에게 왜 중요한가요?**

Node.js 백엔드에서 세션 저장소나 작업 큐, 캐시로 Redict를 쓰고 있었다면 이제 보안 수정이 계속 나온다고 기대하기 어렵습니다. 당장 깨지지는 않더라도 다음 인프라 점검 때 Valkey 전환을 일정에 넣어 두는 것이 좋습니다. Redict를 직접 고르지 않았더라도 배포판 패키지나 PaaS의 기본값으로 들어와 있을 수 있으니 한 번 확인해 보세요.

## 4. AI가 3주 만에 Rust로 옮긴 curl, 그리고 Daniel Stenberg의 답

**무엇인가요?**

curl의 Rust 재작성 프로젝트 두 개가 등장했습니다. 하나는 curl과 libcurl을 메모리 안전하게 처음부터 다시 구현했다는 urlx이고, 다른 하나는 이름까지 curl을 그대로 쓰는 Rust 재작성본으로 비용이 8,600달러 들었다고 밝혔습니다. curl 창시자 Daniel Stenberg가 11월 17일 블로그에서 이에 대한 생각을 남겼습니다.

**숫자로 본 이야기**

- Stenberg가 직접 세어 보니 약 185,000줄의 C 코드가 약 340,000줄의 Rust 코드가 됐습니다.
- 변환에 걸린 약 3주 동안 원본 curl에는 300개 넘는 커밋이 들어갔고 200개 남짓의 버그가 고쳐졌습니다. 그 사이 취약점도 몇 건 수정됐습니다.
- 올해 curl에서 확인된 취약점 81건 중 메모리 안전 언어였다면 막았을 법한 것은 14건(17.3%)이라고 합니다. 나머지 67건은 Rust 버전에도 그대로 있었을 것이라는 계산입니다.

**그의 주장**

- 코드를 한 번 쓰는 것은 어려운 부분이 아닙니다. 이번 재작성이 가능했던 것도 문서화가 잘된 curl 코드와 방대한 테스트, 사용자 덕분이라고 봅니다.
- curl의 가치는 수십 년간 쌓인 피드백, 커뮤니티, 그리고 ABI·API 안정성에서 나오며, 새로 쓴 코드가 이것을 단번에 따라잡을 수는 없다고 말합니다.
- 그는 언어와 관계없이 재작성보다 꾸준한 리팩터링을 선호하며, 재작성 측과 연락한 적은 없고 그들의 계획도 모른다고 덧붙였습니다.

**개발자에게 왜 중요한가요?**

에이전트 덕분에 "통째로 다시 쓰기"의 비용이 크게 내려간 것은 사실입니다. 하지만 이 글은 비용이 내려간 것이 작성 단계뿐이라는 점을 짚습니다. 사내 레거시를 AI로 다른 언어나 프레임워크로 옮기자는 이야기가 나온다면, 옮기는 동안 원본에 쌓이는 변경을 어떻게 따라갈지, 그리고 옮긴 뒤 누가 유지할지를 먼저 따져 봐야 합니다. 1번 글에서 소개한 차등 테스트가 바로 이런 상황을 위한 도구이기도 합니다.

## 마무리

에이전트는 코드를 쓰는 속도와 범위를 빠르게 넓히고 있지만, 오늘 소식은 모두 그 바깥에 있는 것들, 즉 검증, 권한, 그리고 유지보수가 결국 결과를 결정한다고 말합니다. 만드는 일이 싸질수록 믿을 수 있게 만드는 일에 더 투자해야 합니다.
