이번 주는 "격리"와 "신뢰"를 다시 생각하게 하는 소식으로 시작합니다. 가상 머신 사이의 벽에 구멍이 났고, AI 코딩 도구를 미끼로 한 공급망 공격은 에이전트의 대화 내용까지 노렸습니다. 한편 AI가 오래된 암호학 미스터리를 풀었다는 연구와, AI를 가장 많이 쓰는 회사의 인력 구성이 어떻게 변했는지 보여 주는 보고서도 함께 살펴보겠습니다.

## 1. PwnEscape: 게스트 VM에서 호스트로 빠져나가는 Linux 커널 취약점

### 무엇이 발견됐나

Pwn.ai의 보안 연구자 Paulos Yibelo가 Vercel의 Sandbox 보안 챌린지에 참가하던 중 Linux 커널 네트워크 스택에서 **게스트에서 호스트로 탈출할 수 있는 취약점**을 찾았습니다. 이름은 **PwnEscape**, 번호는 **CVE-2026-99999**입니다.

문제는 하이퍼바이저가 아니라 **호스트 커널의 IPv4 처리 경로**에 있습니다.

- VM 안에서 보낸 패킷에 붙은 체크섬 오프로드 메타데이터를 커널이 충분히 검증하지 않습니다.
- 그 결과 이미 검증을 마친 IPv4 헤더에 나중에 값이 덮어써집니다. 연구자의 시연에서는 헤더 길이가 20바이트에서 60바이트로 바뀌면서, 옆에 있던 호스트 메모리 32바이트가 밖으로 나가는 패킷에 섞여 나왔습니다.
- 연구자는 여기서 더 나아가 호스트 커널 메모리 일부를 원하는 대로 쓰고, 호스트 root 권한으로 명령을 실행하는 데까지 성공했다고 밝혔습니다. 다만 이는 통제된 실험 환경에서의 결과입니다.

AlmaLinux 공지에 따르면 문제가 된 코드는 2008년(Linux 2.6.27)과 2010년에 들어간 것이라, 사실상 오래전부터 거의 모든 배포판 커널에 들어 있었습니다. Red Hat도 RHEL 8, 9, 10을 영향 대상으로 올렸습니다.

### 패치 현황

- 9월 4일 커널 보안 담당자에게 비공개로 보고됐고, 수정 커밋 `6785011f8b16`이 **10월 14일 메인라인에 병합**됐습니다.
- NVD 설명 기준으로 5.10, 5.15, 6.1, 6.6, 6.12, 6.18, 7.2 안정 브랜치에도 수정이 들어갔습니다.
- AlmaLinux는 10월 16일 8, 9, 10용 패치 커널을 testing 저장소에 먼저 올렸습니다.
- 연구자, 커널 개발자, Red Hat 누구도 **우회책은 제시하지 않았습니다.** 패치된 커널로 바꾸는 것이 유일한 해결책입니다.

업계 반응도 빨랐습니다. 일본의 Sakura Internet은 10월 16일부터 모든 리전에서 VPS 신규 신청과 사양 변경 등을 멈췄고, AWS는 EC2, Lambda, Fargate가 영향을 받지 않는다고 밝혔습니다. Vercel은 Sandbox에서 고객 데이터가 접근된 정황은 없다고 설명했습니다.

### 개발자에게 왜 중요한가

이 취약점은 **호스트**의 문제이기 때문에, VM 안의 게스트 커널을 업데이트해도 소용이 없습니다. 내가 할 수 있는 일은 상황에 따라 다릅니다.

- **VPS나 클라우드를 빌려 쓰는 경우**: 사용하는 업체의 공지를 확인하세요. 호스트 패치와 재부팅 일정이 잡혀 있을 수 있습니다.
- **직접 KVM 호스트를 운영하는 경우**: 배포판의 패치 커널로 업데이트하고 재부팅해야 합니다. 재부팅 전에는 게스트를 옮기거나 내려 두세요.
- **AI 에이전트가 만든 코드를 microVM 샌드박스에서 돌리는 경우**: Firecracker 같은 샌드박스도 결국 호스트 커널을 공유합니다. 샌드박스는 방어선 중 하나일 뿐, 비밀 값과 네트워크 권한을 최소로 주는 원칙은 그대로 지켜야 합니다.

연구자는 약한 설정을 노리는 익스플로잇이 몇 주 안에 나올 수 있다고 예상했습니다. 미룰 이유가 없는 패치입니다.

```bash
# 호스트에서 현재 커널 버전 확인
uname -r
```

## 2. 가짜 Web3 액셀러레이터: npm 패키지로 코딩 에이전트의 요청을 가로채다

### 무슨 일이 있었나

Elastic Security Labs가 **REF8801**이라는 이름으로 추적하는 캠페인을 공개했고, The Hacker News가 10월 19일 이를 보도했습니다. 공격자는 **Apex Accelerator**라는 가짜 Web3 투자 프로그램을 내세워, 암호화폐 스타트업 창업자들에게 Claude와 Gemini 무료 크레딧, 코딩 도구, 보안 감사를 제공한다며 접근했습니다. 싱가포르의 업계 행사에 모습을 드러내는 등 신뢰를 쌓는 데도 공을 들였습니다.

미끼가 된 npm 패키지는 두 개입니다. 지금은 모두 내려갔습니다.

- **`@apexacc/cli`**: 창업자용 AI 어드바이저라고 소개된 코딩 에이전트
- **`@apexacc/audit`**: 토큰, 지갑, 스마트 컨트랙트를 검사하는 도구 18개를 제공한다는 MCP 서버

### 어떻게 동작하나

흥미로운 점은 `postinstall` 스크립트를 쓰지 않았다는 것입니다. 패키지의 `bin` 항목이 가리키는 런처가 **명령을 실행하거나 `npx`로 부를 때** 동작합니다. 런처는 GitHub 릴리스에서 플랫폼별 Bun 실행 파일을 내려받아 홈 디렉터리에 저장한 뒤 실행합니다. 그 뒤 Windows에서는 여러 단계를 거쳐 브라우저 정보, 지갑, 메신저 데이터 등을 훔치는 스틸러가, macOS에서는 가짜 인증 창으로 로그인 비밀번호를 받아 내는 CloudSyncD 백도어가 설치됩니다.

개발자 입장에서 더 눈여겨볼 부분은 **AI 에이전트를 노린 기능**입니다.

- `@apexacc/cli`는 오픈소스 코딩 에이전트 Oh My Pi를 거의 그대로 다시 포장한 것이었습니다. Elastic에 따르면 1,363개 파일 중 1,351개가 원본과 같았고, 추가된 부트스트랩 코드가 핵심이었습니다.
- 이 코드는 실행 중인 프로세스의 `OPENROUTER_BASE_URL`과 `OPENROUTER_API_KEY`를 공격자 서버와 토큰으로 바꿔 놓습니다. 화면에는 여전히 OpenRouter라고 표시되지만, **프롬프트, 대화 기록, 에이전트가 읽은 로컬 파일 내용 같은 도구 출력**이 공격자 서버로 전송됐습니다.
- 에이전트 설정 파일 `~/.apex/agent/mcp.json`에는 공격자가 운영하는 MCP 서버가 등록됐습니다. MCP 서버는 도구 이름과 설명을 정할 수 있기 때문에, 모델이 어떤 도구를 어떻게 부를지에 영향을 줄 수 있습니다.
- 캡처된 소스에서는 도구 실행 승인이 기본적으로 모두 자동 허용으로 설정돼 있었습니다.
- `@apexacc/audit`는 Claude Desktop, Cursor, Windsurf 설정에도 자신을 등록하려 했지만, 버그 때문에 이 동작은 제대로 끝나지 않았다고 합니다. 18개 감사 도구의 결과는 모두 꾸며 낸 값이었습니다.

### 개발자에게 왜 중요한가

지난주까지 다룬 공급망 공격이 주로 토큰과 키를 노렸다면, 이번 사례는 **LLM으로 오가는 대화 자체**와 **에이전트의 도구 구성**을 노렸다는 점이 다릅니다. 에이전트에게 코드베이스를 읽게 했다면 그 내용이 통째로 새어 나갈 수 있다는 뜻입니다.

- 모르는 출처의 AI CLI나 MCP 서버를 `npx`로 바로 실행하지 마세요. `--ignore-scripts`로는 이런 `bin` 기반 실행을 막을 수 없습니다.
- 사용하는 에이전트와 에디터의 MCP 설정 파일을 가끔 열어 보고, 직접 추가하지 않은 서버가 있는지 확인하세요.
- LLM 제공사의 base URL을 환경 변수로 바꿀 수 있는 도구라면, 실제 요청이 어디로 가는지 한 번쯤 확인해 볼 만합니다.
- 무료 크레딧이나 무료 감사를 내세운 낯선 제안은 의심부터 하는 것이 안전합니다.

## 3. Claude, 25년 넘은 NIST 타원곡선 시드의 출처를 재현하다

### 무엇이 밝혀졌나

Anthropic의 Frontier Red Team이 10월 16일, 내부 연구용 Claude 모델이 **NIST 타원곡선의 시드 값이 어떻게 만들어졌는지** 재현해 냈다고 발표했습니다.

P-256처럼 ECDSA와 TLS에서 널리 쓰이는 NIST 곡선은 정해진 시드를 해시해서 곡선 파라미터를 만듭니다. 그런데 그 시드 자체가 어디서 왔는지는 설명된 적이 없었습니다. 그래서 오랫동안 혹시 의도적으로 고른 값, 즉 백도어가 아니냐는 의심이 따라다녔고, 시드를 찾는 사람에게 주는 현상금까지 걸려 있었습니다.

Anthropic의 설명은 이렇습니다.

- 시드는 해시 결과가 아니라 C 표준 라이브러리의 오래된 난수 함수 **`lrand48`** 의 출력이었고, 이 함수는 **Unix 타임스탬프**로 초기화돼 있었습니다.
- 소수 곡선 P-192, P-224, P-256, P-384, P-521과 이진 곡선 B-233, B-283, B-409, B-571의 시드를 재현했습니다. B-163의 시드는 아직 설명되지 않았습니다.
- 소수 곡선의 타임스탬프는 1997년 5월부터 1998년 4월 사이에 분포합니다.
- Claude는 일부 시드의 상위 비트가 모두 0이라는 점에서 `lrand48`의 흔적을 알아챘고, 격자 축소 기법으로 생성기의 내부 상태를 복원한 뒤 거꾸로 돌려 초기화 시점을 찾았습니다. 걸린 시간은 30분이 채 안 됐다고 합니다.
- 재현용 Python 코드는 CC0로 공개됐고, 현상금은 Let's Encrypt를 운영하는 ISRG에 기부됩니다.

### 개발자에게 왜 중요한가

이번 결과는 **암호 공격이 아닙니다.** ECDSA나 P-256이 약해졌다는 뜻이 아니고, 오히려 누구나 평범한 난수 생성기와 시계만으로 시드를 다시 만들 수 있게 됐으니 백도어 가능성은 더 낮아졌다는 것이 Anthropic의 설명입니다. 지금 쓰는 TLS 설정이나 JWT의 ES256 서명을 바꿀 필요는 없습니다.

그래도 두 가지는 생각해 볼 만합니다. 하나는 표준이나 라이브러리의 "설명 없는 상수"가 신뢰를 갉아먹는다는 점입니다. 다른 하나는 AI가 이런 패턴 찾기와 역추적에 매우 빨라졌다는 점입니다. 앞으로는 내 코드 속 예측 가능한 난수나 시간 기반 시드도 같은 방식으로 더 쉽게 드러날 수 있습니다. 보안 용도에는 `Math.random()` 대신 Node.js의 `crypto` 모듈이나 Web Crypto API를 쓰는 습관을 다시 확인해 두세요.

```ts
// 보안 토큰에는 암호학적으로 안전한 난수를 사용
import { randomBytes, randomUUID } from 'node:crypto'

const token = randomBytes(32).toString('hex')
const id = randomUUID()
```

## 4. Anthropic 내부 인력 보고서: 주니어 비중 감소, 회의 시간 증가

### 무엇이 발표됐나

Anthropic이 10월 16일, AI 에이전트를 많이 쓰는 자사 직원들의 일하는 방식과 인력 구성이 어떻게 바뀌었는지 분석한 보고서를 공개했습니다. 주말 동안 Hacker News 등에서 크게 화제가 됐습니다.

눈에 띄는 수치는 이렇습니다.

- 기술 부서에서 **주니어가 차지하는 비중**이 2025년 초 이후 21%에서 14%로 줄었습니다.
- **기술직 신규 채용 중 주니어 비중**은 27%에서 9%로 더 빠르게 떨어졌습니다. 주니어 채용 공고는 2025년 12월 이후 크게 줄었습니다.
- 다만 기술직 채용 자체는 절대 숫자로는 계속 늘었습니다. 영업, 재무, 채용 쪽이 더 빨리 늘면서 전체 인원 중 기술직 비중은 61%에서 56%로 낮아졌습니다.
- 에이전트 작업 시간은 2026년 3월 처음으로 사람의 근무 시간을 넘었고, 직원이 직접 지시하는 대화형 에이전트만 봐도 8월에는 사람 근무 시간의 6배였습니다. 에이전트는 여러 개가 동시에 돌기 때문에 단순 비교에는 한계가 있습니다.
- 직원의 회의 시간 중앙값은 1년 전보다 20% 늘었고, 기술직 개인 기여자도 16% 늘었습니다.

Anthropic은 스스로 여러 한계도 밝혔습니다. 도구를 먼저 쓴 사람이 원래 성과가 오르던 사람일 수 있고, 코드 품질 지표는 대략적인 대리 지표이며, 자사의 고용 방식이 다른 회사에 그대로 적용되기는 어렵다는 것입니다. 주니어 감소 분석도 원인을 증명한 것이 아니라 현상을 기술한 것이라고 선을 그었습니다.

### 개발자에게 왜 중요한가

한 회사의 데이터이지만, AI 도입이 가장 앞선 조직에서 벌어지는 일이라는 점에서 업계가 갈 방향을 미리 보여 주는 신호로 읽힙니다. 코드를 직접 치는 시간보다 **에이전트에게 일을 나누고, 결과를 검토하고, 사람들과 맞추는 시간**이 늘고 있다는 것입니다.

경력이 짧은 개발자라면 "AI가 쓴 코드를 읽고 틀린 곳을 찾아내는 능력"이 점점 더 중요한 경쟁력이 됩니다. 팀을 이끄는 입장이라면, 주니어를 덜 뽑았을 때 몇 년 뒤 시니어가 어디서 나올지도 함께 고민해야 할 시점입니다.

## 마무리

오늘 소식을 관통하는 한 줄은 "벽이 있다고 믿는 순간이 가장 위험하다"입니다. VM 경계, 에이전트가 말을 거는 API 주소, 출처 모를 상수 모두 확인하기 전까지는 믿음일 뿐입니다. 이번 주에는 내 에이전트의 MCP 설정 파일과 서버 커널 버전부터 한 번 열어 보면 어떨까요.
