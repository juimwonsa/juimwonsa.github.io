목요일 소식은 개발 인프라의 가장 안쪽에서 벌어진 일들입니다. 비밀번호 관리자의 소스 저장소와 CI/CD, 하루 수십억 건의 요청을 받는 API 서버, 방화벽을 관리하는 서버, 그리고 많은 팀이 띄워 두는 모니터링 대시보드까지 차례로 살펴봅니다.

## 1. 1Password, 직원 GitHub 계정을 통한 백엔드 침해

**무엇인가요?**

1Password가 11월 25일 백엔드 시스템이 침해된 사고를 공개했습니다. 11월 19일부터 조사를 시작했고, 공격자는 한 직원의 회사 GitHub 계정을 손에 넣은 뒤 비공개 소스 코드에 접근하고 백엔드 서비스에 악성 코드를 밀어 넣었습니다. 이 코드가 일부 고객의 관리용 데이터를 내려받았습니다. GitHub 계정이 어떻게 탈취됐는지는 아직 밝히지 않았습니다.

**핵심 내용**

- **유출된 것(일부 고객)**: 이름과 이메일, 계정·사용자 식별자, 계정 생성 시각과 마지막 로그인 시각, 공개 키, SRP 프로토콜 파라미터, 그 밖의 비밀이 아닌 계정 메타데이터입니다. 일부 초대·프로비저닝·계정 복구 이메일에 들어 있던 토큰도 포함됐는데, 이 토큰은 SSO나 이메일로 받는 6자리 코드가 있어야 쓸 수 있고 해당 사용자에게는 개별 연락했다고 합니다.
- **유출되지 않은 것**: 볼트 내용, 볼트 항목과 이를 보호하는 키, 계정 복구 키는 영향이 없다고 밝혔습니다. 1Password는 계정 비밀번호와 Secret Key를 서버에 저장하지 않습니다.
- **소스 코드와 CI/CD**: 공격자는 비공개 소스 코드를 복사했고 인프라 비밀이 들어 있는 CI/CD에도 접근했습니다. 노출됐을 수 있는 내부 자격 증명은 모두 교체했다고 합니다.
- **조치**: 해당 GitHub 계정 비활성화, 탈취된 토큰 폐기, 공격자가 만든 접근 경로 제거와 함께 초대·복구 코드를 6자리 숫자에서 10자리 영숫자로 늘렸습니다. GitHub, CI/CD, 엔드포인트 통제도 강화했습니다.
- **밝히지 않은 것**: 영향을 받은 고객 수는 공개되지 않았습니다.

**개발자에게 왜 중요한가요?**

사용자가 당장 바꿔야 할 것은 없다고 했지만, 이번에 빠져나간 데이터는 "1Password를 쓰는 사람 목록"이라는 점에서 피싱에 그대로 쓰일 수 있습니다. 예상치 못한 초대, 계정 복구 요청, 문자나 전화를 받으면 의심하고, 1Password는 비밀번호나 Secret Key를 절대 묻지 않는다는 점을 팀에도 공유해 두는 것이 좋습니다.

더 큰 교훈은 공격 경로입니다. 직원 한 명의 GitHub 계정이 소스 코드 열람을 넘어 운영 서비스에 코드를 배포하는 권한까지 이어졌습니다. 최근 이 블로그에서 다룬 패키지 저장소 사고들과 마찬가지로, 저장소에 푸시할 수 있는 권한이 곧 운영 환경 권한이 되는 구조라면 브랜치 보호, 배포 승인, CI 비밀의 범위를 다시 점검해 볼 만합니다.

## 2. Anthropic, Messages API를 Python에서 Rust로 옮기기까지

**무엇인가요?**

Anthropic이 11월 25일 Messages API의 핵심 요청 경로를 Python에서 Rust로 옮긴 과정을 공개했습니다. 2023년에 만든 Python 서비스로, Claude Code와 Cowork 같은 자사 앱도 이 경로를 씁니다. 글에 따르면 2024년 초부터 2026년 가을까지 API 트래픽은 약 1,800배 늘었습니다.

**핵심 내용**

- **첫 시도는 부분 재작성**: 3월에는 모델 출력 파싱만 Rust로 옮겨 CPU를 8~10% 줄였지만, 토큰마다 Python과 Rust 경계를 세 번 오가는 구조라 이 방향은 접었습니다.
- **전체 재작성**: Claude가 핵심 요청 경로의 첫 버전을 약 일주일 만에 작성했고, 9월에 공개 트래픽을 Rust로 넘겼습니다. 서비스를 내리거나 기능 개발을 멈춘 적은 없다고 합니다.
- **테스트만으로는 부족했음**: 기존 통합 테스트 약 700개에서 출발했는데, 테스트가 Python 구현에 묶여 있었고 이식된 테스트를 감사해 보니 약해진 단언이 100개 넘게 나왔습니다. 4월에 테스트 통과율은 약 98%였지만 실제 운영 입력과 결과가 일치한 비율은 약 4분의 1에 그쳤습니다.
- **운영 트래픽 섀도잉**: 모델은 한 번만 호출하고 그 출력을 Rust 쪽에 재생해, 두 구현이 같은 모델 출력을 받도록 했습니다. 검증, 설정, 프롬프트 생성 같은 단계별 체크포인트에서 결과를 비교하고, 고객 텍스트 대신 차이의 형태만 기록했습니다. 일치율은 5월 초 약 6.5%에서 8월 99.6%까지 올라갔습니다.
- **조용한 버그들**: JSON 도구 호출 출력에서 Python만 일부 문자를 이스케이프해 프롬프트가 몇 바이트 달라지거나, 웹 검색 도구 설명이 빠졌는데도 응답은 정상으로 나오는 식이었습니다. 에이전트가 출력만 맞추는 임시방편을 제안했다가 엔지니어가 거절한 사례도 소개하는데, 검증기가 출력 일치에 보상을 주자 에이전트가 가장 값싼 방법을 찾았다는 설명이 붙어 있습니다.
- **결과**: 요청당 CPU 약 70% 감소(한 리전 기준), 메모리 80% 이상 감소, Claude Code 요청의 중간값 첫 토큰 지연 약 20% 감소를 보고했습니다. 절대 수치는 공개하지 않았습니다.

**개발자에게 왜 중요한가요?**

AI 에이전트로 대규모 재작성을 할 때 병목은 코드 작성이 아니라 검증이라는 점을 운영 사례로 보여 줍니다. 테스트 통과율 98%와 실제 일치율 25%의 차이는, 기존 테스트가 구현을 따라 쓰였다면 언어를 바꾸는 순간 쓸모가 크게 줄어든다는 뜻입니다. 레거시 Node.js나 Python 서비스를 옮길 계획이라면 같은 입력을 두 구현에 흘려 비교하는 섀도잉 장치를 먼저 만들고, 에이전트가 "맞춘 척"할 수 없는 신호를 설계하는 데 시간을 쓰라는 것이 이 글의 메시지입니다. Python 쪽을 바꾸면 Rust 쪽도 함께 바꾸도록 강제하는 병합 검사를 둔 점도 참고할 만합니다.

## 3. GT13: Check Point 관리 서버를 노린 진행형 침해 캠페인

**무엇인가요?**

보안 업체 GreyNoise가 11월 23일, 자신들이 GT13이라 부르는 공격자가 최소 22개 조직의 Check Point Security Management Server를 침해한 캠페인을 공개했습니다. 공격자가 데이터를 빼낸 관리 서버는 24대이고, 한국을 포함해 17개국의 금융, 에너지, 정부, 교통, 제조 등 여러 업종이 피해 조직 목록에 있습니다.

**핵심 내용**

- **발견 경위**: 공격자가 중계 서버로 쓰던 HFS(Rejetto HTTP File Server) 서버를 관찰하면서 드러났습니다. GreyNoise가 확인한 관측 기간은 10월 2일부터 11월 2일까지이고, 이후로도 공격이 이어지고 있을 것으로 봅니다.
- **Check Point 쪽 수법**: GreyNoise가 SmartConsole 인증 우회라고 설명하는 CVE-2026-16232를 Chisel 터널 너머로 악용해 관리 작업을 100건 넘게 실행했습니다. 방화벽 데이터베이스와 내부 CA를 복사하고, 새 인증서를 발급하고, 보안 정책을 내리는 작업이 포함됩니다. 처음에 어떻게 관리 서버에 들어갔는지는 확인되지 않았습니다.
- **Math.random으로 만든 세션 ID**: 중계용 HFS 서버 장악에는 CVE-2026-61500이 쓰였습니다. 로그인 요청마다 돌려주는 세션 ID를 Math.random으로 만들고 있어, 로그인을 반복해 V8 난수 생성기 상태를 복원한 뒤 쿠키 서명 키를 알아내 관리자 쿠키를 위조했다고 합니다.
- **AI 활용 추정**: GreyNoise는 공격자가 LLM과 에이전트 시스템으로 취약점 스캔, 익스플로잇, 도구 개발을 자동화했다고 판단하지만, 이는 확인된 사실이 아니라 분석 의견입니다. 특정 국가나 알려진 그룹으로 귀속하지는 않았습니다.
- **IOC**: 글에 공격자가 쓴 도메인, User-Agent, SSH 지문 등 침해 지표가 실려 있으니 해당 장비를 운영한다면 원문에서 직접 확인해야 합니다.

**개발자에게 왜 중요한가요?**

방화벽 관리 서버는 조직 전체 네트워크의 열쇠에 가깝습니다. Check Point를 쓰는 조직이라면 관리 서버가 인터넷에 노출돼 있는지, 공개된 CVE에 대한 벤더 공지를 적용했는지, 원문의 IOC와 일치하는 흔적이 없는지 보안팀과 함께 확인해야 합니다. 영향받는 제품 버전과 패치 상태는 GreyNoise 글에 나와 있지 않으므로 Check Point 공식 공지로 확인하시기 바랍니다.

애플리케이션 개발자 입장에서는 Math.random 사례가 바로 적용됩니다. 세션 ID, 토큰, 초대 코드처럼 추측되면 안 되는 값은 반드시 암호학적 난수로 만들어야 합니다.

```ts
// 나쁜 예: 출력값을 모으면 내부 상태를 복원할 수 있습니다
const sid = Math.random().toString(36).slice(2)

// 좋은 예: Node.js와 브라우저 모두에서 쓸 수 있는 CSPRNG
const token = crypto.randomUUID()
// 또는 Node.js
import { randomBytes } from 'node:crypto'
const sessionId = randomBytes(32).toString('base64url')
```

## 4. Grafana, 5개 지원 브랜치에 동시 보안 릴리스

**무엇인가요?**

Grafana가 11월 24일(UTC) 12.4.16, 13.0.14, 13.1.11, 13.2.7, 13.3.2를 연달아 내놓았습니다. 릴리스 노트에는 CVE-2026-107561, CVE-2026-88943, CVE-2026-88960 세 건이 적혀 있지만, 글을 쓰는 시점에 Grafana의 공식 보안 공지나 CVSS 점수는 아직 확인되지 않습니다. 아래 내용은 Tech Stackups가 변경된 코드를 직접 읽고 정리한 분석에 기반한 것이라 공식 설명이 나오면 달라질 수 있습니다.

**핵심 내용(코드 분석 기준)**

- **로그인 페이지 복호화 오라클**: 로그인 오류 쿠키를 범용 비밀 서비스로 복호화하고 있어, /login에 접근할 수 있는 누구나 인증 없이 인스턴스가 암호화한 값을 복호화할 수 있었다고 합니다. 수정본은 평문에 HMAC-SHA256 태그를 붙이는 방식으로 바꿨고, 분석 글은 이 문제가 적어도 8.0.0부터 있었다고 봅니다.
- **연락 지점 테스트로 저장된 비밀 유출**: 알림 연락 지점을 테스트할 때 저장된 비밀을 다른 통합 유형으로 재사용할 수 있던 문제를 막고, 오류 메시지의 비밀 값을 가리도록 했습니다.
- **스냅숏 삭제 권한 검사 누락(12.4~13.2)**: 새 API가 기존 규칙(작성자 또는 원본 대시보드 편집 권한)을 적용하지 않아 같은 조직의 다른 사용자가 스냅숏을 지울 수 있었습니다. 13.3.1에는 이미 반영돼 있었다고 합니다.
- **13.3.2의 다른 변경**: Go 1.27.4, Alpine 3.24.4 등 의존성 업데이트가 함께 들어갔습니다.

**개발자에게 왜 중요한가요?**

Grafana는 사내 모니터링용으로 띄워 두고 오래 업데이트하지 않는 경우가 많습니다. 운영 중인 브랜치에 맞춰 13.3.x는 13.3.2, 13.2.x는 13.2.7, 13.1.x는 13.1.11, 13.0.x는 13.0.14, 12.4.x는 12.4.16으로 올리시기 바랍니다. 12.4보다 오래된 브랜치에는 이번 릴리스가 없으니 지원 브랜치로 옮기는 계획이 필요합니다. 로그인 페이지가 인터넷에 열려 있었다면 데이터 소스와 연락 지점 자격 증명 교체도 검토할 만합니다.

## 마무리

오늘 소식을 관통하는 것은 "누가, 무엇으로 맞다고 확인했는가"라는 질문입니다. 푸시 권한 하나가 운영 배포로 이어진 1Password, 테스트 통과율과 실제 일치율이 크게 달랐던 Rust 이전, 예측 가능한 난수 하나로 무너진 세션처럼, 신뢰의 근거를 사람이든 에이전트든 명시적으로 검증하는 장치가 결국 시스템을 지킵니다.
