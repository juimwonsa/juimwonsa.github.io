어제와 그제(10월 28~29일)는 서버를 운영하는 사람과 프런트엔드를 만드는 사람 모두에게 챙길 거리가 있었습니다. Linux 커널의 TCP 연결 처리에서 원격으로 건드릴 수 있는 메모리 버그가 크게 알려졌고, Next.js 팀은 AI 에이전트로 번들 크기를 줄이는 도구를 내놓으면서 다음 주 보안 릴리스를 예고했습니다. GitHub은 연례 보고서 Octoverse에서 에이전트가 PR을 얼마나 많이 만들고 있는지 숫자로 보여 줬고, Google은 보안 작업에 특화된 새 모델을 제한 공개했습니다.

## 1. Linux 커널 IPv4 TCP use-after-free (CVE-2026-98432)

**무엇인가요?**

IPv4 TCP 연결을 맺는 과정에서 생기는 경쟁 조건(race condition) 버그입니다. 연결 요청에 IP 옵션이 붙어 있을 때, 커널이 그 옵션 메모리를 새 소켓에 복사하지 않고 그대로 넘겨 버립니다. 그런데 다른 CPU가 아직 같은 메모리를 읽으며 SYN-ACK을 만들고 있을 수 있고, 그 사이 메모리가 해제되면 use-after-free가 됩니다. 버그는 Linux 4.4 시절부터 있었고, IPv6 경로는 영향이 없습니다.

**왜 크게 다뤄지나요?**

- 커널 CVE 팀은 CVSS 9.8로 매겼지만, 배포판마다 평가가 크게 다릅니다. Red Hat은 문서에 따라 5.9와 8.1, Oracle·SUSE는 8.1, Amazon은 7.0입니다. 실제 위험도는 환경에 따라 다르다는 뜻입니다.
- The Hacker News 보도에 따르면 이 버그는 Anthropic 연구원이 찾았고, Anthropic은 MPTCP(멀티패스 TCP) 리스너가 열린 서버에서 Claude가 작성한 익스플로잇으로 원격 root 명령 실행까지 해냈다고 밝혔습니다. 커널 주소 유출에 약 48분, 이후 명령 실행까지 약 5분이 걸렸다고 합니다. 다만 익스플로잇 코드는 공개되지 않았고, 10월 29일 기준 실제 공격 보고나 CISA KEV 등재는 없습니다.

**패치 상황 (10월 29일 기준 보도 내용)**

- 업스트림 수정 버전: 5.10.272, 5.15.223, 6.1.190, 6.6.159, 6.12.113, 6.18.56, 7.2.10, 7.3
- Debian bookworm·trixie, Oracle Linux(UEK), Amazon Linux 2023의 6.18·6.12 커널은 수정본이 나왔습니다.
- Ubuntu(16.04부터 26.10까지)와 RHEL 8·9·10, OpenShift 4는 아직 수정본이 없습니다. Amazon Linux 2도 대기 중입니다.

**개발자가 할 일**

Node.js나 Firebase 바깥에 직접 VM·컨테이너 호스트를 운영한다면 먼저 커널 버전부터 확인해 두세요. 컨테이너는 호스트 커널을 공유하므로 이미지 업데이트로는 해결되지 않습니다.

```bash
uname -r
# 요청 소켓 마이그레이션을 쓰지 않는다면 한 가지 경로를 줄이는 임시 조치
sudo sysctl -w net.ipv4.tcp_migrate_req=0
```

**주의할 점**: 위 sysctl은 일부 경로만 막을 뿐 근본 해결이 아닙니다. Red Hat은 기준을 만족하는 완화책이 없다고 밝혔습니다. 결국 배포판 커널 업데이트가 나오는 대로 적용하고 재부팅하는 것이 유일한 확실한 방법이니, Ubuntu·RHEL 사용자는 보안 공지를 계속 지켜봐야 합니다.

## 2. Next.js: 번들 크기를 줄이는 에이전트 스킬, 그리고 11월 3일 보안 릴리스

**next-bundle-optimizer 스킬**

Next.js 팀이 10월 28일 블로그에서 Turbopack 번들 분석기를 AI 에이전트가 쓸 수 있게 만든 스킬을 소개했습니다. Next.js 16.4 이상, 그리고 기본 번들러인 Turbopack이 필요합니다.

```bash
npx skills add vercel/next.js --skill next-bundle-optimizer
```

설치한 뒤 에이전트에서 `/next-bundle-optimizer`를 실행하면 됩니다. 동작 방식이 꽤 흥미롭습니다.

- `next analyze`로 저장한 스냅숏을 JSON으로 내보내 모듈 그래프와 청크 그래프를 다시 구성합니다. 이 데이터는 `next analyze export`로 직접 뽑아 쓸 수도 있습니다.
- 서로 강하게 연결된 모듈 묶음을 찾고, 어떤 import 경계를 끊으면 그 묶음을 지연 로딩할 수 있는지 최소 컷 알고리즘으로 계산합니다.
- 서버 컴포넌트로 옮길 수 있는 로직, 중복 설치된 큰 의존성, 트리 셰이킹이 안 된 코드도 찾아 줍니다.
- 기본은 보고만 하고, `/next-bundle-optimizer fix`를 붙이면 수정을 적용한 뒤 다시 분석해서 전후를 비교합니다.

개발자가 가장 자주 놓치는 함정도 짚어 줍니다. `lazy(() => import('./HeavyComponent'))`로 지연 로딩을 했어도, 같은 번들의 다른 파일 하나가 `HeavyComponent`를 정적으로 import하면 결국 처음부터 내려받게 됩니다. 이런 관계는 사람이 코드만 보고 찾기 어렵습니다.

Vercel은 이 스킬로 v0와 vercel.com에서 압축 기준 2MB 가까운 JavaScript를 덜어 냈다고 합니다. 예를 들어 실험 사용자에게만 필요한 코드 에디터가 거의 모든 페이지에서 미리 로드되고 있었고, 공용 유틸 파일 하나가 관측 쿼리 엔진 전체를 끌어오고 있었다고 합니다.

사람이 직접 보는 분석기(`next analyze`)도 좋아졌습니다. 큰 라우트를 모아 보여 주는 요약 화면, 크기순 정렬 표, 자동 저장된 스냅숏 간 비교, 첫 렌더링에 꼭 필요한 모듈만 걸러 보는 기능이 추가됐습니다.

**11월 3일 보안 릴리스 예고**

같은 주에 Next.js는 11월 3일(미국 시간 화요일)에 정기 보안 릴리스를 낸다고 미리 알렸습니다. 중간(Medium) 등급 취약점 7건이 대상이고, 영향 범위와 버전은 릴리스 때 함께 공개됩니다. 10월에만 긴급 업데이트가 있었던 만큼, 다음 주 초에 업그레이드할 시간을 미리 잡아 두는 편이 좋겠습니다.

**주의할 점**: 2MB 절감은 Vercel 자체 앱 기준이고, 효과는 앱 구조에 따라 크게 다릅니다. `fix` 모드는 import 구조를 바꾸므로, 변경마다 PR을 따로 만들고 프리뷰 배포에서 화면 동작을 확인한 뒤 합치는 흐름을 권합니다.

## 3. GitHub Octoverse 2026: PR 10개 중 4개는 에이전트가 시작

GitHub이 10월 28일 연례 보고서 Octoverse 2026을 공개했습니다. 집계 기간은 2025년 10월 1일부터 2026년 9월 30일까지입니다. 어제 정리한 Universe 발표의 배경이 되는 숫자들입니다.

- **활동량**: 지난 12개월간 푸시 179억 건, 커밋 343억 건, 병합된 PR 13억 건, GitHub Actions 작업 약 450억 건입니다. 푸시는 2024년과 2025년을 합친 것보다 많습니다.
- **에이전트가 시작한 PR**: 첫 초안을 코딩 에이전트가 만든 PR 비율이 3월 17%에서 9월 40% 이상으로 뛰었습니다. 9월 한 달에만 1억 1천만 건입니다. GitHub이 감지한 경우만 센 값이라 실제로는 더 많을 수 있다고 합니다.
- **병합률**: 2주 안에 병합된 비율이 에이전트가 관여한 PR은 2월 83%에서 9월 90%로 올랐고, 감지된 에이전트 관여가 없는 PR은 약 86%로 그대로였습니다.
- **언어**: 월간 기여자 수 기준으로 TypeScript가 1위, Python이 2위, JavaScript가 3위입니다. 에이전트 신호가 있는 저장소 중 35%가 TypeScript를 주 언어로 썼는데, GitHub은 인과 관계가 아니라 참고 수치라고 선을 그었습니다.
- **보안**: 비밀 값 노출을 막는 푸시 보호 검사가 58억 회 실행돼 2025년보다 네 배 가까이 빠른 속도입니다.

**개발자에게 의미하는 것**: 코드를 만드는 비용은 급격히 내려갔고, 이제 병목은 검토와 검증으로 옮겨 가고 있습니다. TypeScript를 주로 쓴다면 이미 가장 에이전트 친화적인 생태계 한가운데 있다는 뜻이기도 합니다. 반대로 에이전트가 만든 PR이 늘수록 타입 검사, 테스트, 비밀 값 스캔 같은 자동 검증 장치가 팀의 실질적인 안전망이 됩니다.

## 4. Google Gemini 4 Carbon: 보안 작업 특화, 일단은 제한 공개

Google이 10월 28일 새 프런티어 모델 Gemini 4 Carbon을 발표했습니다. 2주 전 나온 Gemini 4 Argon의 후속으로, 긴 작업과 사이버 보안 능력을 전면에 내세웠습니다.

- **성능 (Google 발표)**: Artificial Analysis Intelligence Index v5.0에서 59점으로 1위라고 밝혔습니다. 가드레일 없이 측정한 보안 벤치마크에서 취약점 찾기(SEC-bench Pro) 88.2%, 익스플로잇(ExploitGym) 54.8%, 패치(CWE-bench) 71.0%를 기록했다고 합니다. 안전한 코드를 만드는 성공률은 Argon의 두 배 이상이라고 합니다.
- **안전성**: 간접 프롬프트 인젝션 벤치마크(Gray Swan)의 공격 성공률이 0.0%였고, Terminal-Bench 4.0에서 편법으로 점수를 얻는 비율도 0.0%로 낮췄다고 합니다.
- **접근 방식**: 이번 주부터 일부 보안 방어 조직에만 먼저 열고, Fairwind 프로그램을 통해 신뢰할 수 있는 파트너로 넓힌 뒤 일반 개발자에게 공개합니다. 일반 공개 날짜는 아직 없습니다. 미국 정부의 자발적 사전 시험에도 참여합니다.
- **가격**: 출시 기념가로 입력 100만 토큰당 2달러, 출력 10달러이고, 이후에는 각각 4달러, 20달러가 됩니다. 캐시된 입력은 95% 할인됩니다.

**주의할 점**: 모든 벤치마크 수치는 Google 자체 발표이고, 일반 개발자는 아직 API로 쓸 수 없습니다. 1번의 Linux 커널 사례처럼 AI가 실제 익스플로잇까지 만드는 시대라, 모델 회사들이 보안 능력이 강한 모델일수록 방어 측에 먼저 푸는 순서를 택하고 있다는 점이 눈에 띕니다.

## 마무리

오늘 소식들은 한 방향을 가리킵니다. 에이전트가 PR의 40%를 쓰고, 번들을 분석하고, 커널 익스플로잇까지 만듭니다. 코드를 쓰는 속도는 더 이상 병목이 아니고, 무엇을 합치고 언제 패치할지 판단하는 일이 개발자의 핵심 역할로 남고 있습니다.
