지난 한 주는 프레임워크 업데이트 소식과 함께 "저장소 자체가 공격당하는" 공급망 사건이 유난히 많았습니다. 특히 패키지가 아니라 git 저장소와 CI를 노리는 공격이 이어지고 있어, 프론트엔드든 백엔드든 저장소를 운영하는 개발자라면 한 번쯤 점검해 볼 만한 내용들입니다. 네 가지를 골라 정리했습니다.

## 1. Next.js 16.4 출시, 그리고 10월 14일 보안 업데이트 예고

10월 6일 Next.js 16.4가 출시됐습니다. 이번 버전의 핵심 메시지는 하나입니다. **"이제 모든 Next.js 앱에 Cache Components를 권장한다."**

### Cache Components가 기본이 됩니다

Cache Components는 컴포넌트나 함수 단위로 `'use cache'`를 붙여 캐시 가능한 부분을 명시하는 방식입니다. 기존 App Router의 암묵적인 캐싱을 대체하는 모델로, 그동안은 일부 상황에서 비용과 성능 면의 보장이 부족해 전면 권장하지 않았습니다. 16.4에서 그 빈틈을 메우는 기능들이 들어가면서, 이제 `create-next-app`으로 만드는 새 프로젝트에는 기본으로 켜지고 Next.js 17에서는 기본 모델이 될 예정입니다.

기존 프로젝트에서 사용하려면 설정 두 개를 켜면 됩니다.

```ts
// next.config.ts
const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
}
```

16.4에서 새로 들어온 기능 중 실무에서 유용해 보이는 것들입니다.

- **`ensureStatic`**: 라우트나 레이아웃에 `export const ensureStatic = 'navigation'`을 선언하면, 그 페이지에 요청 시점 렌더링이 필요한 컴포넌트가 끼어드는 순간 빌드가 실패합니다. 블로그나 마케팅 페이지처럼 "반드시 정적이어야 하는" 페이지에 실수로 동적 요소가 들어가 서버 비용이 늘어나는 일을 막을 수 있습니다.
- **`navigation()` / `prefetch()`**: 프리페치 단계에서 불러오지 않을 부분을 지정합니다. 예를 들어 메일 목록의 링크를 프리페치할 때 첫 메시지만 미리 가져오고, 스레드 전체는 실제로 클릭했을 때 불러오도록 나눌 수 있습니다.
- **에이전트용 업그레이드 도구**: `npx next@canary upgrade --agent=latest`를 실행하면 현재 버전 확인부터 마이그레이션 가이드, codemod, 검증 단계까지 코딩 에이전트가 따라갈 수 있는 형태로 준비해 줍니다. `experimental.agentUpgrade` 설정으로 보안 업데이트가 있을 때 개발 서버에서 알림을 받을 수도 있습니다.

이 밖에도 Turbopack 디스크 캐시 용량 20~25% 감소, 화면에 보고 있는 페이지만 갱신하는 서버 HMR, 프로덕션 CSS 클래스명 단축 같은 개선이 별도 설정 없이 적용되고, React 19.3이 함께 들어갔습니다.

### 10월 14일 보안 업데이트를 놓치지 마세요

더 급한 소식도 있습니다. Next.js 팀은 10월 8일 공지를 통해 **10월 14일(미국 기준 수요일)에 정기 일정 외 보안 업데이트를 배포한다**고 예고했습니다. 상위 의존성에서 나온 취약점 세 건으로, 두 건이 Critical, 한 건이 High 등급입니다. 이 중 두 건은 9월 보안 릴리스에 들어갈 예정이었다가 조율 문제로 미뤄진 것이라고 합니다.

영향 범위와 패치 버전은 업데이트와 함께 공개되므로 아직 구체적인 내용은 알 수 없습니다. 운영 중인 Next.js 서비스가 있다면 이번 주 안에 배포 일정을 비워 두고, 공지가 나오면 바로 올릴 수 있도록 준비해 두는 것이 좋겠습니다.

## 2. GhostAction 공격 재등장: 탈취한 계정으로 워크플로를 심는다

보안 업체 Socket이 10월 9일, 2025년 9월에 처음 보고됐던 **GhostAction** 공격이 다시 대규모로 나타났다고 발표했습니다.

수법은 단순하지만 위험합니다.

1. 공격자가 어떤 경로로든 메인테이너 계정의 자격 증명을 손에 넣습니다.
2. 저장소의 기본 브랜치에 `security-audit.yml`이라는 이름의 워크플로 파일을 직접 커밋합니다. 이름과 달리 보안 기능은 전혀 없습니다.
3. 이 워크플로는 어떤 브랜치나 태그에 푸시가 일어나도 실행되며, 저장소에 등록된 Actions 시크릿과 함께 **git 히스토리 전체**에서 AWS, OpenAI, Anthropic, GitHub, Slack 등의 키 패턴을 찾아 외부 서버로 전송합니다.

10월 8일 하루에만 346개 저장소에 커밋이 들어갔고, 이후 조사에서 500개가 넘는 계정이 관련된 것으로 확인됐다고 합니다. 이전 버전이 Actions 시크릿만 노렸다면, 이번에는 소스 코드에 실수로 커밋했다가 지운 키까지 히스토리에서 긁어 간다는 점이 달라졌습니다.

### 점검 포인트

- `.github/workflows/` 아래에 내가 만들지 않은 `security-audit.yml` 또는 `github_actions_security.yml`이 있는지 확인합니다. 포크한 저장소도 Actions를 켜기 전에 살펴봐야 합니다.
- 예전에 커밋했다가 지운 API 키가 있다면 "지웠으니 괜찮다"고 생각하지 말고 폐기 후 재발급합니다. 히스토리에 남아 있는 한 노출된 것으로 봐야 합니다.
- GitHub 시크릿 스캐닝의 푸시 보호를 켜고, 외부 기여자의 워크플로 실행에는 승인을 요구하도록 설정합니다.
- 계정에는 피싱에 강한 2단계 인증(패스키, 보안 키)을 적용합니다.

## 3. Zod 저장소 악성 커밋 사건과 GitHub의 푸시 기록 기능

### 무슨 일이 있었나

10월 11~12일 Hacker News에서 "Zod 4.6.6이 감염됐다"는 글이 화제가 됐습니다. 정리하면 사건 자체는 9월 21일에 있었던 일입니다. 같은 날 `colinhacks/zod`, `standard-schema/standard-schema`, `nubjs/nub` 세 저장소의 main 브랜치에 "Fix bugs and improve performance"라는 평범한 메시지의 악성 커밋이 연달아 푸시됐습니다. 추가된 코드는 설치 시점에 실행되어 이더리움 스마트 컨트랙트에서 다음 접속 주소를 받아오고, 그곳에서 받은 자바스크립트를 실행하는 구조였습니다.

다행히 결과는 "아슬아슬하게 막은" 쪽에 가깝습니다.

- **npm에 배포된 `zod`에는 악성 코드가 포함되지 않았습니다.** 해당 커밋은 릴리스 전에 되돌려졌습니다.
- 메인테이너에 따르면 Zod는 trusted publishing과 별도의 배포 환경을 쓰고 있어서, 저장소에 코드가 들어가도 바로 npm으로 나가지 않았습니다.
- 태그 생성만으로 배포가 돌던 `@nubjs/nub`는 0.9.4 버전이 npm 배포 단계까지 갔지만, npm의 정적 검사에 걸려 공개되기 전에 차단됐습니다.

메인테이너는 원인을 npm 토큰이 아니라 **탈취된 git 푸시 자격 증명**으로 보고 있으며, 앞으로는 릴리스마다 2FA를 거친 명시적 승인이 필요한 방식으로 바꾸겠다고 밝혔습니다. npm에서 받은 Zod를 쓰고 있다면 당장 할 일은 없지만, lockfile에 `@nubjs/nub@0.9.4`가 있는지 정도는 확인해 볼 만합니다.

### GitHub, "누가 푸시했는지"를 커밋마다 기록

이 사건과 GhostAction이 공통으로 보여주는 건, git 커밋의 작성자 정보는 누구나 마음대로 적을 수 있다는 점입니다. 공교롭게도 GitHub는 10월 12일 **push attribution** 기능을 제한적 공개 프리뷰로 내놓았습니다.

- 커밋마다 실제로 인증을 거쳐 푸시한 사용자를 별도로 기록하고, 화면과 API에서 author, committer 옆에 함께 보여줍니다.
- 새 저장소 규칙 조건인 **"Committer must match pusher"**를 룰셋에 추가하면, committer 정보가 푸시한 사람의 인증된 이메일과 일치하지 않는 푸시를 막을 수 있습니다. 권한이 낮은 계정이 신뢰받는 메인테이너인 척 커밋을 올리는 수법을 차단하는 장치입니다.

현재는 GitHub Enterprise 고객 대상이고 계정 담당자를 통해 신청해야 합니다. 개인 저장소에서 바로 쓸 수는 없지만, 커밋 서명과 함께 "커밋의 출처를 어떻게 믿을 것인가"에 대한 플랫폼 차원의 답이 나오기 시작했다는 점에서 눈여겨볼 만합니다.

## 4. Anthropic, 오픈소스 프로젝트용 무료 AI 취약점 스캐너 공개

Anthropic이 10월 8일 오픈소스 메인테이너를 위한 무료 취약점 스캔 서비스 **OSS Scanner**를 공개했습니다. 내부 보안 프로젝트에서 Claude로 취약점을 찾던 경험을 바탕으로 만든, 신청한 프로젝트만 대상으로 하는 서비스입니다.

- **신청 방식**: `anthropics/oss-scanner` GitHub 저장소에 프로젝트 정보를 담은 YAML 파일을 PR로 올립니다. 저장소 주소, 담당자 이메일, 그리고 오프라인에서 빌드 환경을 갖추는 Dockerfile 경로가 필수입니다. 어떤 입력을 공격자가 조작할 수 있는지 적은 위협 모델 파일을 함께 넣으면 결과의 정확도를 높이는 데 도움이 됩니다.
- **동작 방식**: 등록된 프로젝트를 주기적으로 스캔하고, 사람의 검토 없이 모델이 작성한 보고서를 메인테이너에게 보냅니다. 그만큼 오탐 가능성이 있어서, 일반적인 90일 공개 기한을 일괄 적용하지는 않는다고 합니다.
- **대상**: 핵심 메인테이너가 신청할 수 있고, 선정 기준은 Google OSS-Fuzz와 비슷하게 운영한다고 밝혔습니다.

발표에 따르면 Anthropic은 주요 오픈소스에서 2만 9천 건이 넘는 후보 취약점을 찾아 그중 6천여 건을 메인테이너에게 보고했고, 10월 2일 기준 584건의 보안 권고가 나왔습니다. npm에 라이브러리를 올리고 있다면 신청을 고려해 볼 만합니다. 다만 모델이 만든 보고서인 만큼, 받은 결과는 직접 재현해 보고 판단하는 과정이 꼭 필요합니다.

## 마무리

이번 주 소식은 결국 **"코드가 어디서 왔는지 증명할 수 있는가"**라는 질문으로 모입니다. Next.js는 에이전트가 업그레이드와 보안 패치를 따라가도록 돕고, GitHub는 커밋마다 실제 푸시한 사람을 남기며, AI 스캐너는 취약점을 대신 찾아 줍니다. 하지만 GhostAction과 Zod 사건이 보여주듯 가장 약한 고리는 여전히 계정 하나, 키 하나입니다. 2단계 인증과 배포 승인 절차, 히스토리에 남은 키 정리 같은 기본기를 이번 기회에 한 번 점검해 보시길 권합니다.
