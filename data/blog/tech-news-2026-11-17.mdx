오늘은 보안 소식이 유난히 많습니다. 그중에서도 웹 프런트엔드를 만드는 사람이라면 1번은 꼭 읽어 보시길 권합니다. 내 코드와 서버는 멀쩡한데 신뢰하던 서드파티 스크립트 하나 때문에 사이트가 카드 정보를 빼돌리는 상황이 실제로 하루 만에 수많은 대형 사이트에서 벌어졌습니다.

## 1. Optimizely Web 스니펫으로 178개 조직에 악성 스크립트 배포

**무엇인가요?**

A/B 테스트 플랫폼 Optimizely Web을 통해 11월 16일 하루 동안 악성 JavaScript가 여러 대형 사이트 방문자에게 전달됐습니다. CSP 모니터링 서비스 Report URI의 Scott Helme가 분석 글을 공개했는데, 확인한 스니펫 1,611개 중 188개(조직 기준 178곳)가 감염돼 있었습니다. Zoom, BBC, CNN, Salesforce, GitLab, IKEA, HSBC, Equifax, Air France-KLM, Ledger 같은 이름이 목록에 올라 있고, Optimizely 자체 사이트도 영향을 받았습니다.

**어떻게 벌어졌나요?**

- Optimizely 고객은 Optimizely CDN에서 프로젝트별 스니펫을 불러옵니다. 이 스니펫에는 모든 페이지에서 실행되는 **Project JavaScript** 칸이 있는데, 공격자가 서로 관계없는 많은 고객 프로젝트의 이 칸에 로더 코드를 써 넣었습니다.
- 로더는 일반 script 태그, base64로 감춘 URL, 도메인이 막혔을 때 `eval`로 돌리는 인라인 전체 복사본까지 세 가지 형태로 들어갔습니다.
- 스니펫을 자기 도메인으로 프록시해 서빙하던 고객도 내용이 같은 프로젝트에서 나오므로 똑같이 감염됐습니다.
- 공격자가 어떻게 쓰기 권한을 얻었는지는 아직 밝혀지지 않았습니다. Report URI는 CDN 캐시 오염은 아니라고 봤고, 글 작성 시점까지 Optimizely의 공식 답변은 없었다고 합니다.

**악성 코드가 한 일**

- 페이지 텍스트, 폼, 클립보드, 외부 요청에 들어 있는 암호화폐 지갑 주소를 공격자 주소로 바꿔치기
- 오후부터는 사이트 자체 입력란에 입력된 카드 번호, 유효기간, CVV를 가로채는 스키머 추가. Stripe처럼 결제사 iframe으로 받는 카드는 손이 닿지 않았습니다.
- HttpOnly가 아닌 쿠키와 페이지 스크린샷 전송
- iPhone과 iPad에는 숨은 iframe으로 iOS 익스플로잇 킷 로드. 글에 따르면 iOS 18.7.3 이상, 26.3 이상은 패치된 상태입니다.

페이로드는 그날 하루에만 26번 다시 빌드됐고, 저녁 무렵 대부분의 고객 스니펫이 정리됐습니다.

**CSP는 얼마나 막았나요?**

이 글에서 가장 실용적인 부분입니다. 영향받은 조직의 호스트를 크롤링해 CSP를 평가해 보니, 페이로드 실행 자체를 막은 곳은 15% 남짓에 그쳤습니다.

- `cdn.optimizely.com`을 허용 목록에 넣어 둔 것은 아무 도움이 안 됐습니다. 악성 코드가 바로 그 신뢰하는 호스트에서 왔기 때문입니다.
- `'strict-dynamic'`은 스니펫이 삽입하는 스크립트를 그대로 신뢰하므로 페이로드를 통과시켰습니다.
- Optimizely 문서가 권하는 `'unsafe-eval'`은 인라인 대체 경로가 돌아가게 해 줬습니다.
- 일부 사이트는 `connect-src`가 데이터 전송을 막았지만, 주소 바꿔치기는 페이지 안에서 일어나므로 막지 못했습니다.

**개발자에게 왜 중요한가요?**

분석·실험·태그 관리 스크립트는 우리 앱 번들과 같은 권한으로 돌아갑니다. 마케팅 팀이 대시보드에서 넣는 코드는 코드 리뷰도, 배포 파이프라인도 거치지 않습니다. 이번 사건은 "신뢰하는 도메인"이 더 이상 안전의 근거가 아니라는 점을 다시 보여 줍니다.

**지금 할 일**

- Optimizely Web을 쓴다면 Project JavaScript와 실험 커스텀 코드에서 `1688360.cc`, `atob(`, 낯선 스크립트를 찾아보고, 계정 쓰기 권한과 자격 증명을 점검하세요.
- 11월 16일 자사 폼으로 받은 카드 정보는 노출됐을 수 있다고 가정하고, HttpOnly가 아닌 쿠키에 담긴 세션이나 비밀값은 교체하는 편이 안전합니다.
- 결제 화면처럼 민감한 페이지에서는 서드파티 실험·분석 스크립트를 아예 빼고, `connect-src`를 좁히고 CSP 위반 보고를 켜 두세요.

## 2. Amazon, API 키를 훔쳐 자기 연료로 쓰는 ARTEX 에이전트 분석

**무엇인가요?**

Amazon 위협 인텔리전스 팀이 인터넷에 노출된 AI 앱을 뒤져 AI 제공자 API 키를 훔치는 공격자 에이전트들을 포착했다고 공개했습니다. LLM 서비스로 위장한 미끼 서버망(MadPot)에 에이전트가 요청을 보내면서 운영자 지시와 진행 기록까지 함께 실어 보낸 덕분에 내부 작업 목록을 볼 수 있었다고 합니다. Amazon은 이 에이전트들이 오픈소스 AI 침투 테스트 도구 ARTEX 위에서 돌았다고 중간 정도의 확신으로 평가했습니다.

**무엇을 노렸나요?**

- **LLM 게이트웨이·프록시**: One API, New API, Veloera, Sub2API, LiteLLM
- **AI 앱 빌더**: Dify, FastGPT, Langflow, RAGFlow, Open WebUI, LobeChat, Ollama

게이트웨이가 우선 표적인 이유는 간단합니다. 관리자 페이지 하나만 뚫리면 여러 제공자의 키가 한꺼번에 나오기 때문입니다.

**어떤 방법을 썼나요?**

새로운 기법은 없었습니다. 로그인 없이 열리는 관리자·제공자 설정 엔드포인트, 설치를 끝내지 않은 인스턴스, 기본 비밀번호, URL을 가져오는 기능을 이용한 SSRF로 클라우드 메타데이터 접근, 그리고 클라이언트 JavaScript와 소스맵, 디버그 경로, env 파일에 남은 비밀값이 주된 입구였습니다. GitHub 저장소, npm·PyPI 패키지, 컨테이너 이미지 레이어, 노트북 파일까지 비밀값을 찾는 데 썼다고 합니다. 훔친 키는 동작을 확인한 뒤 공용 풀에 넣고, 다시 그 키로 모델을 돌려 다음 키를 찾는 구조였습니다.

**개발자에게 왜 중요한가요?**

사내 실험용으로 띄운 LiteLLM이나 Dify, Open WebUI가 생각보다 흔하게 인터넷에 그대로 열려 있습니다. 이런 도구에는 결제 수단이 연결된 API 키가 모여 있으니, 공격자 입장에서는 가장 수지맞는 표적입니다. 이 블로그에서 Langflow 원격 코드 실행을 다룬 적이 있는데, 그런 알려진 취약점이 이제는 사람이 아니라 에이전트에 의해 대량으로 훑어지고 있다는 뜻입니다.

**지금 할 일**

- 자체 호스팅한 AI 도구가 공개 인터넷에 열려 있는지 확인하고, 기본 관리자 키(LiteLLM의 master key 등)를 바꾸고 설치 마법사를 끝까지 마쳐 두세요.
- 프런트엔드 번들과 소스맵에 키가 섞여 들어가지 않았는지 빌드 결과물을 검색해 보세요. React나 Vite 앱에서 공개 접두사가 붙은 환경 변수는 전부 브라우저로 나간다는 점을 잊기 쉽습니다.
- 제공자 콘솔에서 사용량 알림과 지출 한도를 걸어 두면, 키가 새도 피해를 빨리 알아챌 수 있습니다.
- Langflow는 1.3.0 이상, RAGFlow는 0.25.0 이상으로 올리는 것이 기사에 정리된 권고입니다.

## 3. Windows 11, 어떤 코딩 에이전트를 쓰는지 진단 데이터로 수집

**무엇인가요?**

보안 연구자 Xusheng Li가 Windows 11의 진단 데이터 구성 요소가 개발자 도구와 코딩 에이전트 실행 여부를 기록해 Microsoft로 보낸다는 사실을 블로그에 정리했습니다. 문제의 구성 요소는 DiagTrack(Connected User Experiences and Telemetry) 서비스가 띄우는 `MissionControlAggregator.dll`이고, 빌드 26200.9974의 ARM64 가상 머신에서 확인했다고 합니다.

**무엇을 기록하나요?**

- **CLI 에이전트**: `copilot.exe`, `claude.exe`, `codex.exe`, `agy.exe`, 그리고 WSL 안의 같은 이름 실행 파일
- **데스크톱 에이전트**: `github.exe`, `claude.exe`, `codex.exe`, `cursor.exe`, `antigravity.exe`
- **개발 도구**: `node.exe`, `python.exe`, `dotnet.exe`, `code.exe`, `devenv.exe` 등은 더 넓은 범주로 묶어 집계

남기는 것은 일정 기간 동안 어떤 도구가 보였는지를 나타내는 비트맵뿐이고, 실행 시간이나 프롬프트, 소스 코드는 보고서에서 발견되지 않았다고 합니다. 연구자는 `cmd.exe`의 이름을 `codex.exe`로 바꿔 실행해 Codex로 인식되는 것까지 확인했습니다. 다만 판정이 프로세스 이름만으로 이뤄진다는 뜻이기도 합니다.

**켜져 있나요?**

`CLICodingAgentUsage`라는 기능 플래그가 연구자 VM에서 서비스 실험으로 이미 켜져 있었지만, 공개 ISO의 기본 이미지에서는 꺼져 있었다고 합니다. 모든 PC에서 동작한다고 단정할 수는 없습니다. 해당 이벤트는 필수가 아닌 선택적 진단 데이터로 분류돼 있어, **설정 → 개인 정보 및 보안 → 진단 및 피드백**에서 선택적 진단 데이터 보내기를 끄면 업로드 대상에서 빠집니다. 글 작성 시점까지 Microsoft의 공식 입장은 없었습니다.

**개발자에게 왜 중요한가요?**

데이터 자체는 거칠지만, 운영체제 제조사가 어떤 AI 코딩 도구가 얼마나 쓰이는지 직접 세고 있다는 점은 의미가 있습니다. 회사 PC라면 보안팀이나 IT 관리자가 진단 데이터 정책을 어떻게 잡아 두었는지 한 번 확인해 볼 만합니다.

## 4. uBlock Origin, 클릭 한 번으로 모든 사이트에 스크립트를 심는 취약점

**무엇인가요?**

광고 차단 확장 uBlock Origin에서, 악성 웹사이트가 확장에 "신뢰하는 필터"를 몰래 추가하게 만들 수 있는 취약점이 보고됐습니다. 신뢰하는 필터는 페이지에 스크립트를 주입할 수 있으므로, 결과적으로 공격자가 다른 아무 사이트에서나 JavaScript를 실행하는 범용 XSS가 됩니다. 가장 심각하게 영향받은 것은 Firefox용 MV2 버전이고, MV3 버전인 uBO Lite에도 덜 위험한 비슷한 문제가 있었습니다. 현재는 수정됐으며 권고 번호는 GHSA-cmqw-9r2w-6wv2입니다.

**어떻게 동작했나요?**

- 기본 필터 목록의 규칙 하나가 확장 내부 리소스로 요청을 보내는데, 페이지가 이 요청을 가로채 설치마다 무작위인 확장 UUID를 알아냅니다.
- 그 UUID로 요소 선택기(element picker) 화면을 보이지 않는 iframe에 띄우고, 메시지로 선택기를 조종합니다.
- 선택기는 원래 스크립트 필터를 막지만, 옵션 값이 필터 문법 뒤에 그대로 이어 붙여지는 탓에 줄바꿈 하나로 새 필터를 통째로 끼워 넣을 수 있었습니다.
- 사용자는 투명한 "생성" 버튼을 한 번 누르기만 하면 됩니다.

근본 원인은 선택기가 자신을 띄운 쪽이 누구인지 확인하지 않고 메시지를 받아들였다는 점입니다. 수정판에서는 콘텐츠 스크립트가 진짜 선택기에게 비밀값을 넘기고, 첫 메시지에 그 값이 있어야만 동작하도록 바꿨습니다.

**개발자에게 왜 중요한가요?**

사용자로서는 확장을 최신 버전으로 유지하면 됩니다. 만드는 쪽에서는 Electron 앱, 브라우저 확장, iframe 위젯 어디에나 적용되는 교훈이 있습니다.

- `postMessage`나 MessageChannel로 들어오는 메시지는 내 UI 컴포넌트에서 온 것처럼 보여도 출처를 검증해야 합니다.
- 확장 리소스 URL이나 내부 ID는 비밀이 아닙니다. 노출될 수 있다고 가정하고 설계하세요.
- 사용자 입력을 다른 문법(필터, 쿼리, 설정 파일)에 이어 붙일 때는 줄바꿈과 구분자를 반드시 걸러야 합니다.

```ts
// Electron preload나 iframe 위젯에서 메시지를 받을 때의 최소 점검
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://app.example.com') return
  if (event.source !== expectedFrame?.contentWindow) return
  // 이후에도 event.data는 신뢰하지 말고 형식을 검증합니다
})
```

## 마무리

오늘 소식은 모두 "믿고 들여놓은 것"이 문제였습니다. 서드파티 스니펫, 설치만 해 둔 AI 게이트웨이, 운영체제의 진단 기능, 광고 차단 확장까지 전부 우리가 직접 고른 도구입니다. 들여놓은 순간 끝이 아니라, 그 도구가 무엇을 할 수 있고 실제로 무엇을 하는지 주기적으로 다시 보는 습관이 필요합니다.
