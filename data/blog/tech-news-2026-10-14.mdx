어제에 이어 오늘도 공급망 보안 소식이 중심입니다. 다만 이번에는 악성 패키지가 아니라, 우리가 "안전하다고 믿고 쓰던 장치" 자체의 허점이 드러났다는 점이 다릅니다. npm의 trusted publishing, Docker Hub의 액세스 토큰, GitLab의 CI 설정 파싱이 그 주인공입니다. 여기에 AI 모델 경쟁 소식 하나를 더해 네 가지를 정리했습니다.

## 1. npm trusted publishing의 SlugFest 취약점과 GitHub의 대응

### 무엇이 문제였나

npm의 trusted publishing은 GitHub Actions 같은 CI에서 장기 토큰 없이, 짧게 유지되는 OIDC 토큰으로 패키지를 배포하게 해 주는 기능입니다. 최근 몇 달 사이 토큰 탈취형 공격이 잇따르면서 사실상 권장 배포 방식이 됐습니다.

보안 업체 Bloom Security가 **SlugFest**라고 이름 붙인 이 문제는 신뢰를 연결하는 기준에 있었습니다. npm은 첫 배포가 성공하기 전까지 저장소를 GitHub의 고유 숫자 ID가 아니라 `owner/repo` 형태의 이름(slug)으로만 확인했습니다. 그래서 다음과 같은 시나리오가 가능했습니다.

1. 메인테이너가 npm에 trusted publisher를 등록해 두고, 정작 그 저장소에서 한 번도 배포하지 않은 채 저장소 이름을 바꾸거나 삭제합니다.
2. 공격자가 비어 버린 그 이름으로 새 저장소를 만듭니다.
3. 새 저장소의 워크플로에서 발급된 OIDC 토큰에는 같은 이름이 들어 있으므로, npm은 이를 정당한 배포 주체로 받아들입니다.
4. 공격자는 원래 패키지 이름 그대로 악성 버전을 올릴 수 있습니다.

Bloom은 이런 조건에 해당하는 패키지를 1,500개 넘게 찾았고, 누적 다운로드는 1천만 회 이상이라고 밝혔습니다. 6월에 GitHub에 제보됐고, 현재까지 실제 악용 사례는 보고되지 않았습니다.

### GitHub가 바꾼 것

GitHub는 10월 2일 changelog를 통해 다음 변경을 적용했습니다.

- **검증되지 않은 trusted publisher 설정은 생성 후 48시간이 지나면 만료됩니다.** 첫 배포가 성공해야 "검증됨" 상태가 되고, 그 뒤로는 만료되지 않습니다.
- 저장소나 프로젝트 식별 정보를 바꾸면 새 신뢰 관계로 취급되어 48시간 창이 다시 시작됩니다. 일반적인 설정 수정은 기한을 늘려 주지 않습니다.
- GitHub Actions의 `issue_comment` 이벤트에서 발급된 토큰으로는 더 이상 배포할 수 없습니다. 기존의 `pull_request_target` 제한도 그대로 유지됩니다.

### 개발자가 할 일

- npm 패키지 설정의 trusted publisher 목록을 열어, 등록된 저장소 이름이 지금도 내가 관리하는 저장소를 가리키는지 확인합니다.
- 저장소 이름을 바꾸거나 다른 조직으로 옮겼다면 기존 설정을 지우고 새로 등록합니다.
- 새로 설정한 경우 48시간 안에 실제 배포를 한 번 돌려 검증 상태로 만들어 둡니다. 그렇지 않으면 다음 릴리스 때 배포가 실패합니다.
- 댓글 명령으로 배포를 트리거하던 워크플로가 있다면 `push`, `release`, `workflow_dispatch` 같은 이벤트로 옮깁니다.

```yaml
# 예: 릴리스 생성 시에만 배포
on:
  release:
    types: [published]
permissions:
  id-token: write
  contents: read
```

## 2. Docker Hub GhostPat: 계정 전환 한 번으로 남의 토큰을 손에 넣다

Docker가 10월 12일, 약 2년 동안 Docker Hub에 남아 있던 치명적 취약점(CVE-2026-105445, CVSS 4.0 기준 9.4)에 대한 보안 권고를 냈습니다. 발견자들은 이를 **GhostPat**이라고 부릅니다.

### 동작 방식

Docker Hub에는 개인 계정을 조직(organization)으로 전환하는 기능이 있습니다. 전환할 때 새 조직의 소유자로 다른 사용자를 지정하는데, 이때 원래 계정의 개인 액세스 토큰(PAT)이 **비밀값은 그대로인 채 소유자만 지정된 사용자로 바뀌어** 넘어갔습니다. 지정된 사용자에게 동의를 묻거나 알리는 절차도 없었습니다.

결과적으로 공격자는 자기 계정에서 토큰을 만든 뒤, 계정을 조직으로 바꾸면서 피해자를 소유자로 지정하기만 하면 됐습니다. 그러면 공격자가 이미 알고 있는 토큰이 피해자 권한으로 레지스트리에 인증되어, 피해자 저장소의 이미지를 pull, push, 삭제할 수 있었습니다. 웹 콘솔 로그인이나 비밀번호, 2단계 인증 설정까지는 건드릴 수 없었습니다.

### 피해 여부와 Docker의 조치

- 취약 기간은 2024년 8월 26일부터 수정이 배포된 2026년 9월 30일까지입니다. Docker는 제보 후 4시간 이내에 서버 측 수정을 적용했다고 밝혔습니다.
- 전환된 토큰으로 이뤄진 약 30만 4천 건의 push를 검토했지만 악용 흔적은 찾지 못했다고 합니다. 다만 pull과 삭제에 대해서는 같은 수준의 결과를 공개하지 않았습니다.
- 10월 2일 해당 사용자에게 메일로 알렸고, 10월 8일 전환된 토큰을 일괄 비활성화했습니다. 앞으로는 소유자 지정 시 동의를 받고 알림을 보내며, 토큰 소유자 변경을 모두 기록합니다.

### 점검 포인트

- Docker Hub 계정 설정의 Personal access tokens 목록에서 모르는 토큰이나 쓰지 않는 토큰을 폐기합니다.
- 계정 전환 메뉴에 내가 가입한 적 없는 조직이 보이는지 확인합니다.
- CI에서 개인 PAT로 이미지를 올리고 있다면, 가능한 경우 조직 액세스 토큰으로 바꾸는 것이 좋습니다. 사람 한 명의 계정에 배포 권한이 묶여 있는 구조 자체가 위험 요소입니다.

## 3. GitLab, 인증 없이 서버 코드 실행이 가능한 CVSS 10.0 취약점 패치

GitLab은 10월 12일 **19.4.2, 19.3.5, 19.2.8** 긴급 패치를 배포했습니다. 가장 심각한 CVE-2026-97229는 CVSS 10.0으로, 인증되지 않은 공격자가 특정 조건에서 CI/CD 설정에 조작한 정규 표현식을 넣어 GitLab 서버에서 임의 코드를 실행할 수 있는 문제입니다. 원인은 정규 표현식 검증 부족으로 설명됐습니다.

같은 릴리스에는 이 밖에도 20여 건의 보안 수정이 들어 있는데, CI를 쓰는 팀이라면 눈여겨볼 만한 항목이 여럿입니다.

- 조작된 저장소를 통한 저장형 XSS (CVSS 8.7)
- Developer 권한으로 보호 브랜치에서 파이프라인을 실행할 수 있던 권한 우회 (8.5)
- 캐시된 raw 파일을 오염시켜 보호된 CI/CD 환경 변수가 노출될 수 있던 문제 (8.2)
- EE 버전에서 AI 에이전트 지시문에 내용을 주입해 의도하지 않은 명령을 실행시킬 수 있던 문제 (7.3)

GitLab.com은 이미 패치가 적용됐고 Dedicated 고객도 따로 할 일이 없습니다. **사내에서 GitLab을 직접 운영(self-managed)하고 있다면 가능한 한 빨리 업그레이드해야 합니다.** 단일 노드 구성은 마이그레이션이 끝날 때까지 서비스가 멈추므로 점검 시간을 잡아 두는 것이 좋습니다.

## 4. Meta, 첫 프런티어 모델 Muse Wonder 공개

Meta의 Superintelligence Lab이 10월 12일 **Muse Wonder**와 **Muse Wonder Full**을 공개했습니다. 4월의 Muse Spark가 가볍고 빠른 응답에 초점을 맞춘 모델이었다면, 이번에는 최상위 모델들과 정면으로 경쟁하겠다는 첫 시도입니다.

- **Muse Wonder**: Meta Model API로 제공됩니다. 보도에 따르면 가격은 입력 100만 토큰당 4달러, 출력 100만 토큰당 20달러로, 다른 회사의 상위 모델과 비슷한 가격대입니다.
- **Muse Wonder Full**: Meta의 AI 코딩 도구 Muse Code 구독자에게만 제공되고, API로는 쓸 수 없습니다.
- 두 모델 모두 Meta의 개인 에이전트 Muse에 탑재될 예정입니다.

Meta는 모델 카드에서 코딩 같은 복잡한 작업 성능이 다른 회사의 최상위 모델과 대등하고, 사용자가 준 정보를 기억해 이어서 활용하는 **"active memory"** 계열 벤치마크에서는 앞선다고 주장합니다. 다만 구체적인 점수는 자체 발표 기준이므로, 실제로 쓸지 판단하려면 내 작업에 직접 돌려 보는 편이 정확합니다.

개발자 입장에서 의미 있는 점은 선택지가 하나 더 늘었다는 것입니다. 이미 여러 모델을 갈아 끼울 수 있는 구조로 에이전트를 만들고 있다면 후보에 올려 볼 만합니다. 반대로 가장 강한 Full 모델이 API로 열리지 않았다는 점, 그리고 오픈 웨이트 여부가 이번 발표에서 언급되지 않았다는 점은 과거 Llama 시절과 달라진 Meta의 방향을 보여 줍니다.

## 마무리

오늘 소식을 한 줄로 줄이면 **"신뢰는 이름이 아니라 고유한 식별자와 명시적 동의에 묶여야 한다"**입니다. npm은 저장소 이름을, Docker Hub는 계정 전환이라는 편의 기능을 믿었다가 구멍이 생겼습니다. 내 프로젝트의 배포 설정과 토큰 목록을 한 번씩 열어 보는 것만으로도 막을 수 있는 위험이 꽤 많습니다.
