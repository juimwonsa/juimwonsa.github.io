한 주를 시작하는 월요일 소식은 보안 패치와 공급망 후속 조치가 중심입니다. 리눅스 데스크톱과 메일 클라이언트 아래에 깔린 암호화 라이브러리의 취약점, 지난 글에서 다룬 AI 라우터 유출 연구에 대한 OpenRouter의 대응, Firebase 사용자라면 바로 확인할 만한 CLI 업데이트, 그리고 장기 실행 에이전트가 실제로 어디까지 갈 수 있는지 보여 준 연구 사례를 살펴봅니다.

## 1. GPGME 이중 해제 취약점(CVE-2026-129975)과 GPGME 2.3.1

**무엇인가요?**

GnuPG 프로젝트가 11월 20일 GPGME 보안 권고를 냈습니다. GPGME는 애플리케이션이 `gpg`를 직접 호출하지 않고 라이브러리 API로 서명·암호화를 쓰게 해 주는 연결 계층입니다. 매우 긴 사용자 ID를 담도록 조작한 OpenPGP 키 하나로 같은 메모리를 두 번 해제하게 만들 수 있는 버그이며, 내부 추적 번호는 T8557입니다.

**핵심 내용**

- **원인**: `src/engine-gpg.c`의 상태 줄·키 목록 읽기 함수(`read_status`, `read_colon_line`)는 1,024바이트 버퍼로 시작해 필요하면 `realloc`으로 키웁니다. 그런데 새 포인터를 컨텍스트에 되돌려 놓는 시점이 함수 끝이라, 콜백 오류 등으로 중간에 빠져나가면 컨텍스트에 이미 해제된 옛 포인터가 남고 컨텍스트 정리 시 한 번 더 해제됩니다.
- **영향**: 권고문은 서명된 데이터를 보내는 방식 등으로 애플리케이션의 데이터를 빼낼 수 있고, 원격 코드 실행 가능성도 배제할 수 없다고 설명합니다. 즉시 업데이트를 강하게 권합니다.
- **대상**: 공유 라이브러리, DLL, 정적 링크를 가리지 않고 2.3.0 미만의 모든 GPGME입니다(2.3.0은 공개 배포되지 않았습니다). 권고문은 Gpg4win, GnuPG Desktop, 대부분의 메일 클라이언트, 다수의 XMPP 클라이언트, Samba, Flatpak을 예로 듭니다. C++·Qt 바인딩인 GPGMEPP, GPGMEQT는 따로 올릴 필요가 없습니다.
- **수정**: GPGME 2.3.1(11월 19일 자)이 수정 버전이고, Windows 쪽은 Gpg4win 5.1.2에 들어갔습니다. 예전 버전에도 그대로 적용될 가능성이 높은 패치가 함께 제공되는데, 공지 메일 첨부가 제대로 전달되지 않았다는 보고가 있어 T8557 티켓에서 받는 편이 확실합니다.
- **공개 경위**: GitLab이 11월 12일 GnuPG에 알렸고 공동 공개일은 11월 25일이었지만, GitLab이 별도 Ruby 취약점 대응으로 먼저 업데이트를 내야 해서 일정이 앞당겨졌습니다.

**당장 할 수 있는 일**

```bash
# 설치된 GPGME 버전 확인 (배포판에 따라 패키지 이름이 다릅니다)
gpgme-config --version 2>/dev/null || pkg-config --modversion gpgme
dpkg -l | grep -i libgpgme   # Debian/Ubuntu 계열
```

리눅스는 배포판 보안 업데이트가 올라오는 대로 적용하고, GPGME를 정적으로 링크해 배포한 바이너리가 있다면 2.3.1로 다시 빌드해야 합니다. 서명 검증 파이프라인처럼 외부에서 받은 키를 자동으로 가져오는 서버가 있다면 우선순위를 높이세요.

**개발자에게 왜 중요한가요?**

GPGME를 직접 쓰지 않아도 Flatpak, 메일 클라이언트, CI 이미지에 깔린 서명 도구를 통해 간접적으로 쓰고 있을 가능성이 큽니다. 외부에서 받은 공개 키를 가져오는 것만으로 공격 면이 생긴다는 점이 핵심입니다. 컨테이너 베이스 이미지와 Electron 앱 빌드 환경처럼 평소 들여다보지 않는 곳까지 패키지 버전을 점검해 두면 좋습니다.

## 2. OpenRouter, 추론 제공사 3곳 퇴출과 ZDR 엔드포인트 125개 제외

**무엇인가요?**

어제 글에서 다룬 Dragos의 카나리 연구(약 200만 건의 프롬프트에 미끼를 심어 유출 경로를 추적한 연구)의 후속 소식입니다. 여러 모델 제공사를 하나의 API로 묶어 주는 OpenRouter가 11월 22일 공지를 내고 대응 내용을 밝혔습니다.

**핵심 내용**

- **OpenRouter 자체**: OpenRouter 시스템에는 침해나 무단 접근이 없었다고 밝혔습니다.
- **조치**: 제공사 세 곳을 플랫폼에서 내보냈고, 연구에서 지목된 곳에 예방 차원의 제외를 더해 총 125개 엔드포인트를 Zero Data Retention(ZDR) 대상에서 뺐습니다. 영향 가능성이 있는 고객에게는 개별 통지했습니다.
- **앞으로**: 연구진의 테스트 방식을 상시 점검에 도입하고, 요청이 제3자에게 넘어가는 네트워크 경로를 기술적으로 검증하며, ZDR 자격 복원 전에는 보증과 검증을 요구할 계획입니다.
- **제공사 공지**: Novita, Phala, Together가 각자 공지를 냈습니다. Together는 6~7월 요청의 프롬프트 유출을 다룬 보안 사건 글을 올렸습니다. OpenRouter는 퇴출한 세 곳의 이름을 공지에 적지 않았고, 모든 관련 제공사가 공개 입장을 낸 것은 아니라고 덧붙였습니다.

**당장 할 수 있는 일**

OpenRouter로부터 통지 메일을 받았다면, 그 기간 프롬프트에 들어갔을 수 있는 API 키·토큰·DB 접속 정보를 교체하는 것이 우선입니다. ZDR을 전제로 라우팅을 설정해 둔 팀은 지금 쓰는 엔드포인트가 여전히 ZDR 대상인지, 특정 제공사를 허용 목록으로 고정할 필요가 있는지 다시 확인하세요.

**개발자에게 왜 중요한가요?**

라우터의 개인정보 옵션은 라우터가 직접 통제할 수 있는 범위까지만 의미가 있다는 점이 실제 조치로 확인됐습니다. 플랫폼 하나가 125개 엔드포인트를 한꺼번에 재분류했다는 것은, 같은 모델 이름 뒤에 있는 실제 처리자가 생각보다 다양하다는 뜻이기도 합니다. 비용과 편의 때문에 라우터를 쓰더라도 민감한 컨텍스트는 1차 제공사로 직접 보내는 경로를 따로 두는 구성을 고려해 볼 만합니다.

## 3. Firebase CLI 15.37: Cloud Functions의 Node.js 26 런타임 프리뷰와 AI Logic의 Gemini 4 Neon

**무엇인가요?**

Firebase가 11월 18일 CLI v15.37.0을 내놓고, 같은 날 Firebase AI Logic에서 Gemini 4 Neon(`gemini-4-neon`) 지원을 추가했습니다.

**CLI 15.37.0 핵심 변경**

- **Node.js 26 런타임(프리뷰)**: Cloud Functions에서 Node.js 26을 런타임으로 선택할 수 있게 됐습니다. 아직 프리뷰이므로 운영 함수보다는 스테이징에서 먼저 시험해 보는 것이 맞습니다.
- **의존성 보안 업데이트**: 심각도 높음·치명적 권고를 해결하려고 `@modelcontextprotocol/sdk`(1.32.2), `undici`(6.29.1), `proxy-addr`(2.0.8)을 올렸습니다.
- **배포 버그 수정**: `firebase deploy --dry-run`이 없는 Firestore 데이터베이스를 실제로 만들어 버리던 문제가 고쳐져, 이제는 어떤 DB가 어디에 생길지 보고만 합니다. 첫 배포가 실패한 2세대 함수가 이후 배포에서도 호출 불가 상태로 남던 문제, Cloud Scheduler가 없는 리전에 예약 함수를 배포하던 문제도 수정됐습니다.
- **에뮬레이터·기타**: Cloud Functions 에뮬레이터의 `/backends` 엔드포인트에 대한 교차 출처 접근을 에뮬레이터 UI 출처로 제한했고, Crashlytics MCP의 `get_report` 도구에 사용자 지정 키 필터(`filterExpression`)가 추가됐습니다.

```bash
npm install -g firebase-tools@latest
firebase --version   # 15.37.0 이상인지 확인
```

```json
// functions/package.json — 프리뷰 런타임을 시험할 때
{ "engines": { "node": "26" } }
```

**AI Logic의 Gemini 4 Neon**

- Gemini Developer API와 Agent Platform Gemini API 두 제공자 모두에서 안정(Stable) 모델로 쓸 수 있고, 제공자와 관계없이 Blaze 요금제가 필요합니다.
- 입력 1,048,576 토큰, 출력 65,536 토큰까지 지원하며 함수 호출, 구조화 출력, Google 검색 그라운딩 등을 쓸 수 있습니다. 이미지·오디오 출력과 Live API는 지원하지 않습니다.
- Agent Platform 쪽은 단기 제공 모델로 분류돼, 후속 모델이 나오면 이르면 45일 뒤 종료될 수 있습니다. 모델 이름을 앱에 하드코딩하지 말고 Remote Config 등으로 바꿀 수 있게 두는 것이 안전합니다.

**주의점**

모델 표에 따르면 Gemini Developer API에서 `gemini-2.5-pro`, `gemini-2.5-flash` 요청은 12월 1일부터 더 새로운 모델로 넘어갑니다. 지난 글에서 예고를 다뤘던 내용으로, 일주일 남짓 남았으니 앱이 아직 2.5 계열을 부르고 있다면 응답 품질과 비용 변화를 미리 확인해 두세요.

**개발자에게 왜 중요한가요?**

Firebase 백엔드를 운영한다면 이번 CLI는 Node.js 26 시험보다도 `--dry-run` 수정과 의존성 보안 업데이트 때문에 올릴 가치가 있습니다. 특히 CI에서 dry run으로 배포를 검증하던 팀은 이전 버전에서 의도치 않게 DB가 생성됐는지 확인해 볼 만합니다.

## 4. 여러 Claude 에이전트가 6주간 풀어낸 블랙홀 물리 난제 두 개

**무엇인가요?**

Anthropic이 11월 17일 공개한 연구 글이 주말 Hacker News 상위에 오르며 다시 화제가 됐습니다. Claude Fable 5.2가 블랙홀과 관련된 이론물리 미해결 문제 두 개를 풀었다는 내용입니다.

**핵심 내용**

- **문제 1, Hawking-Page 전이**: 약한 결합의 N=4 초대칭 양-밀스 이론에서 이 상전이가 급격한지 완만한지를 가리는 계산입니다. 2003년 논문에서 시작됐지만 마무리되지 않았던 계산을 Claude가 끝냈고, 결과는 급격한 전이였습니다.
- **문제 2, 3차원 중력의 모듈러 부트스트랩**: 기존에 증명된 상한(c/8.5)보다 좁은 상한 c/Λ(Λ는 약 9.1266)를 증명했고, 이 방법 안에서는 그 상한이 최적임도 보였습니다.
- **작업 방식**: 연구자가 미해결 문제를 물었고 Claude가 후보 22개를 제시했습니다. 이후 문제마다 별도 에이전트가 약 6주 동안 백그라운드에서 작업하며 서로의 진행 기록을 읽었습니다. 계산은 독립된 사본이 두 번씩 수행해 대조했고, 부트스트랩 문제는 이전 에이전트가 61번 실패한 뒤 다른 에이전트가 찾은 패턴과 방법론으로 풀렸습니다.
- **검증과 한계**: 결과는 Lean으로 형식 검증됐고 물리학자가 주요 결과를 모두 확인했다고 밝혔습니다. 다만 두 결과 모두 우리 우주를 직접 설명하거나 실용적 응용이 있는 것은 아니라고 Anthropic 스스로 선을 그었습니다.

**개발자에게 왜 중요한가요?**

물리학 내용보다 눈여겨볼 것은 작업 구조입니다. 긴 작업을 여러 에이전트로 나누고, 공유 기록으로 진행 상황을 주고받고, 같은 계산을 독립적으로 두 번 돌려 대조하고, 마지막에 기계적 검증(Lean)과 사람의 확인을 거치는 흐름은 코딩 에이전트 운영에도 그대로 옮겨 올 수 있는 패턴입니다. 실패한 시도가 수십 번 쌓인 뒤에야 성과가 나왔다는 점도, 에이전트 작업의 비용과 검증 체계를 함께 설계해야 하는 이유를 보여 줍니다.

## 마무리

오늘 소식을 묶는 키워드는 보이지 않는 중간 계층입니다. 앱 아래의 GPGME, 모델 앞의 라우터, 배포 앞의 CLI처럼 평소 신경 쓰지 않던 층이 보안과 비용을 좌우하고, 에이전트 연구조차 결국 결과 사이의 검증 계층이 성패를 갈랐습니다.
