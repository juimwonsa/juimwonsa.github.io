이번 주 후반(10월 28~30일)에는 Node.js 쪽 소식이 몰렸습니다. 지난 몇 달 동안 예고만 됐던 일정이 실제로 진행돼서, Node.js 26이 LTS가 됐고 Node.js 27은 새로운 Alpha 채널로 첫 빌드를 냈습니다. 같은 날 거의 모든 JavaScript 프로젝트가 간접 의존성으로 쓰는 minimatch에 DoS 취약점이 공개됐습니다. AI 에이전트가 만든 코드를 어디서 실행할지 고민하는 분들이 볼 만한 도구와, 오픈소스에 AI로 기여하기 전에 확인할 정책 모음도 함께 묶었습니다.

## 1. Node.js 26 LTS Lithium, 그리고 Node.js 27 첫 Alpha

**무엇이 바뀌었나요?**

10월 28일 Node.js 26.13.0이 나오면서 26.x 라인이 공식적으로 LTS가 됐습니다. 코드명은 Lithium입니다. 이번 릴리스 자체는 26.12.1 대비 코드 변경이 없고, `process.release` 같은 메타데이터만 LTS로 바뀐 버전입니다. 지원은 2029년 4월 말까지입니다. 같은 날 24.22.2도 함께 나왔습니다.

LTS가 됐다는 것은 이제 운영 환경에서 26을 기본으로 고려해도 된다는 신호입니다. 26 라인에 들어 있는 주요 변화를 다시 정리하면 다음과 같습니다.

- **Temporal API가 플래그 없이 기본 활성화**되어 있습니다. 시간대를 다루는 날짜 계산을 외부 라이브러리 없이 할 수 있습니다.
- **V8 14.6**으로 올라가면서 `Map`·`WeakMap`의 upsert 메서드 등이 추가됐고, 네이티브 애드온은 다시 빌드해야 합니다.
- **`fetch()`의 바탕이 되는 Undici가 8 버전**이 됐습니다. 저수준 동작이 미묘하게 달라질 수 있어 HTTP 클라이언트 코드는 테스트가 필요합니다.
- `http.Server.prototype.writeHeader()`와 `_stream_*` 계열 내부 모듈이 제거됐습니다. 오래된 패키지가 이 모듈을 직접 불러오면 바로 깨집니다.

```js
// Node.js 26에서는 플래그 없이 동작합니다
const now = Temporal.Now.zonedDateTimeISO('Asia/Seoul')
const nextWeek = now.add({ days: 7 })
console.log(nextWeek.toString())
```

Vercel도 10월 29일 Node.js 26 LTS를 빌드와 Vercel Functions에서 정식 지원하고, 새 프로젝트의 기본 버전으로 바꿨다고 밝혔습니다.

**Node.js 27 Alpha는 무엇이 다른가요?**

Node.js는 27부터 메이저를 1년에 한 번(4월) 내고, 모든 메이저를 LTS로 만듭니다. 그 대신 10월부터 3월까지 Alpha 채널을 운영하는데, 10월 29일 그 첫 결과물인 `v27.0.0-alpha.0.0.0`이 나왔습니다. Nightly와 달리 서명·태그가 붙고, 주요 오픈소스 패키지 테스트(CITGM)를 거친다는 점이 다릅니다. 다만 Alpha 사이에도 API가 바뀔 수 있어 운영용은 아닙니다.

첫 Alpha에서 눈에 띄는 변경은 이렇습니다.

- V8이 15.6 계열로 크게 올라가 `Math.sumPrecise()`, `Iterator.zip()` 등이 기본으로 켜집니다.
- `--max-old-space-size`를 지정하지 않으면 **기본 힙 한도가 물리 메모리의 절반(256MB~4GB 범위)**이 되고, `Buffer`·`ArrayBuffer` 메모리도 이 한도에 포함됩니다. 메모리를 많이 쓰는 서버나 Electron 백그라운드 작업은 지금부터 값을 명시해 두는 편이 안전합니다.
- `structuredClone()`, `postMessage()`, `v8.serialize()`의 직렬화 형식이 바뀌어 이전 Node.js가 읽지 못합니다. 직렬화한 데이터를 디스크나 캐시에 저장해 두는 경우 주의해야 합니다.
- 번들 FIPS 프로바이더가 빠지고 OpenSSL 3 이상이 필요하며, Intel macOS 지원은 실험적 단계로 내려갑니다.

**개발자가 할 일**

- 서버·CI의 기본 런타임을 22에서 26으로 올릴 계획을 세워 두세요. 22는 2027년 4월 30일에 지원이 끝납니다.
- 라이브러리를 관리한다면 CI 매트릭스에 27 Alpha를 추가해 두면, 내년 4월 정식 출시 전에 깨지는 지점을 미리 찾을 수 있습니다.

## 2. minimatch 글롭 패턴 DoS (CVE-2026-118764)

**무엇인가요?**

글롭 패턴 매칭 라이브러리 minimatch에서 10월 29일 공개된 취약점입니다. `optimizationLevel`이 2 이상일 때, 패턴 전처리 단계에서 공격자가 넣은 `**/..` 조각을 반복해서 펼치고 그 결과를 서로 다시 비교하는 과정이 폭발적으로 커집니다. 그래서 짧은 패턴 하나로 CPU와 메모리를 크게 소모시킬 수 있습니다. GitHub이 매긴 점수는 CVSS 4.0 기준 8.7(High)입니다. 수정 버전은 11.0.1입니다.

**왜 신경 써야 하나요?**

minimatch는 직접 설치하지 않았어도 거의 모든 Node.js 프로젝트에 들어 있습니다. glob, Jest, Mocha, ESLint 계열 도구 등이 간접 의존성으로 끌고 오기 때문입니다. 실제로 공개 직후 여러 저장소에서 보안 스캐너가 3.x, 8.x, 9.x, 10.x 버전을 한꺼번에 경고하는 이슈가 올라왔습니다.

**실제 위험은 어디에 있나요?**

- 핵심은 **글롭 패턴을 외부 입력에서 받는가**입니다. 빌드 도구나 테스트 러너처럼 개발자가 직접 쓴 패턴만 처리한다면 위험이 거의 없습니다.
- 반대로 API가 사용자에게서 파일 필터 패턴을 받아 minimatch로 컴파일하는 구조라면, 요청 하나로 서버를 멈추게 할 수 있습니다.
- 10월 30일 기준 공개된 익스플로잇 코드나 실제 공격 보고, CISA KEV 등재는 없습니다.

```bash
# 프로젝트에 들어 있는 minimatch 버전과 경로 확인
npm ls minimatch --all
```

**주의할 점**: 수정은 11.0.1에만 들어갔고, 스캐너는 그보다 낮은 모든 버전을 일괄 경고하고 있습니다. 오래된 메이저는 상위 패키지가 범위를 막고 있어 바로 올리기 어렵습니다. 외부 입력 패턴을 처리하는 코드가 있다면 그 경로부터 11.0.1로 올리거나 패턴 길이·문자를 검증하고, 나머지는 상위 패키지 업데이트를 기다리는 식으로 우선순위를 나누는 것이 현실적입니다.

## 3. kern: AI가 만든 코드를 매번 새 컨테이너에서 돌리는 루트리스 런타임

**무엇인가요?**

10월 29일 GeekNews에 소개된 오픈소스(Apache-2.0) 도구입니다. AI 에이전트의 도구 호출이나 AI가 생성한 코드, CI 작업을 호스트에서 바로 실행하지 않고, 필요할 때마다 컨테이너를 띄웠다가 버리는 방식으로 실행합니다.

**핵심 특징**

- 데몬도 소켓도 없는 단일 정적 바이너리이고, 호스트 root 권한 없이 동작합니다.
- OCI 이미지와 Dockerfile을 쓰며, 기존 `docker-compose.yml`도 읽을 수 있습니다.
- Python·Node SDK와 MCP 서버를 제공합니다. SDK는 기본적으로 네트워크와 호스트 디렉터리 접근을 막고 시간 제한을 겁니다.
- 시간 초과, 메모리 초과, 시작 실패를 서로 다른 결과 코드로 돌려줘서, 에이전트가 원인에 맞게 재시도하거나 설정을 조정할 수 있습니다.
- `--security-profile untrusted` 옵션은 루트 파일시스템을 읽기 전용으로 만들고 모든 capability를 제거합니다.
- 작성자 측정에 따르면 빈 명령 하나를 실행할 때 `docker run --rm`보다 약 80배 빠르다고 합니다.

**개발자에게 왜 중요한가요?**

Claude Code나 Codex 같은 에이전트에게 테스트 실행이나 스크립트 실행을 맡기면, 결국 에이전트가 쓴 코드가 내 컴퓨터에서 돕니다. 매 호출마다 깨끗한 환경을 빠르게 만들 수 있다면, 에이전트용 샌드박스를 Docker보다 가볍게 구성할 수 있습니다. Node SDK와 MCP 서버가 있어 TypeScript로 만든 에이전트 도구에 붙이기도 쉬워 보입니다.

**주의할 점**

- 컨테이너는 호스트 커널을 공유합니다. 작성자도 여러 사용자가 함께 쓰는 호스트에서 악의적인 코드를 돌리는 용도로는 권하지 않습니다. 어제 다룬 Linux 커널 취약점처럼 커널 버그 하나로 격리가 무너질 수 있으니, 완전히 신뢰할 수 없는 코드는 VM 수준 격리가 필요합니다.
- Linux 전용입니다. Windows는 WSL2, macOS는 Linux VM이 있어야 합니다.
- 성능 수치는 작성자 측정값이고 공개된 지 얼마 안 된 프로젝트이니, 도입 전에 직접 확인해 보세요.

## 4. 오픈소스 프로젝트별 AI 기여 정책 모음

**무엇인가요?**

NumPy·SciPy 등에 기여해 온 Melissa Weber Mendonça가 관리하는 GitHub 저장소로, 오픈소스 프로젝트들이 AI로 만든 기여를 어떻게 다루는지 정책을 표로 모아 둔 것입니다. Google 오픈소스 블로그의 10월 30일 주간 소식에서도 소개됐습니다.

**눈에 띄는 내용**

- 목록 안의 상당수 프로젝트가 AI·LLM 사용 기여를 **아예 금지**합니다(Gentoo, libxml2, Forgejo 등).
- 허용하는 프로젝트도 대부분 **AI 사용 사실을 밝히고 사람이 직접 검토**하도록 요구합니다.
- 표기 방식도 제각각입니다. Linux 커널과 Mesa는 커밋에 `Assisted-by:` 같은 태그를 요구하지만, pip·Requests처럼 AI 도구를 `Co-authored-by:`로 넣지 말라는 곳도 있습니다.
- LLVM은 입문자용 good first issue에 AI 도구를 쓰지 못하게 하고, Homebrew는 AI 도움을 받은 PR을 한 번에 하나만 열 수 있게 합니다.

**개발자에게 왜 중요한가요?**

에이전트가 PR까지 만들어 주는 시대라, 의존하는 라이브러리의 버그를 고쳐 PR을 보내는 일도 훨씬 쉬워졌습니다. 그런데 프로젝트마다 규칙이 다르고, 규칙을 모르고 보낸 PR은 바로 닫히거나 이후 기여까지 막힐 수 있습니다. 보내기 전에 해당 프로젝트의 CONTRIBUTING 문서와 이 목록을 한 번 확인하는 습관이 필요합니다. 특히 에이전트가 커밋 메시지에 자동으로 넣는 공동 작성자 표기가 그 프로젝트 정책과 맞는지도 살펴보세요.

## 마무리

이번 주 소식을 관통하는 키워드는 "기본값을 다시 확인하기"입니다. Node.js 26은 운영 기본 런타임이 될 준비를 마쳤고, 27은 힙 한도와 직렬화 형식처럼 조용히 동작을 바꾸는 기본값을 예고했습니다. minimatch는 아무도 직접 설치하지 않은 패키지가 문제가 될 수 있다는 점을, kern과 AI 기여 정책은 에이전트가 만든 코드를 어디서 실행하고 어떻게 내보낼지에도 기본 규칙이 필요하다는 점을 보여 줍니다.
