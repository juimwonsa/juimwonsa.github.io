이번 주말 소식은 "내가 실행하는 코드를 얼마나 믿을 수 있나"라는 질문으로 묶입니다. 패키지 매니저가 내려받은 코드를 정말 검증하는지 실험한 연구, AI 에이전트가 만든 코드를 격리해서 돌리는 샌드박스의 오픈소스 공개, 그리고 코딩 에이전트 쪽의 새 모델과 도구 업데이트를 차례로 살펴봅니다.

## 1. Trail of Bits: 패키지 매니저는 변조된 패키지를 막아 줄까

### 무엇이 나왔나

보안 회사 Trail of Bits가 10월 14일, 패키지 매니저 25종이 **레지스트리 서버가 장악된 상황**에서 변조된 패키지를 걸러 내는지 직접 실험한 결과를 공개했습니다. Docker 컨테이너와 mitmproxy로 "정상 패키지에 악성 코드를 끼워 넣어 내려주는 서버"를 흉내 내고, 기본 설정 그대로 설치했을 때 악성 코드가 실행되는지를 확인하는 방식입니다. 락파일이 있는 경우와 없는 경우를 모두 시험했습니다.

결과는 꽤 냉정합니다. 락파일이 없어도 모든 다운로드를 검증한 것은 **Go와 vcpkg 두 개뿐**이었고, 기본값으로 서명까지 검증한 것은 Go 하나였습니다.

### JavaScript 패키지 매니저는 어땠나

| 도구 | 락파일 해시 검증 | 서명 검증 |
| --- | --- | --- |
| npm | 락파일이 있으면 검증 | 설치 중엔 안 함. `npm audit signatures`를 따로 돌려야 함(Sigstore로 키 확인) |
| pnpm | 락파일이 있으면 검증 | `pnpm audit signatures`가 키를 레지스트리에서 받아 와서, 서버가 장악되면 공격자 키를 믿게 될 수 있음 |
| Yarn | 락파일이 있으면 검증 | 해당 기능 없음 |
| Bun | 락파일(`bun.lock`)이 있으면 검증 | 해당 기능 없음 |

pnpm은 5월에 나온 11.4 이전까지 해시가 맞지 않으면 기본적으로 락파일을 덮어써 버렸다는 점도 지적됐습니다.

### 개발자에게 왜 중요한가

요즘 공급망 공격은 대부분 "악성 버전이 정상적으로 게시되는" 형태라 이번 실험과 시나리오가 다르긴 합니다. 그래도 미러, 사내 프록시, CDN 중 한 곳만 뚫려도 같은 일이 생길 수 있으니, 최소한 락파일이 실제로 지켜지도록 CI를 설정해 두는 것이 좋습니다.

```bash
# CI에서는 락파일과 다르면 실패하도록
npm ci
pnpm install --frozen-lockfile
yarn install --immutable
bun install --frozen-lockfile

# npm은 레지스트리 서명과 provenance를 따로 확인
npm audit signatures
```

### 주의할 점

- 애플리케이션은 락파일을 반드시 커밋하세요. 이번 연구에서도 락파일이 있어야만 검증하는 도구가 가장 많았습니다.
- 락파일은 업데이트를 늦추는 효과도 있으니, Dependabot이나 Renovate로 주기적으로 갱신하는 습관을 함께 들여야 합니다.
- 실험은 도구마다 한 가지 버전과 Ubuntu 환경에서만 진행됐다는 한계가 있습니다.

## 2. Perplexity, 에이전트 샌드박스 SPACE를 오픈소스로 공개

### 무엇이 나왔나

Perplexity가 자사 에이전트 서비스 Computer의 작업 실행 기반인 **SPACE**를 이번 주 Apache 2.0 라이선스로 공개했습니다. AI 에이전트가 작성한 코드나 명령을 작업마다 별도의 **Firecracker microVM**(자체 커널과 파일 시스템을 가진 경량 가상 머신)에서 실행하는 플랫폼으로, Rust로 작성됐고 HTTP API와 SSE로 다룹니다.

### 핵심 내용

- **템플릿에서 샌드박스 생성**: 템플릿을 기준으로 리눅스 환경을 만들고 명령을 실행해 출력을 스트리밍으로 받습니다. 스냅샷은 변경분만 저장합니다.
- **자격 증명은 VM 밖에**: 샌드박스 자체를 신뢰하지 않는다는 전제로 설계돼, API 키 같은 비밀값을 VM 안에 넣지 않고 네트워크 계층에서 바깥쪽이 대신 붙여 줍니다. 외부 접속 허용 범위도 VM 밖에서 통제합니다.
- **E2B 호환 래퍼**: 이미 E2B Python SDK로 샌드박스를 쓰고 있다면 큰 변경 없이 시험해 볼 수 있는 호환 계층이 들어 있습니다.
- **레드팀 결과 공개**: 여러 AI 모델에 VM 탈출을 시도하게 한 108회 실험에서 호스트에 닿은 경우는 없었습니다. 다만 네트워크 제한을 일부 우회한 사례는 있었고, Perplexity는 이를 고친 뒤 재시험에서 막혔다고 밝혔습니다.

### 개발자에게 왜 중요한가

Electron 앱이나 Node.js 서버에 "AI가 코드를 실행해 주는" 기능을 넣으려면 결국 격리 실행 환경이 필요합니다. 지금까지는 E2B 같은 호스팅 서비스나 컨테이너로 해결하는 경우가 많았는데, 대규모로 실제 운영 중인 시스템을 직접 띄워 보고 구조를 참고할 수 있다는 점이 큽니다. 특히 "비밀값은 샌드박스 밖에서 주입한다"는 설계는 규모와 상관없이 따라 할 만한 원칙입니다.

### 주의할 점

- 호스팅 엔드포인트는 없고 직접 운영해야 합니다. KVM을 쓸 수 있는 Linux x86_64 호스트가 필요해서, macOS 개발 머신에서 바로 돌리기는 어렵습니다.
- 레드팀 결과는 Perplexity가 직접 발표한 수치입니다. 도입 전에 자기 환경에서 egress 정책을 따로 검증하세요.

## 3. DeepSeek V4.1 Flash 1017: 코딩 에이전트용 업데이트와 Search API

### 무엇이 나왔나

DeepSeek가 10월 17일 **DeepSeek-V4.1-Flash-1017** 체크포인트를 웹, 앱, API에 배포했습니다. API에서는 기존 `deepseek-flash` 모델 이름이 그대로 새 모델로 연결되기 때문에, 이 이름을 쓰던 서비스는 코드 변경 없이 바로 바뀐 모델을 쓰게 됩니다.

### 핵심 내용

- **코딩·에이전트 성능**: DeepSeek 자체 수치로 DeepSWE에서 77.0점(이전 V4.1-Flash 74.2점)을 기록했고, 이전보다 더 짧은 출력으로 작업을 끝낸다고 설명합니다.
- **스펙과 가격**: 컨텍스트 1M 토큰, 최대 출력 384K 토큰. 피크 시간 기준 입력(캐시 미스) 1M 토큰당 0.3달러, 출력 1.2달러이고 비피크 시간에는 절반입니다.
- **예전 이름 정리**: `deepseek-v4-flash`, `deepseek-v4-flash-vision-exp` 이름은 아직 받지만, 실제로는 새 모델이 응답하고 Flash 가격으로 과금됩니다.
- **Search / Fetch API 공개**: 자체 검색 엔진 기반으로 `POST /v1/tools/search`, `POST /v1/tools/fetch` 엔드포인트가 열렸습니다. 성공 요청 1,000건당 0.75달러, 계정당 5 QPS이며, DeepSeek Harness·Claude Code·Codex를 통한 서버 측 호출은 11월 1일(베이징 시간)부터 과금됩니다.

### 개발자에게 왜 중요한가

DeepSeek API는 OpenAI 호환 주소와 함께 Anthropic 호환 주소(`https://api.deepseek.com/anthropic`)도 제공합니다. 그래서 Claude Code 같은 기존 에이전트 도구에 저렴한 모델을 붙여 보는 실험이 쉽습니다. 에이전트에 웹 검색을 붙이고 싶었다면 별도 검색 API 계약 없이 같은 키로 해결할 수 있다는 점도 실용적입니다.

```bash
curl https://api.deepseek.com/v1/tools/search \
  -H "Authorization: Bearer $DEEPSEEK_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"query": "electron security site:electronjs.org", "count": 5}'
```

### 주의할 점

- 모델 이름이 고정 버전이 아니라서, 프로덕션에서 출력 형식에 민감한 기능이 있다면 이번 같은 조용한 교체로 동작이 바뀔 수 있습니다. 회귀 테스트를 한 번 돌려 보세요.
- 벤치마크는 모두 DeepSeek 발표 기준입니다. 데이터가 해외 서버로 나가는 것이 문제가 되는 서비스라면 사내 정책도 함께 확인해야 합니다.

## 4. OpenCode 2.0: 하나의 백그라운드 서비스로 바뀐 오픈소스 코딩 에이전트

### 무엇이 나왔나

터미널 기반 오픈소스 코딩 에이전트 OpenCode가 메이저 버전 2.0을 공개했고, 이번 주 Hacker News에서도 크게 화제가 됐습니다. 가장 큰 변화는 구조입니다. 터미널, 데스크톱, 웹 클라이언트가 각자 돌지 않고 **하나의 백그라운드 서버**에 붙는 방식으로 바뀌었습니다.

### 핵심 내용

- **Code Mode**: 에이전트가 작은 스크립트 하나로 여러 도구 호출을 이어서 실행할 수 있습니다. 도구를 하나씩 부르며 왕복하는 횟수가 줄어듭니다.
- **백그라운드 작업**: 실행 중인 서브에이전트나 셸 명령을 백그라운드로 보내고 다른 일을 계속할 수 있습니다.
- **git worktree 연동**: 에이전트가 worktree를 만들어 여러 작업을 나란히 진행할 수 있습니다.
- **SDK**: 다른 앱에 OpenCode를 넣거나 서버 API를 호출할 수 있는 새 SDK 패키지가 나왔습니다.

### 주의할 점

- **1.x 플러그인은 2.0에서 동작하지 않습니다.** 쓰던 플러그인이 있다면 2.0 버전이 나왔는지 먼저 확인하세요.
- LSP 설정은 남아 있지만 언어 서버를 실행하지 않아 진단 정보가 나오지 않습니다. 대신 에이전트가 `tsc`나 ESLint를 직접 돌리게 하는 방식을 권장합니다.
- 업그레이드는 먼저 마지막 1.x 버전으로 올린 뒤 `opencode upgrade --major`를 실행하는 순서입니다. 설정과 `.opencode` 디렉터리는 미리 백업해 두세요.

## 마무리

패키지 매니저 연구와 SPACE는 같은 이야기를 반대쪽에서 합니다. 남이 만든 코드든 AI가 만든 코드든, 실행하기 전에 "어디까지 믿을지"를 도구가 아니라 내가 정해 두어야 합니다. 오늘은 CI의 설치 명령이 락파일을 강제하는지부터 확인해 보면 어떨까요.
