화요일 소식은 개발자 책상 위와 배포 파이프라인 바깥에서 벌어진 일들이 중심입니다. 출장용으로 많이 쓰는 여행용 라우터와 원격 KVM이 제조사 클라우드를 통해 감염된 사건, 컨테이너 회사에서 에이전트 보안 회사로 스스로를 다시 정의한 Docker, 모델 크기 대신 반복 횟수로 성능을 끌어올리려는 GLM-5.4, 그리고 앱스토어 심사 바깥의 행정 절차 때문에 앱이 조용히 사라질 수 있다는 사례를 살펴봅니다.

## 1. GL.iNet 클라우드 원격 관리 악용, 라우터와 KVM에 악성코드 설치

**무엇인가요?**

여행용 라우터와 원격 KVM(Comet 시리즈)으로 개발자 사이에서도 많이 쓰이는 GL.iNet이 보안 공지를 냈습니다. 공격자가 GL.iNet 클라우드 원격 관리 서비스의 취약점을 이용해 일부 라우터와 KVM 장비에 악성코드를 설치했고, 회사는 11월 20일 이를 발견했다고 밝혔습니다.

**핵심 내용**

- **경로 차단과 감염은 별개**: 클라우드 쪽 침투 경로는 막았지만, 이 조치가 이미 감염된 장비에서 악성코드를 지워 주지는 않습니다. 최신 안정 보안 펌웨어를 설치하면 이번 사건에서 발견된 악성코드가 공장 초기화 없이 제거된다고 합니다.
- **감염 징후**: 실행 중인 프로세스 목록에 `crond -i /tmp/.log` 문자열이 보이면 감염을 의심해야 합니다.
- **최소 수정 펌웨어(라우터)**: GL-MG1300·GL-MT3000·GL-MT6000은 4.11.1, GL-E5800은 4.10.3, GL-BE3600·GL-BE9300은 4.10.2, GL-BE14000은 4.9.3, GL-BE6500·GL-MT3600BE·GL-MT5000은 4.9.1, GL-BE10000은 4.8.7, GL-AX1800·GL-AXT1800·GL-SFT1200·GL-X3000·GL-XE3000은 4.8.4, GL-MT2500/MT2500A·GL-X2000은 4.7.14입니다.
- **최소 수정 펌웨어(KVM)**: RM1·RM1V2·RM10·RM10RC·RM1PE·RM4PE는 1.10.3, RMQ1은 1.8.7입니다.
- **조사 진행 중**: 감염된 KVM에 연결된 컴퓨터까지 영향을 받았는지는 아직 확인 중입니다. 공식 간이 점검으로 모든 감염 장비를 잡아내지는 못한다고 회사 스스로 밝혔습니다.

**당장 할 수 있는 일**

```bash
# 장비에 SSH로 접속해 의심 프로세스가 있는지 확인
ssh root@192.168.8.1 'ps w | grep "/tmp/.log" | grep -v grep'
```

기본 관리 주소는 장비와 설정에 따라 다를 수 있습니다. 결과가 나오든 나오지 않든 위 목록의 버전 이상으로 펌웨어를 올리고, 클라우드 원격 관리를 실제로 쓰지 않는다면 꺼 두는 편이 안전합니다. KVM으로 서버나 개발 PC를 원격 제어해 왔다면, 그 경로로 입력한 비밀번호와 세션을 교체하는 것까지 고려하세요.

**개발자에게 왜 중요한가요?**

KVM은 연결된 컴퓨터의 키보드·화면을 그대로 넘겨받는 장비이고, 라우터는 개발 PC의 모든 트래픽이 지나가는 길목입니다. 장비 자체의 취약점이 아니라 제조사 클라우드가 뚫리면서 사용자가 아무것도 하지 않았는데도 감염됐다는 점이 이번 사건의 핵심입니다. 홈랩과 원격 근무 장비도 서버처럼 펌웨어 버전과 외부 관리 기능을 목록으로 관리할 때가 됐습니다.

## 2. Docker, 새 브랜드와 함께 에이전트 보안으로 영역 확장

**무엇인가요?**

Docker가 새 브랜드를 공개하면서, 컨테이너 도구를 넘어 AI 에이전트의 격리·보안·거버넌스를 회사의 중심 축으로 내세웠습니다. 발표의 출발점은 에이전트는 단순한 워크로드가 아니라 스스로 무엇을 실행하고 어디에 접근할지 결정하는 행위자라는 관점입니다.

**핵심 내용**

- **Docker Sandboxes**: 에이전트를 독립 커널을 가진 microVM 안에서 실행합니다. 컨테이너보다 한 단계 강한 경계로 에이전트가 호스트에 손대지 못하게 하려는 제품입니다.
- **Docker AI Governance**: 조직 단위로 네트워크·파일 접근 정책을 정하고, 에이전트가 어떤 MCP 도구를 쓸 수 있는지 통제합니다.
- **신뢰의 세 층**: 신뢰할 수 있는 공급망, 신뢰할 수 있는 실행 환경, 신뢰할 수 있는 생태계로 나눠 파트너와 함께 만들고, 특정 벤더에 묶이지 않게 하겠다고 밝혔습니다.
- **기존 제품 유지**: 컨테이너 제품군은 그대로 이어지며, 개방성과 개발자 우선 원칙도 유지한다고 했습니다. 고래 마스코트 Moby도 새로 디자인됐습니다.
- **빠진 정보**: 이번 발표에는 가격, 라이선스, 새 출시 일정 같은 구체적인 수치가 없습니다. Hacker News에서는 Sandboxes가 오픈소스가 아니라는 점과 브랜드 개편 자체에 대한 비판이 많았습니다.

**개발자에게 왜 중요한가요?**

Claude Code나 Codex 같은 코딩 에이전트를 로컬에서 돌리면 에이전트가 내 홈 디렉터리, SSH 키, 클라우드 자격 증명에 그대로 닿습니다. 지금까지는 각자 컨테이너나 VM을 꾸려 막아 왔는데, Docker가 이 영역을 공식 제품군으로 묶었다는 것은 에이전트 격리가 개인 취향에서 조직 정책의 대상으로 넘어가고 있다는 신호입니다. 다만 핵심 격리 계층이 닫힌 소스라는 점은 도입 전에 따져 볼 부분입니다. 팀에서 에이전트 사용 규칙을 정하고 있다면, 어떤 MCP 서버와 네트워크 대상을 허용할지 목록부터 만들어 두면 이런 도구를 쓰든 쓰지 않든 도움이 됩니다.

## 3. GLM-5.4: 같은 레이어를 두 번 돌리는 Loop Transformer

**무엇인가요?**

Z.ai가 GLM-5.4를 공개했습니다. 같은 레이어 묶음을 여러 번 반복 실행하는 Loop Transformer 구조를 쓴 첫 플래그십 모델로, 규모는 약 750B이며 2T~3T 파라미터 모델에 맞먹는 성능을 목표로 한다고 밝혔습니다.

**핵심 내용**

- **만든 방식**: 처음부터 사전 학습하지 않고, 기존 GLM-5 기반 모델을 이어서 학습했습니다. GLM-5 모델의 28개 레이어를 두 번 실행하는 구조입니다.
- **규모를 키우기 위한 장치 세 가지**: 반복마다 토큰별 게이트를 두어 업데이트를 점진적으로 반영하고 활성값이 폭주하지 않게 했습니다. 첫 번째 패스의 희소 KV는 공유하고 패스마다 슬라이딩 윈도를 따로 두는 하이브리드 KV 캐시로, 1M 컨텍스트에서도 배포 비용 증가를 GLM-5.3보다 낮게 유지했다고 합니다. 첫 패스의 희소 어텐션 인덱스를 두 번째 패스에서 재사용해 추가 비용을 줄였습니다.
- **통제 실험**: 파라미터 수가 같은 30B 규모 비교에서 반복 모델은 학습 연산량이 약 10% 더 들었고, 수학·과학 추론·긴 컨텍스트 과제에서 이득이 가장 컸습니다. 대부분의 벤치마크에서 평균 출력 길이도 10~14% 줄었다고 합니다.
- **속도**: 한가한 시간에는 초당 최대 200토큰, 부하가 최대일 때는 초당 70~80토큰입니다.
- **사용 방법**: GLM Coding Plan, ZCode, Z.ai Chat에서 쓸 수 있습니다. API는 출시 예정이지만 날짜가 없고, 가중치는 안전성 보강을 마친 뒤 공개한다고 했습니다.
- **주의점**: 750B 모델 자체의 벤치마크 점수는 공개되지 않았습니다. 성능 주장은 30B 통제 실험과 데모에 기대고 있다는 점을 감안해야 합니다.

**개발자에게 왜 중요한가요?**

같은 가중치를 여러 번 통과시키는 방식은 저장해야 할 파라미터를 늘리지 않고 계산을 더 쓰는 접근입니다. 이 방향이 통한다면 메모리는 그대로 두고 어려운 토큰에만 반복을 더 주는 적응형 연산(Z.ai가 다음 과제로 꼽은 것)으로 이어지고, 자체 호스팅 비용 구조도 달라질 수 있습니다. 당장은 API가 없으니 코딩 플랜에서 실제 작업으로 체감해 보고, 가중치와 API가 나오면 지금 쓰는 모델과 같은 과제로 비교해 보는 정도가 현실적입니다.

## 4. Apple, 9년 된 오픈소스 앱 FSNotes를 EU App Store에서 삭제

**무엇인가요?**

macOS·iOS용 오픈소스 노트 앱 FSNotes의 개발자가 GitHub Discussions에 글을 올려, 앱이 몇 주 전 유럽 전역의 App Store에서 사라졌고 Apple로부터 명확한 이유나 해결 방법을 듣지 못했다고 밝혔습니다. 9년간 운영해 온 앱입니다.

**핵심 내용**

- **발견 경위**: 10월 판매 대금이 지급되지 않으면서 문제가 드러났습니다.
- **지원 요청**: 11월 5일과 11월 17일 두 차례 지원 요청을 넣었지만, 글을 쓴 11월 23일까지 답이 없었다고 합니다.
- **개발자 측 조치**: EU 디지털 서비스법(DSA)에 따른 판매자(trader) 정보를 제출했고, 우크라이나 사업자 등록 서류도 냈지만 검토 중인지조차 알 수 없는 상태입니다.
- **현재 상태**: 앱은 GitHub에서 소스와 함께 무료로 계속 받을 수 있습니다. Hacker News 댓글에는 미국·영국 스토어에서는 아직 보인다는 이야기와 DSA 판매자 검증 문제일 것이라는 추측이 있지만, 원글이 확인한 내용은 아닙니다.

**개발자에게 왜 중요한가요?**

Electron이나 네이티브로 Mac App Store·App Store에 앱을 올리는 개인 개발자라면, 코드와 심사 가이드라인이 아니라 판매자 정보 같은 행정 절차 때문에 특정 지역에서 앱이 내려갈 수 있다는 점을 기억해 둘 만합니다. App Store Connect의 계약·세금·판매자 정보 상태를 주기적으로 확인하고, 지역별로 앱이 실제로 노출되는지 점검해 두면 좋습니다. 스토어 밖 배포 경로(직접 다운로드, GitHub 릴리스)를 하나쯤 열어 두는 것도 이런 상황에서 사용자를 잃지 않는 방법입니다.

## 마무리

오늘 소식을 관통하는 것은 내가 직접 다루지 않는 바깥 계층에 대한 신뢰입니다. 제조사 클라우드, 에이전트를 감싸는 실행 환경, 앱스토어의 행정 절차처럼 내 코드 밖에 있는 층이 결국 보안과 배포를 좌우하니, 그 층을 목록으로 만들고 대안 경로를 하나씩 준비해 두는 습관이 필요합니다.
