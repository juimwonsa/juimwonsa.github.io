오늘은 보안 사고 하나와 새 개발 도구 셋입니다. 먼저 이번 주 GitHub에서 벌어진 대규모 CI 시크릿 탈취 캠페인을 자세히 다룹니다. 공개 저장소에 쓰기 권한이 있는 계정을 쓰고 있다면 오늘 바로 점검해 볼 만합니다. 이어서 AWS가 직접 만든 로컬 에뮬레이터, 에이전트 안의 판단 단계를 싸고 빠르게 처리하려는 Google의 새 API, 그리고 Expo가 내놓은 React 없는 크로스플랫폼 런타임을 살펴봅니다.

## 1. wfx: 탈취된 GitHub 계정 4,837개로 CI 시크릿을 쓸어 담은 캠페인

**무슨 일이 있었나요?**

11월 10일(UTC)부터 공격자가 실제 개발자들의 GitHub 계정으로 로그인해, 그 계정이 쓰기 권한을 가진 저장소에 CI 시크릿 탈취 스크립트를 심었습니다. Aikido Security가 처음 알렸고, Endor Labs와 SafeDep이 분석을 보탰습니다. 스크립트 안에 붙은 이름을 따 wfx라고 부릅니다. 타이포스쿼팅이나 의존성 혼동 같은 속임수가 아니라, 진짜 계정과 진짜 권한을 그대로 쓴 공격이라는 점이 핵심입니다.

**규모**

- 자격 증명이 악용된 계정은 4,837개입니다.
- 쓰기 권한을 확인하는 탐색용 PR은 6만 개가 넘는 저장소에 열렸고, 실제로 시크릿이 빠져나간 저장소는 최소 1,806개로 집계됐습니다.
- 이 중 1만여 건은 계정 주인의 저장소가 아니라 협업자나 조직 권한으로 접근한 남의 저장소였습니다.
- SafeDep이 공개 저장소의 기본 브랜치만 훑어도 악성 커밋을 받은 저장소가 8천 개를 넘었습니다. 대부분은 기존 워크플로에 스크립트를 덧붙이는 방식이었고, 수백 곳은 `package.json`의 `postinstall` 훅으로 심겼습니다.
- 패키지 배포 권한이 있는 계정도 최소 50개 포함돼 있어, 후속 악성 릴리스 가능성이 거론됩니다. Packagist와 Go 모듈에서는 악성 버전이 이미 확인됐고, WebdriverIO 봇 계정으로도 커밋이 들어갔습니다(패키지 릴리스 영향은 없었다고 합니다).

**공격 흐름**

1. `wfx-docs` 브랜치에서 문서 수정처럼 보이는 PR을 열어 쓰기 권한과 PR 워크플로 실행 여부를 떠봅니다.
2. 기존 워크플로에 수백 줄짜리 단계를 끼워 넣거나, 숨김 셸 스크립트와 `postinstall` 훅을 추가하거나, 임시 브랜치에 새 워크플로 파일을 만듭니다.
3. 워크플로가 돌면 Actions 시크릿과 변수, `GITHUB_TOKEN`, OIDC 토큰, 클라우드·레지스트리·AI 서비스 키, 러너 메모리 속 비밀까지 모아 외부 서버로 보냅니다.
4. GitHub OIDC 토큰을 AWS·GCP·Azure 세션으로 바꿔 장기 IAM 키를 만들거나, AWS 역할 신뢰 정책을 아무 계정이나 맡을 수 있게 고치고, Azure에 `wfx-ci-`로 시작하는 페더레이션 자격 증명을 추가해 버팁니다.
5. 곧바로 되돌리는 커밋을 올리고 워크플로 실행 기록과 로그를 지워 흔적을 줄입니다.

**개발자에게 왜 중요할까요?**

저장소 하나의 문제가 아니라 계정 단위의 문제라는 점이 무섭습니다. 내 계정이나 토큰이 새면, 내가 협업자로 들어가 있는 모든 저장소와 조직이 같이 노출됩니다. 피해자 중 한 명은 유출된 GitHub CLI OAuth 토큰이 쓰였다고 밝혔지만, 캠페인 전체의 계정 탈취 경로는 아직 확인되지 않았습니다. 지난 10월 GhostAction 때 털린 계정이 이번에 훨씬 높은 비율로 다시 쓰였다는 분석도 있어, 당시 토큰을 교체하지 않았다면 특히 위험합니다.

**점검 방법**

탐색용 PR만 열렸어도 그 계정은 탈취된 것으로 봐야 합니다. 11월 10일 이후 기록을 기준으로, 내가 쓰기 권한을 가진 저장소를 아래처럼 훑어볼 수 있습니다.

```bash
# 탐색용 PR 찾기 (조직 단위)
gh search prs "docs: dependency audit notes" --owner <조직명> --state open

# 알려진 공격 커밋 메시지 찾기
git log --all --since=2026-11-10 \
  --grep="ci: refresh build cache" \
  --grep="chore: add ci helper" \
  --grep="chore: add dependency audit workflow"

# 남아 있는 공격 브랜치 확인
git ls-remote origin 'refs/heads/wfx-docs' 'refs/heads/chore/*' 'refs/heads/ci-check-*'

# 숨김 스크립트와 postinstall 훅 확인
ls -a | grep '^\.ci-'
jq '.scripts.postinstall' package.json
```

**주의할 점**

- 공격자가 즉시 되돌리고 실행 기록을 지우기 때문에, 지금 파일이 깨끗하다고 안심하면 안 됩니다. 분석 업체들은 워크플로 실행 번호가 중간에 비어 있는지 보는 편이 더 확실한 단서라고 말합니다.
- 스크립트가 실행된 저장소라면 그 워크플로가 닿을 수 있던 모든 시크릿과 클라우드 역할을 노출된 것으로 보고 교체해야 합니다. 키만 바꾸면 끝나지 않습니다. AWS 신뢰 정책에 `"Principal": {"AWS": "*"}` 형태가 생겼는지, 11월 10일 이후 만들어진 IAM 키와 `wfx-ci-*` Azure 페더레이션 자격 증명이 있는지까지 지워야 합니다.
- 해당 커밋 상태에서 `npm install`을 돌린 로컬 머신도 감염된 것으로 보고 키를 교체하라는 권고가 나와 있습니다.
- 장기적으로는 워크플로 파일에 코드 오너 리뷰를 걸고, `GITHUB_TOKEN`을 기본 읽기 전용으로 두고, 배포 시크릿을 보호된 environment로 옮기고, 만료되는 세분화 토큰을 쓰는 것이 기본입니다. 가능한 곳에서는 `npm ci --ignore-scripts`로 설치하고 새 라이프사이클 훅이 생기면 알림을 받도록 해 두면 좋습니다.

## 2. AWS Emulator: AWS 계정 없이 로컬과 CI에서 AWS API 테스트

**무엇이 나왔나요?**

AWS가 11월 11일 AWS Emulator를 공개했습니다. AWS API를 호출하는 코드를 실제 AWS 대신 내 컴퓨터나 개발 서버, CI에서 테스트할 수 있게 해 주는 로컬 에뮬레이터입니다. AWS 계정 없이도 쓸 수 있고, 에뮬레이터 자체 요금은 없습니다. 라이선스는 CC0 퍼블릭 도메인 헌정이라 사실상 제약 없이 쓸 수 있습니다.

**핵심 내용**

- **실행 방식**: Linux 패키지(RPM, Debian)로 로컬 프로세스로 띄우거나, Docker로 macOS와 Windows에서도 실행할 수 있습니다. AI 코딩 에이전트에게 설치와 설정을 맡기는 스킬도 함께 제공합니다.
- **임베디드 모드(Rust)**: Rust 프로젝트에 개발 의존성으로 추가하면 테스트마다 프로세스 안에 격리된 에뮬레이터를 띄울 수 있습니다. 엔드포인트나 인증서 설정이 필요 없어 병렬 테스트에 편합니다.
- **서버 모드**: AWS CLI나 각 언어 SDK의 엔드포인트를 에뮬레이터로 돌리면 기존 코드를 그대로 시험할 수 있습니다.
- **호환성 공개**: 릴리스마다 서비스별로 실제 AWS와 동작이 얼마나 일치하는지 점수를 공개하고, 알려진 차이점은 저장소에서 따로 추적합니다. 일치도 테스트 스위트도 별도 저장소로 공개돼 있습니다.
- **에이전트가 만든 코드**: AWS 블로그에 따르면 코드는 전부 자율 에이전트가 작성했고, 팀은 코드를 직접 쓰거나 리뷰하지 않았다고 합니다. 테스트 작성, 문제 발견, 수정을 맡은 에이전트 팀이 실제 AWS와 결과를 비교하는 테스트 수만 개를 기준으로 계속 고쳐 나가는 구조라고 설명합니다.

**개발자에게 왜 중요할까요?**

지금까지 로컬에서 AWS를 흉내 내려면 서드파티 에뮬레이터에 기대야 했습니다. AWS가 직접 만들고 일치도까지 공개하는 도구가 생긴 셈이라, S3·SQS·DynamoDB 같은 서비스를 쓰는 Node.js 백엔드나 서버리스 코드의 통합 테스트를 클라우드 비용과 자격 증명 없이 CI에서 돌리기가 쉬워집니다.

**주의할 점**

- 개발과 테스트 전용입니다. 운영 워크로드, 부하 테스트, 장시간 실행에는 맞지 않고, 리소스는 메모리에만 있어 종료하면 사라집니다.
- IAM 정책이나 리소스 정책을 AWS처럼 평가하지 않으므로 권한과 보안 테스트에 쓰면 안 됩니다. 에뮬레이터는 통과했는데 실제 AWS에서는 거부되는 경우가 있을 수 있습니다.
- 리전과 계정을 구분하지 않으니 인스턴스 하나에 리전 하나, 계정 하나만 쓰라는 권고가 있습니다.
- 사용 통계 전송이 기본으로 켜져 있습니다. 요청과 응답 내용은 보내지 않는다고 하지만, 회사 정책상 꺼야 한다면 설정으로 끌 수 있습니다.
- 버그 리포트는 받지만 외부 PR은 받지 않습니다. 소스에서 직접 빌드하려면 디스크 공간이 상당히 필요하니 가능하면 배포 패키지나 Docker를 쓰는 편이 낫습니다.

## 3. Gemini Decisions API: 생성 없이 판단만, 최대 1,000개 질문을 한 번에

**무엇이 나왔나요?**

Google이 11월 11일 Gemini Decisions API와 이를 위한 새 모델 Gemini Decision 1(`gemini-decision-1`)을 공개했습니다. 정해진 선택지 안에서 고르는 판단을 위한 API로, 답을 토큰 단위로 생성하지 않고 후보를 채점해 확률과 신뢰도를 돌려줍니다. 라우팅, 도구 선택, 안전 검사, 채점처럼 에이전트 안에서 자주 일어나는 작은 결정을 겨냥합니다.

**핵심 내용**

- **입력**: 텍스트, 이미지, 오디오, 영상, PDF를 섞은 입력을 최대 256K 토큰까지 하나로 보내고, 그 입력에 대한 질문을 최대 1,000개까지 한 요청에 담을 수 있습니다.
- **질문 유형 세 가지**: 예·아니요 확률(`noul`), 2~255개 선택지 중 고르기(`choice`), 0부터 시작하는 순서형 기준 채점(`score`)입니다. 모든 답에 0~1 사이 신뢰도가 붙습니다.
- **지연 시간**: Google 발표 기준 종단 간 150~250ms이고, 질문을 1개에서 100개로 늘려도 지연이 거의 늘지 않는다고 합니다.
- **가격**: 입력 100만 토큰당 0.10달러, 출력 토큰은 0달러입니다. 공통 입력은 요청당 한 번만 과금되고, 질문마다 추가되는 지시문 토큰만 더해집니다. AI Studio에는 시제품용 무료 등급이 있습니다.
- **사용처**: Gemini API와 Google AI Studio에서 Python, JavaScript, REST로 쓸 수 있고, Google Cloud 지원은 곧 제공될 예정입니다. OpenRouter, LangChain, Vercel AI SDK, LiteLLM 등과의 연동이 순차적으로 열립니다.

**개발자에게 왜 중요할까요?**

지금은 "이 요청을 어떤 모델로 보낼까", "이 입력이 정책에 맞나" 같은 판단도 범용 LLM에 프롬프트를 보내고 텍스트 답을 파싱해서 처리하는 경우가 많습니다. 이런 단계를 확률이 붙은 구조화된 답으로 바꾸면 파싱 오류가 줄고, 신뢰도가 낮은 경우만 큰 모델이나 사람 검토로 넘기는 분기를 코드로 깔끔하게 짤 수 있습니다. 한 장의 이미지나 문서에 대해 체크리스트 수십 개를 한 번에 확인하는 검수 작업에도 잘 맞습니다.

**주의할 점**

- 성능과 비용 비교는 Google이 직접 고른 벤치마크 기준입니다. 커뮤니티에서는 정확도는 좋지만 평가 전체 비용은 오히려 높았다는 후기도 나왔으니, 내 데이터로 먼저 재 보는 것이 좋습니다.
- 답을 생성하는 모델이 아니므로 자유 형식 설명이 필요한 곳에는 맞지 않습니다.
- Vertex AI 등 Google Cloud 경로가 아직 열리지 않아, 회사 정책상 Cloud 프로젝트로만 써야 한다면 조금 기다려야 합니다.

## 4. Expo Exact: React 없이 웹·iOS·macOS·Linux 앱을 만드는 에이전트 중심 런타임

**무엇이 나왔나요?**

Expo 공동 창업자 Charlie Cheever가 이번 주 Exact라는 실험적 앱 런타임을 미리 공개했습니다. Rust로 만들었고, 하나의 코드로 웹, iOS, macOS, Linux 네이티브 앱을 만드는 것이 목표입니다. 이름은 Expo지만 React Native와는 별개입니다. React도 JSX도 쓰지 않고, 네이티브 화면을 그릴 때 WebView나 JavaScript 브리지도 거치지 않습니다. 라이선스는 MIT입니다.

**핵심 내용**

- **UI는 Contract, 로직은 TypeScript나 Rust**: 화면은 Exact 전용 선언형 언어인 Contract로 작성하고, 데이터와 로직은 TypeScript나 Rust로 씁니다. Contract는 컴파일돼 각 플랫폼 런타임이 해석하는 가벼운 실행 계획이 됩니다.
- **플랫폼별 렌더링**: 웹은 실제 DOM과 CSS를 쓰는 작은 런타임, macOS와 iOS는 AppKit·UIKit, Linux는 Rust 레이아웃 엔진으로 그립니다. 레이아웃은 CSS의 Block, Flex, Grid 모델을 따릅니다.
- **에이전트용 공통 명령**: 화면 트리 조회, 스크린샷, 탭, 입력, 상태 확인, 로그 같은 명령 10개가 모든 플랫폼에서 똑같이 동작합니다. 같은 테스트 스크립트를 모든 플랫폼에서 돌릴 수 있고, 가상 시계로 시간을 직접 앞당겨 타이밍 때문에 흔들리는 테스트를 줄입니다.
- **오류와 디버깅**: 오류는 타입 정보가 담긴 구조화된 JSON으로 나오고, 화면 요소에서 소스 코드 위치로 바로 이어지는 소스맵을 제공합니다.

**개발자에게 왜 중요할까요?**

React와 Electron으로 데스크톱·웹 앱을 만들어 온 입장에서는 방향이 꽤 다릅니다. 코드를 사람이 아니라 에이전트가 짜고 돌려 보고 고치는 상황을 처음부터 전제로, 빌드부터 화면 확인과 조작, 테스트까지 에이전트가 혼자 돌 수 있게 설계했습니다. 당장 쓸 도구라기보다는, 에이전트 시대의 UI 프레임워크가 어떤 모습일지 보여 주는 실험으로 볼 만합니다.

**주의할 점**

- 1.0 이전의 초기 프로젝트라 API 안정성과 하위 호환을 보장하지 않습니다. 정식 릴리스도 아직 없습니다.
- Android는 실행과 테스트, 에이전트 제어까지만 되고 스토어 배포 패키징은 미완성이며, Windows 지원은 진행 중입니다.
- 새 DSL을 배워야 한다는 부담, Slint나 Qt QML 같은 기존 선택지와의 비교, 아직 소수 개발자 중심이라는 점이 커뮤니티에서 지적됐습니다.

## 마무리

오늘 네 소식에 모두 에이전트가 등장합니다. 에이전트가 만든 에뮬레이터, 에이전트 안의 판단을 맡는 API, 에이전트가 직접 돌리는 앱 런타임이 나온 같은 주에, 공격자는 사람 계정과 CI 권한을 자동화로 대량 악용했습니다. 자동화로 할 수 있는 일이 늘수록 토큰과 워크플로 권한을 얼마나 좁게 주느냐가 먼저 챙길 일이 됩니다.
