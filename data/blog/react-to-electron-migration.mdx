처음 프로젝트를 기획했을 때, 당연히 React로 개발하여 서버에 올리고 도메인을 연결해 웹 서비스로 배포할 계획이었습니다. 하지만 개발이 진행되면서 예상치 못한 요구사항들이 수면 위로 올라왔습니다.

## 1. 왜 웹이 아니라 Electron이었나?

가장 큰 이유는 '오프라인 사용성'과 'OS와의 깊은 연동'이었습니다.

처음에는 단순히 React 빌드 파일을 로컬에서 실행하거나, Flutter 같은 멀티플랫폼 프레임워크를 검토하기도 했습니다. 하지만 우리 서비스가 연동해야 할 대상은 결국 윈도우 기반의 게임 프로그램이었고, 플레이스토어나 앱스토어 같은 스토어 배포가 목적이 아니었기에 윈도우 환경에 가장 최적화된 선택지가 필요했습니다.

결국 익숙한 웹 기술 스택(React, Node.js)을 그대로 활용하면서 데스크톱 앱의 강력한 기능을 쓸 수 있는 Electron을 최종 선택하게 되었습니다.

## 2. Electron의 핵심 기능: 자동 업데이트와 커스텀 프로토콜

Electron을 쓰면서 가장 만족스러웠던 부분은 배포와 인증 과정에서의 편의성이었습니다.

### 서버 동기화 기반 자동 업데이트
배포된 서버의 최신 패키지 버전과 현재 설치된 버전을 비교하여, 업데이트가 있을 때 자동으로 내려받고 설치해주는 기능을 구현했습니다. 웹 서비스처럼 사용자가 항상 최신 버전을 보고 있다는 확신을 줄 수 있어 운영 측면에서 매우 효율적인 기능이었습니다.

### Cafe24 OAuth와 커스텀 프로토콜
기존에 웹에서 사용하던 Cafe24 OAuth 로그인 기능을 데스크톱 앱으로 가져오는 과정이 고민이었지만, Electron의 커스텀 프로토콜(Custom Protocol) 등록 기능을 통해 해결할 수 있었습니다. 브라우저에서 인증을 마치고 myapp:// 같은 주소로 앱을 다시 호출하면, 앱이 이를 감지하여 로그인 처리를 완료하는 흐름은 사용자 경험 측면에서 매우 매끄러웠습니다.

## 3. 기술적 도전과 해결 과정

물론 모든 과정이 순탄치만은 않았습니다.

### 까다로운 IPC 통신
Electron의 보안 모델인 Main 프로세스와 Renderer 프로세스 사이의 데이터 주고받기(IPC)는 생각보다 복잡했습니다. 웹 브라우저 환경에만 익숙했던 저에게 보안을 위해 contextBridge와 preload.js를 거쳐야 하는 구조는 생소했습니다. 하지만 이 구조를 이해하고 나니 앱의 안정성과 보안에 대해 깊이 있게 고찰해보는 계기가 되었습니다.

### 버전 업그레이드와 구문 변화
Electron 버전을 최신으로 업데이트했을 때, 이전 버전에서 잘 작동하던 커스텀 프로토콜 등록 코드가 작동하지 않는 문제가 있었습니다. 확인 결과 최신 버전에서는 새로운 등록 구문(Syntax)을 추가해줘야 했습니다. 이 미묘한 변화를 찾아내고 수정하는 과정에서 프레임워크의 변화에 민첩하게 대응하는 법을 배울 수 있었습니다.

## 결론

웹 개발자에게 Electron은 단순히 '웹을 창에 띄우는 것' 그 이상이었습니다. OS의 제약 조건을 이해하고, 로컬 환경의 이점을 활용하는 법을 배우는 귀중한 경험이었습니다.

혹시 웹 서비스의 한계를 느끼고 데스크톱 앱 전환을 고민하고 계신 분들이 있다면, Electron이라는 강력한 도구를 추천합니다. IPC 통신과 버전 관리라는 도전적인 과정이 기다리고 있을지라도 말이죠.
