오늘은 AI를 만드는 쪽, AI에 데이터를 내주는 쪽, AI를 도구로 쓰는 쪽의 소식을 하나씩 골랐습니다. 사내에서 Langflow로 에이전트를 돌리고 있다면 첫 번째 소식부터 확인해 주세요. 웹사이트를 운영한다면 두 번째, Codex를 매일 쓴다면 세 번째 소식이 관련 있습니다.

## 1. Langflow: 로그인 없이 슈퍼유저 세션을 받고, MCP로 코드까지 실행

**무엇이 문제인가요?**

Langflow는 드래그 앤 드롭으로 LLM 워크플로와 에이전트를 만드는 Python 기반 오픈소스 도구입니다. IBM이 10월 28일 보안 공지를 내고 다음 날 CVE 기록을 공개했는데, 그중 두 건이 CVSS 9.8입니다.

- **CVE-2026-93680 (인증 우회)**: 1.0.0부터 1.12.8까지는 자동 로그인(`LANGFLOW_AUTO_LOGIN`)이 기본으로 켜져 있습니다. 이 상태에서는 아무 자격 증명 없이 `/api/v1/auto_login`을 호출하기만 해도 슈퍼유저 세션 쿠키가 발급됩니다. 예전에 토큰 수명을 줄이는 패치가 있었지만 익명 사용자가 세션을 받는 구조 자체는 그대로였습니다.
- **CVE-2026-110186 (원격 코드 실행)**: Langflow는 플로를 MCP 도구로 노출하는 엔드포인트(`/api/v1/agentic/mcp`)를 갖고 있습니다. Ostorlab 분석에 따르면 위의 자동 로그인 세션이 이 엔드포인트 인증도 통과합니다. 그다음 도구 목록을 보고, 서버에서 Python 코드로 실행되는 커스텀 컴포넌트를 넣은 플로를 만들면 곧바로 서버에서 임의 코드가 돌아갑니다.
- 이 밖에 권한이 낮은 사용자가 Agentic Assistant를 통해 OS 명령을 실행할 수 있는 취약점(8.8)과 운영자가 넣어 둔 API 키가 노출되는 취약점(6.5)도 함께 공개됐습니다.

10월 30일 기준으로 실제 악용 사례는 보고되지 않았고 CISA의 악용 취약점 목록에도 없습니다. 다만 인증 없이 MCP 도구 목록을 읽어 오는 Metasploit 모듈이 이미 공개돼 있습니다. 2025년의 Langflow 취약점이 실제 공격에 쓰였던 전례도 있어서 여유를 두기 어렵습니다.

**어떻게 대응하나요?**

수정 버전은 10월 22일에 나온 **1.13.0**이고, IBM은 별도의 임시 우회책을 제시하지 않았습니다. 먼저 내 인스턴스가 열려 있는지 확인합니다.

```bash
# 200이 돌아오면 취약한 상태, 403이면 자동 로그인 경로가 닫힌 상태
curl -s -o /dev/null -w "%{http_code}\n" https://langflow.example.internal/api/v1/auto_login

pip show langflow | grep Version
```

업그레이드할 때는 순서가 중요합니다. 1.13.0부터 자동 로그인이 꺼지기 때문에, 비밀번호 없이 쓰던 설치를 그냥 올리면 로그인을 못 하게 될 수 있습니다.

```bash
# 1) 데이터베이스, 시크릿 키, 업로드 파일, 지식 베이스 디렉터리 백업
# 2) 슈퍼유저 비밀번호를 미리 지정
echo "LANGFLOW_SUPERUSER_PASSWORD=충분히-긴-비밀번호" >> .env

# 3) 업그레이드 후 env 파일과 함께 실행
pip install --upgrade "langflow==1.13.0"
langflow run --env-file .env
```

Docker라면 `langflowai/langflow:1.13.0` 이미지로 바꾸되 영구 볼륨은 그대로 유지합니다. 로그인이 안 된다고 지우고 다시 설치하면 플로가 사라질 수 있으니, 공식 문서의 복구 절차를 따르는 것이 안전합니다. 로컬 Chroma 기반 지식 베이스가 SQLite로 바뀌는 변경도 함께 들어 있으니 백업은 꼭 해 두세요.

**개발자에게 왜 중요한가요?**

에이전트 빌더는 원래 코드를 실행하라고 만든 도구입니다. 그래서 인증이 한 군데만 뚫려도 곧바로 서버 장악으로 이어집니다. 사내망 안에 있으니 괜찮다고 생각하기 쉽지만, 같은 네트워크의 다른 컨테이너나 감염된 개발 PC도 공격자가 될 수 있습니다. 업그레이드 뒤에도 `/api/v1/auto_login` 요청 로그와, 누가 만들었는지 모르는 커스텀 컴포넌트나 API 키가 없는지 한 번 살펴보는 것을 권합니다. Langflow가 아니더라도 MCP 엔드포인트를 노출하는 도구라면 그 엔드포인트가 어떤 인증을 거치는지 점검해 볼 만합니다.

## 2. robots.txt 한 줄로 여러 AI 회사의 학습 거부하기

**무엇이 바뀌나요?**

지금까지 사이트 콘텐츠가 AI 학습에 쓰이지 않게 하려면 `GPTBot`, `ClaudeBot`, `Google-Extended`처럼 회사별 크롤러 이름을 하나하나 적어야 했습니다. 10월 30일, Google, Microsoft, OpenAI, Anthropic이 하나의 공통 토큰 `__usage_ai-training`을 존중하겠다고 밝혔습니다. 바탕이 된 IETF 인터넷 드래프트는 Anthropic의 Kevin Kelley가 같은 날 제출했고, IETF AI Preferences 워킹 그룹이 다루는 어휘 정의를 그대로 가져다 씁니다.

```text
# 사이트 전체를 AI 학습에서 제외하고, 보도 자료만 허용
User-Agent: __usage_ai-training
Disallow: /
Allow: /press-kit/
```

새 문법은 없습니다. 기존 robots.txt 그룹에서 User-Agent 자리에 정책 토큰을 넣는 방식이고, 경로 매칭과 가장 긴 경로 우선 규칙은 RFC 9309를 그대로 따릅니다.

**언제부터, 어떻게 적용되나요?**

- **Anthropic**: 이미 적용을 시작했다고 알려졌습니다.
- **Microsoft(Bing)**: 2027년 2월 1일부터 크롤링하면서 반영합니다. 페이지 단위로는 메타 태그나 `X-Robots-Tag` 헤더로 `ai-training:disallow`를 지정할 수 있고, 페이지 설정이 robots.txt보다 우선합니다.
- **Google**: 2027년 지원을 목표로 합니다. 이 토큰으로 학습을 거부하고 `Google-Extended`를 따로 적지 않았다면 Google-Extended를 막은 것으로 취급하고, Google-Extended를 명시적으로 허용했다면 그 설정을 따릅니다.
- **OpenAI**: 앞으로 몇 달 안에 지원하겠다고만 했고 날짜는 밝히지 않았습니다.

**주의할 점**

- `User-Agent: *` 그룹은 이 토큰에 적용되지 않습니다. 와일드카드로 전부 막아 뒀다고 학습 거부가 표현되는 것이 아니므로 토큰 그룹을 따로 적어야 합니다.
- 이 토큰은 크롤링 차단이 아니라 **사용 방식에 대한 선호 표시**입니다. 크롤러 접근 자체를 막으려면 기존처럼 각 크롤러 이름으로 규칙을 써야 합니다. 반대로 학습만 거부해도 일반 검색 노출에는 영향이 없다고 Microsoft는 설명합니다.
- 다루는 범위는 학습뿐입니다. 검색 결과를 바탕으로 답을 만드는 그라운딩은 별개라서, Bing은 페이지 단위 `ai-grounding` 설정을 따로 두고 2027년 3월 1일 이후에는 기존 NoArchive·NoCache를 학습이나 그라운딩 선호로 읽지 않겠다고 밝혔습니다.
- 드래프트는 아직 IETF 합의를 거친 표준이 아니고, 참여 여부도 각 회사의 자발적인 약속입니다. 이미 학습에 쓰인 데이터에는 소급되지 않습니다.

**개발자에게 왜 중요한가요?**

Next.js라면 `app/robots.ts`, 정적 사이트라면 `public/robots.txt` 한 곳만 고치면 되니 적용 자체는 몇 분이면 끝납니다. 고민해야 할 것은 정책입니다. 학습은 막되 AI 검색 답변에는 노출되고 싶은지, 문서 사이트처럼 오히려 학습되기를 원하는지 정한 뒤, 회사별 규칙과 공통 토큰이 서로 충돌하지 않는지 확인해 두는 편이 좋습니다.

## 3. 12월부터 ChatGPT와 Codex가 사용량을 함께 씁니다

**무엇이 바뀌나요?**

OpenAI 도움말 센터에 따르면 12월부터 Plus, Pro, Business 구독자는 ChatGPT와 Codex의 사용 한도를 하나로 합쳐 쓰게 됩니다. GeekNews 요약에 따르면 Work의 에이전트 기능을 ChatGPT 기본 경험으로 들여오는 변화와 함께 이뤄집니다.

- 사용량은 토큰 단위로 계산되고, 같은 작업이라도 어떤 모델을 쓰는지와 작업이 얼마나 복잡한지에 따라 차감량이 달라집니다.
- Instant 채팅은 공유 한도에서 차감되지 않습니다.
- 남은 사용량과 초기화 시점은 설정의 사용량 메뉴에서 볼 수 있습니다.
- 한도에 닿으면 초기화를 기다리거나, 요금제를 올리거나, 크레딧을 사서 크레딧 대상 기능을 계속 쓸 수 있습니다.

OpenAI는 대부분의 사용자가 지금보다 더 자주 기다리지는 않을 것이라고 설명했지만, 요금제별 전체 한도와 모델별 차감률은 공개하지 않았습니다. Hacker News에서는 기준이 투명하지 않다는 비판과, Codex를 많이 쓰다가 일반 채팅까지 막힐 수 있다는 걱정이 많았습니다.

**개발자에게 왜 중요한가요?**

지금은 채팅으로 설계를 의논하고 Codex로 구현을 맡겨도 서로의 한도를 갉아먹지 않습니다. 12월부터는 한쪽을 많이 쓰면 다른 쪽도 함께 줄어듭니다. 특히 에이전트를 길게 돌리는 날에는 오후에 채팅을 못 쓰는 상황이 생길 수 있습니다. 12월이 오기 전에 다음을 준비해 두면 좋겠습니다.

- 한 주 동안 Codex를 얼마나 쓰는지 사용량 화면에서 미리 감을 잡아 두기
- 단순한 질문은 Instant 채팅으로 돌려서 공유 한도를 아끼기
- 무거운 자동화나 CI 작업은 구독 대신 사용량만큼 과금되는 API 키로 분리해 예측 가능하게 만들기
- 팀 단위라면 Business 요금제에서 누가 얼마나 쓰는지 확인할 방법을 미리 정해 두기

지난주 Claude Code의 백그라운드 요약 호출이 사용량을 많이 잡아먹는다는 분석까지 떠올리면, 이제 AI 코딩 도구는 성능만큼이나 한도를 어떻게 세고 보여 주는지가 선택 기준이 되고 있습니다.

## 마무리

세 소식 모두 AI 도구가 이제 정책과 경계의 문제가 됐다는 점을 보여 줍니다. 에이전트 빌더는 인증 경계를, 웹사이트는 데이터 사용 경계를, 구독 서비스는 사용량 경계를 다시 그리고 있습니다. 덧붙여 Next.js의 11월 정기 보안 릴리스가 미국 시간 11월 3일(한국 시간 오늘 밤에서 내일 새벽)로 예정돼 있으니, 업그레이드 시간도 함께 잡아 두시길 바랍니다.
